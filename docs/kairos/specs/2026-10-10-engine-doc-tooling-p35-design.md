## Design

本相位收口 plan 文档读取的一处权威缺口：同一份 plan 有**九个读取点（共十处到达 plan 解析的站点，含登记行一处）、四种失败策略**，坏结构的两个面分别是「静默放行」与「裸崩」。根因不是某个被吞掉的 `catch`，而是**读取权落在视图平面**——`face/cli.ts` 把 `BoardView.planGraph` 这条渲染路径的产物当门禁证据注入 session，于是一个 draw 契约变成了 gate 契约。计数口径写死在此：度量的单位是**到达 plan 解析的站点**，不是「拼出 `new PlanDocType("plan")` 的站点」——`grep -rn 'new PlanDocType("plan")' packages/cdd-engine/src-next`（排除 `__tests__/`）共 9 处 = 8 个显式读取点 + `contract/doc.ts` 登记行 1 处；第九个读取点是 `session/ledger.ts` 的 `Ledger#briefRevision`，它经由 `readonly #brief = new BriefRenderer();`（`session/ledger.ts:668`）的默认参数到达解析，这条 grep 看不见它。故总计 10 = 9 读取点 + 1 登记行，与 overall D90 / Phase-inventory 的 `9+1`、四策略同源。

裁定把 plan 的 read + parse + classify 收进 `infra/plan-source.ts` 的一处深类，失败成为一个携带行为的判别值，坏结构走既有的 `doc-contract` 拒绝通道，降级成为带警告的显式值，「读不出」不再授权下游结论。三件不破坏的事：plan grammar 语义不动、`doc-contract` 判定语义与既有拒绝报文不动、健康 plan 的板面与 `next:` / `reason:` 字节不动。

### 1. 病根

#### 1.1 一份文档、九个读取点、一个登记行、四种策略

九个读取点（模块 + 符号，非行号）分四类策略：

| 读取点 | 策略 | 坏 plan 的后果 |
| --- | --- | --- |
| `face/board-view.ts` 的 `BoardView.planGraph` | 捕获 → `null` | `  wave     (none)`、exit 0、`next:` 照常 |
| `face/cli.ts` 的 `Cli#sceneOf`（场景装配） | 裸抛 | 无 BLOCKED 面、无 path、无 `next:` |
| `face/cli.ts` 的 `Cli#renderWaveBoard` | 裸抛 | 同上 |
| `face/cli.ts` 的 usage 校验（`planIds` 块，`Cli#runWork` 内） | 裸抛 | 同上 |
| `session/preflight.ts` 的 `PreFlight#vet` graph 门禁 | 裸抛 | 同上（且被场景装配抢先） |
| `session/preflight.ts` 的 `PreFlight#ledgerFactsOf` | 裸抛 | 同上 |
| `render/brief.ts` 的 `BriefRenderer`（构造注入解析器，`extract` 内解析） | 裸抛 | 同上（本相位删除该解析：`BriefRenderer` 的 `render` / `taskBody` / `extract` 三面改收 `text` + `doc`，`PlanRead.text()` / `PlanRead.doc()`，见 §2.1 / §2.6） |
| `session/run.ts` 的 `Lifecycle#recordPlanSnapshot` | 捕获 → 不记快照 | 快照缺失在 wave 门里保守读作 `stall` |
| `session/ledger.ts` 的 `Ledger#briefRevision`（`:941`；经 `readonly #brief = new BriefRenderer();`（`:668`）的默认参数到达解析） | 捕获 → `null`（brief 事实不记） | 该次 review/fix 完成时不记 brief 修订，`briefDrifted` 读作未漂移、已评审波次不重开 |

`Lifecycle#recordPlanSnapshot` 是**策略正确的那一个**（缺失 → 拒绝，而非放行），本相位保留它的语义，只把「吞掉的缺失」换成「已知的缺失」——它改吃 `PlanRead`，非 ready 不记快照。`Ledger#briefRevision` 是第四类：它同样 `catch → null`，但吞掉的不是图而是一条修订哈希——算不出就不记，与「present facts only」一致；它与第一类不是一件事，后者把图吞成 `null` 后板面读作「没活干」，而这里不记的是「这次评审的 brief 基准是哪一版」。

**登记行**（唯一合法的构造点，不是读取点）：`contract/doc.ts` 的 `docTypeParsers` 里 `plan: new PlanDocType("plan")`。

**渲染消费点**（只读 `null` / 空集，不是解析点，移出上表）：`BoardView.#waveLines`、doc 面 `BoardView.render`、`BoardView.#programBoard` 内的 `waveCell` 局部。三处今日把「零 task block」「没有 plan」「读不出」压成同一个空值/`(none)`，§2.4 逐个拆开。

判定面另有一处通用分发：`contract/judge.ts` 的 `#contextOf` 直接调 `docTypeParsers[input.docKey].parse(...)`，于是同一份文档的 body 坏结构会把**判定门自己打死**，而不是产出一行 `Finding`。

顺序事实（今日成立、须有 pin）：`PreFlight` 的 doc-contract 结构拒绝发生在 `face/gate.ts` 的 `renderBrief` **之前**。这个顺序今日是 `BriefRenderer` 裸抛的唯一保障；本相位把 brief 的第二处解析删掉（§2.1 / §2.6），保障于是不再依赖时序——`renderBrief` 拿到的已是 `PlanRead.doc`，它没有解析可抛。

#### 1.2 为什么补 `catch` 不管用

两个面是同一个缺陷的两端：board 吞掉后把「读不出」渲染成「没活干」，dispatch 则在更早的场景装配处裸崩成 `cdd: task 27 carries the reserved section "#### DependsOn" more than once`。补 `catch` 只会把裸崩面也改成静默，让「读不出」在所有面上都读作「没活干」。

形式化的病句：**证据缺失被读作缺失的证据**。`session/pipeline.ts` 的 `#waveState` 把 `graph === null` 读作「wave 面从未进入」，`#wavesExhausted` 读作「没关门」，`session/dispatch-authority.ts` 的 `#waveStation` 读作「无站牌」——三处同一个推理错误，靠 `null` 这一个值串起来。

正确形状在同一份文档里已经存在：front-matter 的坏法走 `contract/frontmatter.ts` 的 `get parseError`，由 `session/preflight.ts` 的 doc-contract 块变成一次带 `routeWord("frontmatterParse")` 的拒绝。差别只在 `parse(): PlanParsed` 是「全成功或裸抛」，而 `parseError` 是值。

#### 1.3 为什么读取必须离开视图面

`contract/judge.ts` 的 `ContractInput` 只带 `content: string`——判定面按值收原文、从不读盘，读盘归 `infra/`（`infra/slug-index.ts` 已按 front-matter 读文档）。这是一个**按面分工**的判据，不是「`contract/` 不碰 IO」：`contract/invariants.ts` 里就住着 `DocFs` / `NodeFs` 读缝。而视图面持有读取权，就把「怎么渲染」升级成了「怎么判」：`face/cli.ts` 场景装配把 `BoardView.planGraph` 的结果当门禁证据往下传，视图因此成为门禁的上游。

#### 1.4 否决面（issue 的四条建议各自停在哪）

- 建议①「返回类型化的失败值」——停在返回类型：谁读、谁判、判据在哪，一个问题没回答。
- 建议②「board 打一行 `CDD_WARN`」——只覆盖视图面，dispatch 的裸崩面原封不动。
- 建议③「新增 `doc-structure` violation 类」——`doc-contract` 已是结构拒绝类，新增等于扩令牌表（P27 的十三 token 分腿），收益只是诊断更细，而 path / field / message 已经在报文里。
- 建议④「`next:` 必须说明被什么挡住」——`next:` 是路由分类器的单一出口，为一个拒绝类分叉会让「路由 == 门禁 == 渲染」多一个例外；「被挡住」的可见性由 `CDD_BLOCKED:` + `reason:` + 报文承担。

### 2. 裁定

#### 2.1 读取收进 `infra/plan-source.ts`：一个深类、两个入口、一个携带行为的值

新增深类 `PlanSource`（家：`infra/plan-source.ts`），构造注入 `DocFs`（默认 `NodeFs`）与 `RepoRoot`，**路径过 `RepoRoot` 的转换对**：`this.#root.resolve(this.#root.relativize(rel))`。`RepoPath` 是带品牌的值（`infra/root.ts` 的 `type RepoPath = string & { readonly __repoPath: unique symbol }`），`relativize` 是它的**唯一构造入口**（`RepoRoot#relativize`：把绝对路径或调用方相对串归一成 repo 相对——它的注释原文即「a bare `docs/x.md` is read relative to repoRoot, NEVER to `process.cwd()`」），`resolve` 是**唯一擦除点**（`RepoRoot#resolve` → 绝对串）。派生面拼出来的模板串与 `DocEntry.rel` 都是普通 `string`，不经这一对就过不了 `tsc`；也不存在「先裸读再兜底」的支路。理由不是洁癖：`NodeFs` 吃字面路径（`existsSync` / `readFileSync`，不经 rebase），按 `process.cwd()` 解析，而仓库根是**逐命令**的事实（`#rootOf()` = `git.topLevel(process.cwd())`，cwd 可以是仓库子目录），今日 dispatch 面的读正因此是根锚定的——站点 `packages/cdd-engine/src-next/face/artifacts.ts` 的 `Artifacts#readText`（`readText(node: Command, root: RepoRoot, file: RepoPath)` → `root.resolve(file)` → `readFileSync`）；不经 `RepoRoot` 的 repo 相对串在子目录下会把健康 plan 读成 `unreadable` / `io`，静默违反「健康 dispatch 报文逐字节不变」。因根要逐命令解析，实例在**命令前奏**（`#rootOf()` 之后）构造一次，作为该命令的单一实例经参数下行到 `Cli#runBoard` / `Cli#sceneOf` / `PreFlight`；`Cli.create()` 阶段尚无根，不在那里构造——「一份读取」的落地口径是**每个命令一个实例、每份文档一次读**，不是进程级单例。两个入口，同一个 `PlanRead`：

- `readFor(entry: DocEntry): PlanRead` — 相位文档的**派生面**：`entry.slug` 是唯一身份，路径是 slug 的纯函数——`` `${ENGINE_RUNTIME.docRoots.plans}/${slug}.md` ``（`infra/doc-roots.ts` 的 `ENGINE_DOC_ROOTS.plans` 就是「slug → doc-tree 反向派生」的根，该文件的注释原文即如此；`ENGINE_DOC_ROOTS` 是全库唯一的根值，`face/declare.ts` 的 help 示例也从它派生）。`slug === null` → `undeclared`；否则**先探存在性**（`DocFs.exists`），不存在 → `undeclared`（该相位还没有 plan，今日的 `(none)` 逐字节不变）；存在才读字节——`read` 回 `null` → `unreadable` / `io`。这条派生**不咨询索引的内容谓词**（索引把「读得出」当入册前提，`infra/slug-index.ts` 的 `#scanRoot` 丢掉不可读候选），所以「存在但读不出」零声明、零新字段就可达 `cause: "io"`。

**没有声明键**：slug 是唯一的文档声明，路径不写进 front matter。写进去的坏处是造出第二个可与 slug 冲突的事实源（声明指 A、slug 派生指 B 时谁对？），而主编排器的错（spec 与 plan 的 slug 不一致）不该由文档内容去兜——那种不一致读出来就是 `undeclared`，症状 `(none)`，与「还没写 plan」同一副面孔；那是 slug 面自己的事，不是读权的事。这条派生的判据是「每份 plan 的文件名等于它的 front-matter `slug`、每份 spec 的文件名等于 `<slug>-design.md`、每份 overall 等于 `<slug>-overall.md`」，**不是**今天的快照——它从落地第一天起就成立（当下语料 34 份 plan ↔ 34 份 spec，0 份文件名与 slug 不符），被打破时的落点也已钉死：正查侧读作 `undeclared`（`(none)` + exit 0，不回退到任何索引猜测，AC #4 第三条），反查侧落成孤儿拒绝（§2.7）——派生方向因此是既有事实，不是本相位的新约定。代价写在这里：非派生路径（同一份 plan 被两个相位共用、或文件名另起）因此不可表达，补救是改名而不是加键。`#scanRoot` 的扫描谓词仍不动——从「刻意不动」变成「根本不需要动」。同理，`FrontMatterHead#plan`、`DocEntry.declaredPlan`、越域校验与 `planPathInvalid` 词行**全部不存在**：没有作者给的路径，就没有域可校；plan 行的字节基准仍是 repo 相对形式，派生值天然如此。

- `readPath(rel: string): PlanRead` — argv 直给路径的读取面：`cdd board --plan` 与三条 argv 驱动读者（usage 校验的 `planIds` 块、`Cli#renderWaveBoard`、`Cli#sceneOf`）共用它，不再各写一次「索引里没有就当没读」。

判别值三态：

```ts
type PlanRead =
  | { readonly kind: "undeclared" }
  | { readonly kind: "unreadable"; readonly path: string; readonly cause: "io" | "syntax"; readonly message: string; readonly field: string | null }
  | { readonly kind: "ready"; readonly path: string; readonly text: string; readonly doc: PlanParsed; readonly graph: TaskGraph; readonly orphan: PlanOrphan | null };

type PlanOrphan = { readonly cause: "spec-absent" | "slug-absent"; readonly specPath: string | null };
```

值**携带行为**，消费点不写 `switch (read.kind)`——同一个三态分支不许在七个调用点各写一遍，那正是本相位要杀的病：

- `path(): string | null` — 派生的 repo 相对路径；`undeclared` 返回 `null`，`unreadable` 与 `ready` 返回那条路径（读不出不等于没有路径）。它是 plan **行**的唯一事实源：对非 `undeclared` 一律取它（读不出也要看得见它去读哪，AC #4）；frontier 输入**不取它**，取下面的 `stationPath()`（见接线段）。类型必须写死成 `string | null`：今日「无 plan 面」的判据就是 `=== null`（`session/pipeline.ts` 的 `#planState` 与 `branchLineOpen`），`PipelineFrontierInput.planPath` 原样吃它；若 `undeclared` 回 `""`，plan 面会从「无」变成 `{ type: "plan", id: "", plan: "" }`，在 argv 字节不变的幌子下悄悄改掉派生路由。
- `stationPath(): string | null` — **frontier 可引用的路径**，`PipelineFrontierInput.planPath` 的唯一取处。判据是「这份文档读得出来（front matter 可解析）」，不是「解析得成图」：`undeclared` → `null`（没有文档）；`unreadable` / `io` → `null`（连 slug 键都没有，面装配不出来，plan 面不可能是下一面——§2.3 的 `io` 边界）；`unreadable` / `syntax` → 那条路径（front matter 已经读出来了，plan 面装配得出，它的 doc-contract 拒绝正是应当被指向的下一面）；`ready` → 那条路径。这正是今日 doc 面的值分布：今日 `planPath` 取自 `index.planOf(slug)?.path`，而索引把「front matter 读得出来」当入册前提（`infra/slug-index.ts` 的 `#scanRoot`），所以 `syntax` 输入今日的 `planPath` 本就非 `null`、图却是 `null`（`face/board-view.ts:892-901` 的 `planGraph` 捕获回 `null`），落到 `PIPELINE_NEXT.plan`；`io` 与 `undeclared` 今日回 `null`。这条访问器因此把今日的分布落成一个**值行为**，消费者不写 `switch (read.kind)`，也不改任何 `next:` 字节；与 `graph()` 的差别只在图——`syntax` 的图仍是 `null`。
- `failure(): { readonly path: string; readonly field: string | null; readonly message: string } | null` — 失败三件的**唯一取处**（`unreadable` 时非 `null`，`undeclared` 与 `ready` 回 `null`）：`path` 是派生/argv 路径，`message` 取 grammar 的 `DocSyntaxError#message` 或 `io` 的读取失败描述，`field` 取 `DocSyntaxError#field`（`io` 没有字段，回 `null`）。`refusal()` 与 `warnLine()` 的报文都从它取件，不在别处重算。（类型是 `field: string | null`，不是 `field?: string`：可选会让「没有字段」与「没读」在类型上不可分。）
- `text(): string | null` — wave brief 与 `#targetSlug` 的原文；非抛，非 ready 返回 `null`。
- `doc(): PlanParsed | null` — brief 的数据面（§2.6 的 `render` / `taskBody` 第二个入参）；非 ready 返回 `null`（`undeclared` 与 `unreadable` 一律没有已解析文档）。
- `graph(): TaskGraph | null` — 门禁 / frontier / 板面的唯一图输入。`ready` 里 **eager** 派生于同一次解析（一次解析只产一份派生，不留第二重惰性事实源）。
- `orphan(): PlanOrphan | null` — 反查的读取事实（§2.7），**只由 argv 面（`readPath`）产生**：`ready` 且解析出的 front matter `slug` 找不到 `<slug>-design.md` 时回 `{ cause: "spec-absent" | "slug-absent"; specPath }`；派生面（`readFor`）恒回 `null`——那里的 entry 就是身份文档，`spec-absent` 结构性不可达（`specPath` 只在 `slug-absent` 时为 `null`——没有 slug 可派生），健康 `ready` 与非 ready 一律 `null`。它与 `graph` 同层：一次读取里算一次，不派生第二条读取路径；消费点因此不写 `switch (read.kind)`，也**不**把它变成 `Finding`——不登记规则，阻塞走 `refusal()`（§2.7）。
- `waves(): readonly TaskBatch[]` — 板面 wave 段的数据面；非 ready 返回空集。**它不是渲染信号**：`waves()` 为空既可能是「这版 plan 还没写 task」也可能是「读不出」，doc 面渲什么字面由 `degradedWaveRow()` 决定（§2.4）。
- `degradedWaveRow(words: PlanReadWords): string | null` — **doc 面**只负责**降级字面量**（§2.4 的四语义减一），外加 §2.7 的孤儿字面：`undeclared` → `(none)`；`ready` 且零 task block → `(empty plan)`；非 ready → `! unparseable` / `! unreadable`；**`ready` 且有波次且非孤儿 → `null`**，表示「健康行不由本访问器负责」；孤儿 → `! no-spec`（`orphan()` 非 `null` 时先折叠，§2.7）。`#waveLines` 仍是装配者：先问 `degradedWaveRow`，得 `null` 才按今日路径渲健康行（`waves()` + `graph.report(ledger.closedWaves())` 的标记 + `#rowRounds(progress, key)` 的轮次段 + `LineCarriers.ofLedger(ledger, "wave", key, rounds)` 的 carried lines，一字不改）；`#nodeBoard` 同源。健康行的字节基准因此留在装配者手里，AC #11 仍是字节断言而不是愿望；`#waveLines` **不再**以 `waves()` 是否为空作为渲 `(none)` 的信号。
- `cell(words: PlanReadWords): string | null` — **程序面**波次格的字面（§2.4 的四语义，外加 §2.7 的孤儿字面；`undeclared` → `""`；**`ready` 且有波次且非孤儿 → `null`**，表示「健康格不由本访问器负责」；孤儿 → `! no-spec`（§2.7），`#programBoard` 得 `null` 才按今日路径渲 `waves[0]!.label.split(" ")[0] + "…"`，即 `W1…`），不接面参数——同一份 `undeclared` 在两面渲不同字面，靠**调哪个访问器**区分，不靠传参分支。
- `planLine(words: PlanReadWords): string | null` — plan 行的**格内容**：非 ready 时返回，孤儿时返回（标记 `! no-spec`，§2.7），**健康的 `ready`（`orphan() === null`）一律返回裸路径**（只渲路径、不带分隔符与标记），形为 `<repo 相对路径> · <标记>`（无标记时就是 `<repo 相对路径>`）。索引成员性**不在本值里判**：`readFor` 收 `DocEntry`、不收 `SlugIndex`，「ready 且已索引」是 `PlanRead` 观测不到的限定语；是否走 `#docCell` 由装配者**先判读取值、判完才问索引**（§2.1 的优先级）决定：`非 ready` 与孤儿不经索引，索引只裁决健康的 `ready`——裸路径因此只属「健康的 `ready` 且未入索引」那一格——标记复用波次格同一个词（`! unparseable` / `! unreadable`；孤儿用 `! no-spec`，§2.7；不另造），格子不经 `#docCell`；标签与 `LABEL_WIDTH` 的 padding 仍由 `#nodeBoard` 的 `  ${row.label.padEnd(LABEL_WIDTH)}${cell.text}` 负责（不搬进本访问器），降级 plan 行的完整字形因而是 `  plan     <repo 相对路径> · ! unparseable`（`LABEL_WIDTH = 9`，`trimEnd` 后无尾随空格）。`undeclared` 返回 `null`，plan 行照旧走索引派生的那一项；**两个入口面都生效**（`--plan` 与 `--spec` 同一条规则，不加面条件——少一个 if 就少一处将来的分叉），读失败不是 slug 缺失，不参与 `#entryMark` 记账，板面消费点因此不写 `switch (read.kind)`。
- `specLine(words: PlanReadWords): string | null` — **spec 行**的格内容，孤儿专用：`orphan() !== null` → `! no-spec`（端口成员 `planOrphanWord()`），其余情形（健康 plan、非 ready、反查判不出的未判态）→ `null`，spec 行交既有的 `#docCell`。与 `planLine` 同形：只管格内容，标签与 `LABEL_WIDTH` 的 padding 仍由 `#nodeBoard` 负责；且**不经** `#entryMark` / `#docCell` 的记账——落进 mark 通道即 `blocked: true`，`#nodeBoard` 会 `return blocked ? 2 : 0` 出 exit 2，而孤儿板面要求 exit 0（§2.7）。
- `warnLine(words: PlanReadWords): string | null` — board 的 `CDD_WARN:` 行，**`unreadable` 产行**（`io` / `syntax` 两个 cause 同一词行），**孤儿也产行**（字面 `! no-spec`，两个 cause 同一字面，§2.7）；`undeclared` 与健康 `ready` 一律返回 `null`——「还没写 plan」是正常态而非读取失败，不产诊断行，`null` 面因此与 `refusal()` 的 `null` 面同宽。
- `refusal(words: PlanReadWords): { gate: "doc-contract"; reason: "doc-contract"; message: string } | null` — preflight 的拒绝通道入参：`unreadable` 与孤儿各回拒绝（报文取 `planReadWord(cause)` / `planOrphanSpec` / `planSlugMissing()`，§2.7）；健康 plan 与反查判不出的未判态返回 `null`。它不产 `Finding`、不登记规则——阻塞来自读取值的拒绝腿（§2.3），与 `ctx.doc` 是否为 doc 形状无关。

`PlanReadWords` 是 `infra/plan-source.ts` 自己声明的词表端口（`planReadWord(cause)` / `planEmptyWord` / `planOrphanWord` / `planOrphanSpec` / `planSlugMissing` / `cellEmpty` / `warnPrefix` …），由 `face/words.ts` 的 `Words` 实现——依赖方向仍是 face → infra，词表仍旧单源。`warnPrefix` 保留，但契约写死：它**委托** `words.stations.warn`（`face/words.ts:201` 的 `CDD_WARN:` 行），字面单源，不另立第二份前缀——实现体读的是那个既有成员，不是第二份 `CDD_WARN:` 字面。

接线（一次读取、一个事实源）：`PlanSource` 在**命令前奏**（`#rootOf()` 解析出仓库根之后）构造一次，作为该命令的单一实例下行；`Cli.create()` 阶段没有根，不在那里构造（与 §2.1 首段同一条约束）；`Cli#runBoard` 在**自己内部**构造 `PlanRead`（`--plan` 走 `readPath`、`--spec` 走 `readFor`；两个旗标同时给出时**`--spec` 胜**——板面的 `PlanRead` 是 `readFor(specEntry)`，`--plan` 只保留既有的两项职责（判定 ① 的存在性探针与 `no docs match` 的旗标归因），与 `face/cli.ts:521` 的 `const entry = specEntry ?? planEntry` 同序；`readPath(planRel)` 只服务 `--plan` 单独给出的调用。overall 视图逐相位读取走同一个实例，按 `index.phaseSpecsOf(slug)` 的行序形成一张有序值表），并以**参数**传给 `BoardNext.of` 与 `BoardView.pipelineFacts`。`BoardView.render` / `#programBoard` / `#waveLines` 仍是静态方法，但改为**收值不再自读**（node 板收一个 `PlanRead`，程序板收逐相位的有序值表）——`BoardView.planGraph` 删除后，板面没有第二个读取点。工作路径上 `PlanRead` 随 `WorkScene` 下行（取代 `planText: string | null` 这个第二重事实源），`PreFlight#vet` 从场景取值，不各读一次；板面不建 `WorkScene` 是既有事实——`PlanRead` 是值，不是场景成员，不为此新增场景。反查与读取同一次，但**只在 argv 面**：`readPath` 在返回 `PlanRead` 前做那一次 `DocFs.exists` 探针；`readFor(entry)` **不反查**——它手里的 entry 就是那份身份文档，`spec-absent` 结构性不可达（§2.7）。因此每张板只算一次、没有第二条派生路径：派生面上零探针，argv 面上一份 plan 一次。三个 doc 面（`phase-spec` / `overall` / `single-spec`）的 `PlanRead` **同样取自 `readFor(entry)`**：今日它们手里的图来自 `face/cli.ts` 的 `const hopPlanPath = planPath ?? index.planOf(slug)?.path ?? null`，那正是同一相的派生路径上的同一份文档，所以「同一次读取」在 doc 面上也成立，不存在只造 `undeclared` 的第二条构造路径。doc 面只吃 `graph()` / `waves()` / `doc()`，不调用 `refusal()`——拒绝腿按**面**（plan 携带面）开，不按值开。`path()` 与 `stationPath()` 的分工在此写死：plan **行**对非 `undeclared` 一律取 `read.path()`（读不出也看得见它去读哪，AC #4）；**frontier 输入**（`BoardView.pipelineFacts` 的 `planPath`）一律取 `read.stationPath()`——`ready` 与 `unreadable`/`syntax` 非 `null`，`undeclared` 与 `unreadable`/`io` 回 `null`。这恰是今日 doc 面的逐 cause 分布：派生路径上的 `syntax` 坏结构今日 `planPath` 非 `null`、图 `null`，落 `PIPELINE_NEXT.plan`（它的 doc-contract 拒绝是应当被指向的下一面）；`io` 与 `undeclared` 今日 `planPath` 为 `null`。本段的「今日行为逐字节不变」因此按 cause 分开成立，`pipelineFacts` 也不再回落到 `index.planOf(slug)?.path`。路径与图在两处各取所需是**设计**，不是分叉事故：渲法（plan 行）给证据位置，路由（frontier）给证据本身——没有图就没有可推进的**波次**，而 `syntax` 的 plan 面指向的是它自己的拒绝。

doc 行的 plan 项与 wave 行同源，规则是一句可判定的话：**plan 行的事实源恒为 `PlanRead.path`**，且**先判读取值、判完才问索引**：`非 ready`（`unreadable` 两 cause）或 `orphan() !== null` 时一律用 `PlanRead.planLine(words)` 渲（repo 相对路径 + 标记）——**孤儿在索引里是常态**（`cdd board --plan <孤儿>` 能到板面就说明它已入册，AC #5 把未入册的 `--plan` 送进 `no docs match`），若先问索引就必然落进 `#docCell`、渲成 `name  version · status` 而丢掉标记，`planLine` 的孤儿分支在两侧都成死代码，而 §2.7 的「不留半个格」也随之落空；索引**只裁决健康的 `ready`**：该路径解析到索引里的 `DocEntry` 就用既有的 `#docCell` 渲（今日字节不变），否则用裸路径（未入册的健康 plan）。三个面因此一致：相位文档有 plan 且派生路径解析到索引里的 `DocEntry` 时走 `#docCell`，健康对照逐字节不变，AC #11 不受影响；`ready` 但派生路径未被索引收进去（plan 文件缺 `doc-type: plan`，或新 plan 覆盖旧 entry）时，plan 行渲该派生路径，而不是 `(none)` 或旧文档的 `name  version · status`；非 ready 时同样渲该路径加读失败标记（`--plan` 面走 `readPath` 的同一条规则）。由 `planLine` 渲出时，plan 行不构造 `DocEntry`、不参与 `#entryMark` 记账、不进 `#docCell` 的 blocked 判定，`#nodeBoard` 照常打 overall / spec / plan / branch 四行，只把 plan 行换成 `PlanRead.planLine(words)` 渲出的这一行。反向约束同源：**不许**把无身份的值包成 `DocEntry`——`face/board-view.ts` 的 `#entryMark` 读 `entry.slug`，空 slug 回 `MARK_SLUG_MISSING`，`#docCell` 随即 `blocked: true`，`#nodeBoard` 的 `return blocked ? 2 : 0` 把这次降级误判成 exit 2。于是「plan 行与波次格一分为二」在任何 kind 上都不发生：同一个 `PlanRead` 供两边，`plan` 行渲声明路径、波次格渲 `! unreadable`；`ready` 而声明路径未入索引时，plan 行渲声明路径、波次格照常渲健康波次行。argv 面由索引成员性裁决的判定（§2.4 判定 ③）不变——它决定的是**拒绝还是成板**，不是行的来源。

`face/gate.ts` 的 `scene.planText!` 改为 `scene.plan.text()`（非抛访问器，`null` 由调用点显式处理，不再靠断言抹平）。

#### 2.2 坏结构升级为类型化错误 `DocSyntaxError`

在 `contract/doc.ts` 的 `DocType` 基类旁定义 `DocSyntaxError`（携带 `field` / `message` / `fix`），不设 plan 专属类；plan grammar 抛它，其余 doc 型可复用。`contract/task-block-grammar.ts` 的 `TaskBlockGrammar#assertNoDuplicateKeys` 改抛它，不再抛裸 `Error`；`parse(): PlanParsed` 的签名不变，`assert` 从此只承载编程不变量。

物化只发生在**有消费者**的地方——判官边界：`contract/judge.ts` 的 `#contextOf` 只**把 `DocSyntaxError` 带出来**（它返回 `JudgeContext`，物化不在这一层），`Finding` 由 `validate` / `validateLedger` 物化——`path` 取 `ContractInput.path`、`field` 取错误自带的字段、`fix` 取错误自带的修复提示。`infra/plan-source.ts` **不物化** `Finding`：`unreadable` 自带的 `path` / `message` / `field` 就是失败值本身，`refusal(words)` 直接交出 `{ gate, reason, message }`——同一事实不在同一对象图里携带两遍（D26「一事实一处」）；`DocSyntaxError` 的 `fix` 因此只服务判定面的 `Finding`。`kind` 字面量统一为 `"doc-syntax"`（`Finding.kind` 是不变量类名词汇，不是 station 的 reason token，故不新增令牌）。两个字面量必须逐字节相同，由测试钉住。

`path` 不进 grammar：文件身份是读者的事实。`contract/judge.ts` 一侧的路径来自 `ContractInput.path`（`Finding.path` 的既有归因源），因此 `validate` / `validateLedger` 对 `#contextOf` 的调用包在 try/catch 里：捕获 `DocSyntaxError` → 产一行 `Finding`，而不是穿透判定门。

#### 2.3 拒绝复用既有 doc-contract 通道

`session/preflight.ts` 的拒绝是**一道不挂门的独立判定**，不是 doc-shape 块里的一行：位置在 in-flight 之后、graph 门之前，依据**场景里的 `PlanRead`**（不是 `ctx.doc`——wave 面到达这一步时 `ctx.doc === null`，`TargetFaceTable.isDocShape` 为假，`session/faces.ts` 给它 `audit: { kind: "task-graph" }`），凡是携带 `PlanRead` 的面（`wave` / `plan` / `branch`）都执行——`branch` 面确实是 plan 携带者：`case "plan"` fallthrough 进 `case "branch"`，`face/cli.ts:1237` 的 `planText = this.#artifacts.readText(node, root, planRel)` 是同一处读取，`:1238` 的 `#targetSlug` 消费它，`face/cli.ts:674` 的 `Cli#runWork` 无条件交给 preflight，`session/preflight.ts:509` 的 `#ledgerFactsOf` 对 `plan | wave | branch` 无 try/catch 地解析（此前引的 `face/cli.ts:805` 是过时注释，已删）；三个 doc 面今日不带 plan，不在此列；`refusal(words)` 非 `null`（`unreadable` 或孤儿，§2.7）→ 与该块既有形状同一 gate id、同一 reason token（`gate: "doc-contract"` / `reason: "doc-contract"`），报文含 plan 路径与字段名。不新增 gate id，不新增 reason token。门的记账写清：`plan` 面（`doc-path` 行，`doc-contract` 本来就在它的 gate 计划里）这次拒绝同时入 `checked`；wave 面上它**不在** gate 计划里，因此**不入** `checked`；`branch` 面同 wave 面**不入** `checked`——`session/faces.ts` 给它 `audit: { kind: "branch-tree" }`，`isDocShape` 为 false，`doc-contract` 不在它的 gate 计划里，而 `cdd implement --type branch` 是 AC #3 的合法可达面。拒绝靠 `reason:` 与报文表达，不许让 wave 面 / `branch` 面声称跑过一个它们没计划的门。拒绝腿在 graph 门之前，非 ready（含孤儿）取值先返回，故该门只在 `read.kind === "ready"` 时抵达；门记账不变——`graph` 行只在实际运行的那次出现（`session/preflight.ts:224-226` 的 `push` 在 `(wave || plan) && planText !== null` 之内），不补 `skipped` 行（该词只属 `checked` 的规则行，`:471` / `:473` / `:475` / `:489`）。因此 plan 面上的第一处拒绝恒为 `doc-contract`，AC #3 观察到的 `reason` 不会变成 `graph`。doc 面既有的 doc-contract 行原样不动。

**不新增 station kind**（`session/dispatch-authority.ts` 的三 kind 不动，P27 的十三 token 不动）：`unreadable` 与 `unparseable` 的可观察面是「结构拒绝先于 station 计算发生」——前者使下游不可达，而不是新增一个 kind。

board 面另落同一条意图（charter ④「读不出不得授权下游 `next:`」）：拿到 `read.kind === "unreadable" || read.orphan() !== null` 的 `PlanRead` 时**不派生任何波次路由**（这对条件与 `BoardNext.of` 共用，孤儿不另开第三条短路）——`BoardNext.of` 短路，`next:` 渲既有的 hop-less 降级形态 `  next:    (none)`（`face/board-view.ts` 的 `next === null` 分支，`face/__tests__/board-view.test.ts` 已钉），且不出 `reason:` 行；原因由波次格（`! unparseable` / `! unreadable` / `! no-spec`）外加 stderr 的 `CDD_WARN:` 承担。这条路径不构造 station，故不新增 `TargetType`、不新增 station kind、不新增 reason token。`undeclared` 不在短路之列：没有 plan 的相位仍走 frontier 的今日语义（`graph === null` → 未进入 → plan 面路由），「读不出」与「没有」不是一件事。

**`io` 的一条结构边界**：plan 携带面（`wave` / `plan` / `branch`）要从 plan 的 front matter 取 `slug:` 当 workspace 键（`face/cli.ts` 的 `#sceneOf` → `#targetSlug` → `new Workspace(rootPath, slug)`；`infra/workspace.ts` 的构造函数形参是 `string`，直接 `path.join`）。plan 读不出（`cause: "io"`）时**没有键**，面在装配前就被既有的身份拒绝拦下：exit 1、无 gate、无 `reason:` 行、报文逐字节保持今日形态。所以这条拒绝腿只在**装配得出**的面里说话，覆盖 `syntax` 与孤儿；`io` 的可观察面就是那条身份拒绝（它点明的正是读失败这个事实）。这不是例外而是前置：没有身份就没有面，没有面就没有门的候选——把 `io` 塞进拒绝腿需要先伪造一个键，那比今日的报文更糟。

#### 2.4 降级显式：视图面与 preview 面

四语义一格不多一格不少：

| 语义 | doc 面 wave 行 | 程序面波次格 |
| --- | --- | --- |
| 真 undeclared（该相位没有 plan） | `(none)` | `""`（`""` 只属于这一种语义） |
| `ready` 但零 task block（skeleton 刚生成） | `(empty plan)` | `(empty plan)` |
| `unreadable` / `unparseable` | `! unreadable` / `! unparseable` | 同 |

§2.7 的孤儿**不是第五种读取语义**：`read.kind` 仍是三态，孤儿是 `ready` 上的身份破损，只把 plan 派生的字面折叠成 `! no-spec`（§2.7）；四语义表与 `(empty plan)` 的分界一字不动。

doc 面的 wave 行分两段：`PlanRead.degradedWaveRow(words)` 只产降级字面量（孤儿另有 `! no-spec`，§2.7），`ready` 且有波次且非孤儿时返回 `null`，由装配者 `#waveLines` 按今日路径（`waves()` + `graph.report(ledger.closedWaves())` + `#rowRounds` + `LineCarriers`）渲健康行；程序面的波次格由 `PlanRead.cell(words)` 生产，它只产降级字面量与空串（`undeclared` → `""`；孤儿 → `! no-spec`，§2.7），`ready` 且有波次且非孤儿时同样返回 `null`，由 `#programBoard` 按今日路径渲 `waves[0]!.label.split(" ")[0] + "…"`（即 `W1…`）——健康 doc 行与健康程序格都「不由本访问器负责」，两面成对。同一份 `undeclared` 在两面渲不同字面，靠**调哪个访问器**区分，`cell` 不接面参数；`#waveLines` / `#nodeBoard` 渲 doc 面波次行时**从不**以 `waves()` 是否为空作为渲 `(none)` 的信号。

格面字面按 `LABEL_WIDTH`（`face/board-view.ts`）对齐：真 undeclared 那一行是 `  wave     (none)`（前导两空格 + `wave` 补齐到 9 列），验收逐字节对照这条字面，不写活动格。

`(empty plan)` 走**独立端口成员** `planEmptyWord()`（与 `cellEmpty` 并列的同级 station，仍是 `PlanReadWords` 的一员），不进 `planReadWord(cause)`——后者只承担 `io` / `syntax` 两种读失败。理由：健康但空的状态不是读失败，塞进失败词法会让测试从同一处推出字面量而永不红。该字面不得回落 `(none)`，也不得回落空串——它是「有 plan、还没写 task」的正常态，与「没有 plan」不是一件事。

board 收到**读取失败或孤儿**的 `PlanRead` 时额外打一行诊断：`CDD_WARN:` + 对应词行，走 **stderr**（`face/lifecycle.ts` 与 `face/cli.ts` 的现有一律 stderr，`words.stations.warn` 是诊断锚）；stdout 的 wave 块零字节变化（只差那一格），退出码仍 0。写者是 **`Cli#runBoard`**：`BoardView.render` 是纯函数（静态返回 `{ lines, exitCode }`，不持有 io 通道），不承担写盘——`Cli#runBoard` 在打印渲染行**之前**调用 `read.warnLine(words)` 写 stderr；overall 板由它按 §2.1 那张有序逐相位值表，对**每个读取失败的相位**各写一行（行内带相位 id）——`undeclared` 的相位不写（`warnLine` 对它返回 `null`），故诊断行数恒等于坏 plan 数与孤儿数之和。把诊断放 stdout 会让一个站牌词跑上没有站牌走的通道。

程序面（`BoardView.#programBoard`）一条降级、两处落点：每个坏 plan 的相位各出一行 `CDD_WARN:`（行内带该相位的 `slug:`，多相位板上才定位得到），打 **stderr**；波次格只渲 `! unparseable` / `! unreadable` / `! no-spec`（真 undeclared 仍是 `""`；孤儿用 `! no-spec`，§2.7），健康相位行的波次格仍按今日路径渲 `W1…`（`cell(words)` 对它返回 `null`），不在格内另造标记，相位行其余列零字节变化。

`cdd board --plan <存在但读不出>` 是 argv 面，**不出板面**：读取失败即拒绝，保持 exit 2，但报文必须点明是读失败而不是「没有这份文档」——`cdd board: cannot read --plan <path>`（**不带原因尾段**：`DocFs.read` 只回 `string | null`、不携带 errno，接缝上已经没有原因可取，硬造一个就是消费者可见的臆造字面——`cause: "io"` / `"syntax"` 的区分走 `CDD_WARN:` 那行与 `planReadWord` 词行，不进这条报文）；`#boardNotFound` 的 `no docs match` 只留给「不存在」与「读得到但不在索引」两种**非读取失败**——与判定 ③ 同义，也只有存在性探针失败与索引缺员两种情形用它）。没有板面就没有 `next:`，charter ④「读不出不得授权下游 `next:`」自动满足。exit 0 的 `! unreadable` 渲染只经相位文档的 slug 派生面到达（§2.1：`docs/kairos/plans/<slug>.md` 存在但读不出），两条面各归各的通道，不复用同一个身份。读得成功但索引里没有这份文档（不是两个 doc root 下的扫描面）仍走既有 `#boardNotFound`（exit 2）。

归类顺序一句写死——四个判决不在同一层，重叠时必须有序，且**判定 0 是存在性探针**（与今日代码同序，零文档读取）：① **`SlugIndex.insideDocRoots` + `existsSync`** → 不存在（不在 doc roots 内或盘上无此文件）→ 既有 `#boardNotFound`（`no docs match`，exit 2；`face/__tests__/cli.test.ts` 的 ghost-path pin 不变）；② 存在 → **读字节**（**只在 `--plan` 单独给出的调用上**——两个旗标同时给出时 X 的字节不读，即使存在但读不出也不得拒绝，供值的 `PlanRead` 恒取 `readFor(specEntry)`），读失败即 `cdd board: cannot read --plan <path>`（exit 2，不带原因尾段——理由见上句）；③ 字节读到后**由索引成员性裁决**，不在索引即既有 `#boardNotFound`（`no docs match`，exit 2）；④ **只有已入索引的 plan 才走文法判决**，坏文法渲 `! unparseable` 板面、exit 0。重叠情形取此序：**存在但读不出 ∧ 不在索引 → `cannot read`**（存在性已过、io 失败先于成员性）；读得到但不在索引的非 plan 文件一律 `no docs match`，其文法如何不参与裁决。值来源不参与这个顺序：两个旗标同时给出时判决仍逐条走（① 探两者的存在性、③ 判任一成员性），而供值的 `PlanRead` 恒取 `readFor(specEntry)`（§2.1），`--plan` 单独给出时才取 `readPath(planRel)`——`cdd board --plan X --spec Y` 里 X 的内容不进任何一格。

`--dry-run` / preview 与真派同批：preview 在坏 plan 上同样返回 BLOCKED，不降级。preview 的卖点是「先看这一轮会做什么」，让它照常输出等于把同一个谎报搬到第二个面。

#### 2.5 缺证据不得授权下游

`session/pipeline.ts` 的 `#waveState` 与 `#wavesExhausted`、`session/dispatch-authority.ts` 的 `#waveStation` 改吃 `PlanRead`：`undeclared` 保留今日语义（未进入 / 没关门 / 无站牌）。两个 `unreadable` cause 与 §2.7 的孤儿在可达路径上不进这三处——真派路径由 §2.3 的结构拒绝先一步拦下，板面路径由 `BoardNext.of` 的同一对短路条件先一步拦住；因此「不授权」成立、`PipelineFaceState` 不必多出第四个值、令牌表不动。frontier 的图与路径输入**不同界**，且两边都以今日为准：图只见 `ready`（`graph()` eager 于同一次解析），路径取 `stationPath()`——`ready` 与 `unreadable`/`syntax` 非 `null`，`undeclared` 与 `unreadable`/`io` 回 `null`。于是「有路径没图」这一格只对应 `syntax`，而它**不构成一次推进**：plan 面拿到同一条路径，它自己的 doc-contract 拒绝（§2.3）就是前沿指向的那一面，`#waveState` 因 `planGraph === null` 照旧读作未进入——这正是今日的形状（今日该输入 `planPath` 非 `null`、图 `null`、落 `PIPELINE_NEXT.plan`），不是本相位新开的路。`io` 与 `undeclared` 的 `planPath` 回 `null`，路由面拿到的仍是今日的回落语义。

`session/run.ts` 的 `Lifecycle#recordPlanSnapshot` 改吃 `PlanRead`：非 ready → 不记快照；「缺快照读作 stall」原样保留。账本是记录面，为一个坏 plan 把已完成的 wave 卡死在闭合点，会把读取缺陷升级成流程死锁，而 stall 已经给出了保守的正确答案。

#### 2.7 反查：plan 必须命名一份相位 spec

前向（相位 → plan）缺失是**正常状态**：一个相位可以注册了、还没写计划，读作 `undeclared`、渲 `(none)`。反向则不同——plan 是**为一枚相位写的**，那份 spec 就是它存在的理由。plan 的 slug 找不到 `docs/kairos/specs/<slug>-design.md` 时，身份已经破了，不能像前向那样降级成 `(none)` 了事。

- **反查只问存在性，不问内容谓词**：派生式与前向是同一个表达式换一个根——`${ENGINE_DOC_ROOTS.specs}/${slug}-design.md`，只经 `DocFs.exists` 探「这份文档在吗」。slug 的来处分两条：**反查只在 argv 面成立**：`readPath` 没有 entry，故由解析后的 front matter `slug` 派生 `<slug>-design.md` 并用 `DocFs.exists` 探一次；`readFor(entry)` **不反查**——它手里的 entry 就是那份身份文档，`spec-absent` 结构性不可达，只剩 `slug-absent`（`entry.slug === null` 时，而那已归 `undeclared`）。理由写在字面上：`#scanRoot` 索引的是 doc root 下任何可读的 `*.md`，`-design` 后缀只是本仓的布局惯例（P15/D59 已退役文件名身份），所以一份合法声明 `slug: X`、文件名却不带 `-design` 的 spec 是正常入册的 entry——若派生面也探，它读自己的 plan 时会算出 `spec-absent`，`cdd board --spec` 把自己的 spec 行渲成 `! no-spec`、`review --type plan` 对一份完全健康的 pair 报 `CDD_BLOCKED`，这就是造出假孤儿，反查就是读取的一部分。不得用 `SlugIndex#phaseSpecsOf` / `#planOf` 的反向拼装实现：索引把「读得出」当入册前提（`infra/slug-index.ts` 的 `#scanRoot` 丢掉不可读候选），那样写会把「存在但读不出」误判成「缺失」，凭空造出一批假孤儿。探针**每张板只算一次**，从同一个 `PlanSource` 缝取（§2.1 的接线仍是唯一入口），不派生第二条读取路径。
- **事实落在读取值上，不登记新规则**：反查的答案不是 doc 形状的违规，而是「这份 plan 有没有命名一个相位」的读取事实，因此 `contract/rules.ts` / `contract/invariants.ts` 一行不改、不产 `Finding`、`kind` 词法零新增（`"doc-syntax"` 仍是唯一新增的词，§2.2）。`PlanRead` 仍只有三态；`ready` 额外携带 `orphan(): PlanOrphan | null`（§2.1）——`spec-absent` 是盘上没有 `<slug>-design.md`（`specPath` 即该派生路径），`slug-absent` 是 argv 面那份 plan 自己没写 `slug`（谁也没命名，无处派生，`specPath` 为 `null`）。阻塞仍走 §2.3 那条**不挂门的腿**：`refusal(words)` 在孤儿时回拒绝，`gate: "doc-contract"` / `reason: "doc-contract"`。拒绝来自场景里的 `PlanRead`、与 `ctx.doc` 是否为 doc 形状无关，所以 `plan` / `wave` / `branch` 三个面加各自 `--dry-run` 一律 `CDD_BLOCKED`——身份破了的 plan 不该被评审，更不该被实施。报文两个词行同族：`spec-absent` 取 `planOrphanSpec`（`<slug>` 与派生路径都进报文），`slug-absent` 取 `planSlugMissing()`。
- **三个观测点各自的落点**：① **spec 行**走非阻塞通道——孤儿字面量像 `planLine` 一样绕开 `#entryMark` / `#docCell` 的记账（落进那条通道 mark 即 `blocked: true`，`#nodeBoard` 会 `return blocked ? 2 : 0` 出 exit 2），所以 **exit 0 由通道选择决定，不由字面量决定**；`#nodeBoard` 在 spec 行上先问 `PlanRead.specLine(words)`，非 `null` 就渲它、不再进 `#docCell`。② **hop-less `next:`** 把短路谓词收成**一对**条件：`read.kind === "unreadable" || read.orphan() !== null`，`BoardNext.of` 与 §2.3 用同一对，孤儿不另开第三条短路，`next:` 渲已有的 `  next:    (none)` 且不出 `reason:` 行。③ `planOrphanWord()` 的家是 `PlanReadWords`（与 `planEmptyWord()` 并列，因为它与其余降级词法同属 cell 载荷那条缝）；`MARK_*` 是身份记账通道，两者不许混。两个 cause 的**格**字面同一个（`! no-spec`）：原因是词法的差别（`planOrphanSpec` / `planSlugMissing()` 进报文与 stderr），不是格的差别。
- **板面降级到既有纪律**：孤儿 plan 上，从 plan 派生出来的每个字面都由**既有访问器**折叠而不是新增分支——`degradedWaveRow(words)`、`cell(words)`、`planLine(words)`、`warnLine(words)` 一律回 `! no-spec`（`planLine` 仍是 `<repo 相对路径> · ! no-spec`），spec 行由 `specLine(words)` 回同一个字面；孤儿判定**先于** `(empty plan)` / 健康行，`ready` 且零 task block 的孤儿同样是 `! no-spec`。`Cli#runBoard` 写一行 `CDD_WARN:` 到 stderr，**exit 0**——视图可以退化，但不能静默。
- **未判态不假装判过**：反查只判「盘上有没有 `<slug>-design.md`」。存在但索引给不出身份文档（缺 `doc-type: phase-spec`，或读不出被 `#scanRoot` 丢掉）时——不拒绝、不渲 `! no-spec`，spec 行照今日渲 `(none)`，这是**未判态**（读得出、索引给不出身份），不是「相位没有 plan」那个合法态，也不新增第二个字面量。界限因此是一句话：**凡是反查判得出的情形，plan 面上不再出现半个格**（spec 行 `! no-spec`、plan 行带同一标记、波次格同字面），判不出的情形照旧渲 `(none)`，不冒充「判过且没问题」。
- **不留豁免**：这条门的判据是「每份 plan 的 slug 都解得到 `<slug>-design.md`」，**不是**今天的快照——它从落地第一天起就绿（当下语料 34 份 plan ↔ 34 份 spec，0 孤儿、0 份文件名与 slug 不符），并在这条不变量被打破的第一份孤儿上变红；因此没有历史债要还，也不接受白名单。

### 3. 失败面

#### 3.1 裸崩面的残留路径

场景装配先于 preview 与 usage 校验执行，`#renderWaveBoard` 又在拒绝分支之后。所有读取点都必须改吃同一个 `PlanRead`，否则会出现「门禁已拒绝、渲染先崩」的顺序漏洞。验收要求 stderr 不再出现 `cdd: ` 前缀的文法报文。

usage 校验的 `planIds` 成员判定在非 ready 时**跳过**——它今日排在 `#renderPreflightBlocked`（`face/cli.ts:779`）之前，若让非 ready 的空集跑到 `face/cli.ts:706-716`，每个请求 id 都会走 `this.#usage(node, …)` 报出 `cdd <verb>: task <id> not found in the plan`（`#usage` 返回 `never`，`error:` + exit 2），AC #3 的 `CDD_BLOCKED:` 就没机会渲出。落法：该循环以 `read.kind === "ready"` 为**执行前提**（不是以「集合为空」为信号）——结构拒绝拥有裁决权，usage 只校验一个可解析 plan 内部的 id 成员性。`BriefRenderer` 不再是这条要求上的风险面：默认参数删除后它**已无解析可抛**（§2.6），`render` / `taskBody` / `extract` 收的是 `PlanRead.text()` 与 `PlanRead.doc`——因此这条要求不再依赖「被前置拒绝挡住」的时序论证；§1.1 的顺序事实仍由 pin 钉住（doc-contract 拒绝先于 brief 渲染），但它现在是冗余保障，不是唯一保障。

#### 3.2 `(none)` 与退出码的既有 pin

`cli.test.ts` 把 `(none)` 降级与 exit 0 绑在一起，`board-view.test.ts` 钉着合法的 `  wave     (none)`。降级面重构后这两处 pin 必须仍绿——它们是「不误伤健康路径」的证据。

#### 3.3 IO 与语法分叉后的报文覆盖

`DocFs.read` 返回 `null` 已是 IO 面的事实（读不出），与文法坏结构（读得出、判不过）是两件事。两条词行各自被至少一条测试覆盖，避免只测其中一条就让另一条裸走。

#### 3.4 判定面的路径归因

`contract/judge.ts` 的 `#contextOf` 只把 `DocSyntaxError` 带出来，物化在 `validate` / `validateLedger`；两侧都必须补上 `ContractInput.path`，否则 `Finding.path` 会出现空串或读者路径，判定面的锚定失效；这个分支由 `contract/__tests__/judge.test.ts` 的新增用例（跑 `validate`）覆盖。

## Constraints

- plan grammar 语义不动：`#### DependsOn` 仍只许一节，其余重复节规则与报文措辞保持
- `doc-contract` 判定语义不动，既有拒绝报文（front-matter 行）逐字节不变；不新增 gate id 与 reason token，不新增 station kind
- 判定面按值收 `contract/judge.ts` 的 `ContractInput.content`，读盘归 `infra/`（`infra/slug-index.ts` 同处；`contract/invariants.ts` 的 `DocFs` / `NodeFs` 是既有读缝，不是新职责）
- slug 是唯一的文档标识：plan 路径由 `ENGINE_DOC_ROOTS.plans` + slug 派生，不在 front matter 里声明路径；不重写 `infra/slug-index.ts` 的扫描谓词；**身份的两个方向不对称**——相位没有 plan 是合法状态（正查缺失不阻塞），plan 的 slug 找不到 `<slug>-design.md` 是身份破损（反查阻塞；只探存在性，不看索引的内容谓词）
- progress 账本口径与 `recordPlanTasks` 的形状不动；`session/run.ts` 的 stall 语义保留
- 不新增 CLI 动词或旗标，不重排 board 既有列与 `next:` / `reason:` 字节
- 无 module-level 裸函数；新类按 OOP-first 落（状态与行为共变），单一职责
