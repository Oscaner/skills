## Design

本相位收口 plan 文档读取的一处权威缺口：同一份 plan 有**九个读取点（共十处到达 plan 解析的站点，含登记行一处）、四种失败策略**，坏结构的两个面分别是「静默放行」与「裸崩」。根因不是某个被吞掉的 `catch`，而是**读取权落在视图平面**——`face/cli.ts` 把 `BoardView.planGraph` 这条渲染路径的产物当门禁证据注入 session，于是一个 draw 契约变成了 gate 契约。计数口径写死在此：度量的单位是**到达 plan 解析的站点**，不是「拼出 `new PlanDocType("plan")` 的站点」——`grep -rn 'new PlanDocType("plan")' packages/cdd-engine/src-next`（排除 `__tests__/`）共 9 处 = 8 个显式读取点 + `contract/doc.ts` 登记行 1 处；第九个读取点是 `session/ledger.ts` 的 `Ledger#briefRevision`，它经由 `readonly #brief = new BriefRenderer();`（`session/ledger.ts:668`）的默认参数到达解析，这条 grep 看不见它。故总计 10 = 9 读取点 + 1 登记行，与 overall D90 / Phase-inventory 的 `9+1`、四策略同源。计数单位是**plan 文档文法**（`PlanDocType` / `docTypeParsers`）的到达站点；结构面的 task 块投影（`contract/task-blocks.ts` 的 `PlanTaskBlocksReader`：依赖边变了没有、这一轮的 `Files` 是否全空）不在同一单位内，其中两处经 `PlanStructure.of` 与 `CliLifecycle#emptyFileTasks` 到达 plan 解析，作为**承认的第二读**在 §1.1 的专表里登记——`PlanRead` 仍是「一份文档读取」的唯一值。

裁定把 plan 的 read + parse + classify 收进 `infra/plan-source.ts` 的一处深类，失败成为一个携带行为的判别值，坏结构走既有的 `doc-contract` 拒绝通道，降级成为带警告的显式值，「读不出」不再授权下游结论。三件不破坏的事：plan grammar 语义不动、`doc-contract` 判定语义与既有拒绝报文不动、健康 plan 的板面与 `next:` / `reason:` 字节不动。

### 1. 病根

#### 1.1 一份文档、九个读取点、一个登记行、四种策略

九个读取点（模块 + 符号，非行号）分四类策略：

| 读取点 | 策略 | 坏 plan 的后果 |
| --- | --- | --- |
| `face/board-view.ts` 的 `BoardView.planGraph` | 捕获 → `null` | `  wave     (none)`、exit 0、`next:` 照常 |
| `face/cli.ts` 的 `Cli#sceneOf`（场景装配） | 裸抛 | 无 BLOCKED 面、无 path、无 `next:` |
| `face/cli.ts` 的 `Cli#renderWaveBoard` | 裸抛 | 同上 |
| `face/cli.ts` 的 usage 校验（`planIds` 块，`Cli#runWork` 内） | 裸抛 | 同上 |
| `session/preflight.ts` 的 `PreFlight#vet` graph 门禁 | 裸抛 | 同上（且被场景装配抢先） |
| `session/preflight.ts` 的 `PreFlight#ledgerFactsOf` | 裸抛 | 同上 |
| `render/brief.ts` 的 `BriefRenderer`（构造注入解析器，`extract` 内解析） | 裸抛 | 同上（本相位删除该解析：`BriefRenderer` 的 `render` / `taskBody` / `extract` 三面改收 `text` + `doc`，`PlanRead.text()` / `PlanRead.doc()`，见 §2.1 / §2.6） |
| `session/run.ts` 的 `Lifecycle#recordPlanSnapshot` | 捕获 → 不记快照 | 快照缺失在 wave 门里保守读作 `stall` |
| `session/ledger.ts` 的 `Ledger#briefRevision`（`:941`；经 `readonly #brief = new BriefRenderer();`（`:668`）的默认参数到达解析） | 捕获 → `null`（brief 事实不记） | 该次 review/fix 完成时不记 brief 修订，`briefDrifted` 读作未漂移、已评审波次不重开 |

`Lifecycle#recordPlanSnapshot` 是**策略正确的那一个**（缺失 → 拒绝，而非放行），本相位保留它的语义，只把「吞掉的缺失」换成「已知的缺失」——它改吃 `PlanRead`，非 ready 不记快照。`Ledger#briefRevision` 是第四类：它同样 `catch → null`，但吞掉的不是图而是一条修订哈希——算不出就不记，与「present facts only」一致；它与第一类不是一件事，后者把图吞成 `null` 后板面读作「没活干」，而这里不记的是「这次评审的 brief 基准是哪一版」。

**登记行**（唯一合法的构造点，不是读取点）：`contract/doc.ts` 的 `docTypeParsers` 里 `plan: new PlanDocType("plan")`。

**第二读者（结构面的任务块投影，本相位承认、已列表登记）**：另有两处站点也到达 plan 解析，但它们走 `contract/task-blocks.ts` 的 `PlanTaskBlocksReader`（task 块文法），不经任何 `PlanDocType`，问的也不是「这份文档是什么」而是「它的 task 块说了什么」。它们既不在上表的九点计数里，也不在登记行守卫的单位（`PlanDocType` 家族）里——把它们塞进同一个守卫，要么换掉守卫的单位（计划 T6 的验收随之失真），要么给它们编一个不存在的 doc 型。它们是**承认的第二读**，不是待收权的读取点：

| 第二读站点 | 用途 | 为何是第二读 |
| --- | --- | --- |
| `session/run.ts` 的 `PlanStructure.of`（轮开 `face/lifecycle.ts` 的 `#dispatch`、轮闭同文件的 `#structureViolations`） | 结构面基线：取 task id 集与每个任务的 `DependsOn` 集，判这一轮有没有改动结构边 | 问的是「依赖边变了没有」，答案是两张集合；结构面归编排器，`PlanRead` 不携带、也不该携带它 |
| `face/lifecycle.ts` 的 `CliLifecycle#emptyFileTasks`（由 `#criterionViolations` 的完成判据调用） | 完成判据的 verification-wave 格：取每个 task 的 `Files` 是否全空 | 问的是「这一轮的 `Files` 是不是全空」，答案是一张 task id 集合——同一份字节，另一个问题 |

`PlanRead` 因此是**一份文档读取**的唯一值；上面两处是同一份文档在结构面上的第二个投影读者，它们的存在由本表登记，而不是靠守卫看不见它们。

**渲染消费点**（只读 `null` / 空集，不是解析点，移出上表）：`BoardView.#waveLines`、doc 面 `BoardView.render`、`BoardView.#programBoard` 内的 `waveCell` 局部。三处今日把「零 task block」「没有 plan」「读不出」压成同一个空值/`(none)`，§2.4 逐个拆开。

判定面另有一处通用分发：`contract/judge.ts` 的 `#contextOf` 直接调 `docTypeParsers[input.docKey].parse(...)`，于是同一份文档的 body 坏结构会把**判定门自己打死**，而不是产出一行 `Finding`。

顺序事实（今日成立、须有 pin）：`PreFlight` 的 doc-contract 结构拒绝发生在 `face/gate.ts` 的 `renderBrief` **之前**。这个顺序今日是 `BriefRenderer` 裸抛的唯一保障；本相位把 brief 的第二处解析删掉（§2.1 / §2.6），保障于是不再依赖时序——`renderBrief` 拿到的已是 `PlanRead.doc`，它没有解析可抛。

#### 1.2 为什么补 `catch` 不管用

两个面是同一个缺陷的两端：board 吞掉后把「读不出」渲染成「没活干」，dispatch 则在更早的场景装配处裸崩成 `cdd: task 27 carries the reserved section "#### DependsOn" more than once`。补 `catch` 只会把裸崩面也改成静默，让「读不出」在所有面上都读作「没活干」。

形式化的病句：**证据缺失被读作缺失的证据**。`session/pipeline.ts` 的 `#waveState` 把 `graph === null` 读作「wave 面从未进入」，`#wavesExhausted` 读作「没关门」，`session/dispatch-authority.ts` 的 `#waveStation` 读作「无站牌」——三处同一个推理错误，靠 `null` 这一个值串起来。

正确形状在同一份文档里已经存在：front-matter 的坏法走 `contract/frontmatter.ts` 的 `get parseError`，由 `session/preflight.ts` 的 doc-contract 块变成一次带 `routeWord("frontmatterParse")` 的拒绝。差别只在 `parse(): PlanParsed` 是「全成功或裸抛」，而 `parseError` 是值。

#### 1.3 为什么读取必须离开视图面

`contract/judge.ts` 的 `ContractInput` 只带 `content: string`——判定面按值收原文、从不读盘，读盘归 `infra/`（`infra/slug-index.ts` 已按 front-matter 读文档）。这是一个**按面分工**的判据，不是「`contract/` 不碰 IO」：`contract/invariants.ts` 里就住着 `DocFs` / `NodeFs` 读缝。而视图面持有读取权，就把「怎么渲染」升级成了「怎么判」：`face/cli.ts` 场景装配把 `BoardView.planGraph` 的结果当门禁证据往下传，视图因此成为门禁的上游。

#### 1.4 否决面（issue 的四条建议各自停在哪）

- 建议①「返回类型化的失败值」——停在返回类型：谁读、谁判、判据在哪，一个问题没回答。
- 建议②「board 打一行 `CDD_WARN`」——只覆盖视图面，dispatch 的裸崩面原封不动。
- 建议③「新增 `doc-structure` violation 类」——`doc-contract` 已是结构拒绝类，新增等于扩令牌表（P27 的十三 token 分腿），收益只是诊断更细，而 path / field / message 已经在报文里。
- 建议④「`next:` 必须说明被什么挡住」——`next:` 是路由分类器的单一出口，为一个拒绝类分叉会让「路由 == 门禁 == 渲染」多一个例外；「被挡住」的可见性由 `CDD_BLOCKED:` + `reason:` + 报文承担。

### 2. 裁定

#### 2.1 读取收进 `infra/plan-source.ts`：一个深类、两个入口、一个携带行为的值

新增深类 `PlanSource`（家：`infra/plan-source.ts`），构造注入 `DocFs`（默认 `NodeFs`）与 `RepoRoot`，**路径过 `RepoRoot` 的转换对**：`this.#root.resolve(this.#root.relativize(rel))`。`RepoPath` 是带品牌的值（`infra/root.ts` 的 `type RepoPath = string & { readonly __repoPath: unique symbol }`），`relativize` 是它的**唯一构造入口**（`RepoRoot#relativize`：把绝对路径或调用方相对串归一成 repo 相对——它的注释原文即「a bare `docs/x.md` is read relative to repoRoot, NEVER to `process.cwd()`」），`resolve` 是**唯一擦除点**（`RepoRoot#resolve` → 绝对串）。派生面拼出来的模板串与 `DocEntry.rel` 都是普通 `string`，不经这一对就过不了 `tsc`；也不存在「先裸读再兜底」的支路。理由不是洁癖：`NodeFs` 吃字面路径（`existsSync` / `readFileSync`，不经 rebase），按 `process.cwd()` 解析，而仓库根是**逐命令**的事实（`#rootOf()` = `git.topLevel(process.cwd())`，cwd 可以是仓库子目录），今日 dispatch 面的读正因此是根锚定的——站点 `packages/cdd-engine/src-next/face/artifacts.ts` 的 `Artifacts#readText`（`readText(node: Command, root: RepoRoot, file: RepoPath)` → `root.resolve(file)` → `readFileSync`）；不经 `RepoRoot` 的 repo 相对串在子目录下会把健康 plan 读成 `unreadable` / `io`，静默违反「健康 dispatch 报文逐字节不变」。因根要逐命令解析，实例在**命令前奏**（`#rootOf()` 之后）构造一次，作为该命令的单一实例经参数下行到 `Cli#runBoard` / `Cli#sceneOf` / `PreFlight`；`Cli.create()` 阶段尚无根，不在那里构造——「一份**文档**读取」的落地口径是**每个命令一个实例、每份文档一次读**，不是进程级单例；结构面的任务块投影（`PlanStructure.of`、`CliLifecycle#emptyFileTasks`）是本相位承认的第二读者，已在 §1.1 列表登记——它们不经 `PlanDocType`，不参与这条口径。两个入口，同一个 `PlanRead`：

- `readFor(entry: DocEntry | null): PlanRead` — 相位文档的**派生面**：`entry.slug` 是唯一身份，路径是 slug 的纯函数——`` `${ENGINE_RUNTIME.docRoots.plans}/${slug}.md` ``（`infra/doc-roots.ts` 的 `ENGINE_DOC_ROOTS.plans` 就是「slug → doc-tree 反向派生」的根，该文件的注释原文即如此；`ENGINE_DOC_ROOTS` 是全库唯一的根值，`face/declare.ts` 的 help 示例也从它派生）。`entry === null` 或 `entry.slug === null` → `undeclared`（这条早退是唯一守卫：doc 面的 `specEntry` 本就可空，调用方把 `index.entryAt(specRel)` 的结果直接交进来，不在调用点判空）；否则**先探存在性**（`DocFs.exists`），不存在 → `undeclared`（该相位还没有 plan，今日的 `(none)` 逐字节不变）；存在才读字节——`read` 回 `null` → `unreadable` / `io`。这条派生**不咨询索引的内容谓词**（索引把「读得出」当入册前提，`infra/slug-index.ts` 的 `#scanRoot` 丢掉不可读候选），所以「存在但读不出」零声明、零新字段就可达 `cause: "io"`。

**没有声明键**：slug 是唯一的文档声明，路径不写进 front matter。写进去的坏处是造出第二个可与 slug 冲突的事实源（声明指 A、slug 派生指 B 时谁对？），而主编排器的错（spec 与 plan 的 slug 不一致）不该由文档内容去兜——那种不一致读出来就是 `undeclared`，症状 `(none)`，与「还没写 plan」同一副面孔；那是 slug 面自己的事，不是读权的事。这条派生的判据是「每份 plan 的文件名等于它的 front-matter `slug`、每份 spec 的文件名等于 `<slug>-design.md`、每份 overall 等于 `<slug>-overall.md`」，**不是**今天的快照——它从落地第一天起就成立（当下语料 34 份 plan ↔ 34 份 spec，0 份文件名与 slug 不符），被打破时的落点也已钉死：正查侧读作 `undeclared`（`(none)` + exit 0，不回退到任何索引猜测，「派生面读不出」那条 AC 的第三条），反查侧落成孤儿拒绝（§2.7）——派生方向因此是既有事实，不是本相位的新约定。代价写在这里：非派生路径（同一份 plan 被两个相位共用、或文件名另起）因此不可表达，补救是改名而不是加键。`#scanRoot` 的扫描谓词仍不动——从「刻意不动」变成「根本不需要动」。同理，`FrontMatterHead#plan`、`DocEntry.declaredPlan`、越域校验与 `planPathInvalid` 词行**全部不存在**：没有作者给的路径，就没有域可校；plan 行的字节基准仍是 repo 相对形式，派生值天然如此。

- `readPath(rel: string): PlanRead` — argv 直给路径的读取面：`cdd board --plan` 与三条 argv 驱动读者（usage 校验的 `planIds` 块、`Cli#renderWaveBoard`、`Cli#sceneOf`）共用它，不再各写一次「索引里没有就当没读」。

判别值三态：

```ts
type PlanRead =
  | { readonly kind: "undeclared" }
  | { readonly kind: "unreadable"; readonly path: string; readonly cause: "io" | "syntax"; readonly field: string | null }
  | { readonly kind: "ready"; readonly path: string; readonly text: string; readonly doc: PlanParsed; readonly graph: TaskGraph; readonly orphan: PlanOrphan | null };

type PlanOrphan = { readonly cause: "spec-absent" | "slug-absent"; readonly specPath: string | null };
```

实现上三态是**带品牌的联合**：`PlanReadState` 带一个模块私有 `symbol` 属性（不导出，别的模块拼不出这个键），`PlanRead` 的构造参数要求该 brand。于是「只有一个生产者、没有第二构造路径」由 `tsc` 判而不是靠注释——今天五处 `new PlanRead` 全在 `infra/plan-source.ts` 内（`PlanSource` 的两条 `undeclared` 早退、`#ioFailure` 的 `io`、`#classify` 的 `ready` / `syntax`），`BoardView.render` 的 `readFor(null)` 回退也是经 `PlanSource` 到达的同一个铸造面。

值**携带行为**，消费点不写 `switch (read.kind)`——同一个三态分支不许在七个调用点各写一遍，那正是本相位要杀的病：

- `path(): string | null` — 派生的 repo 相对路径；`undeclared` 返回 `null`，`unreadable` 与 `ready` 返回那条路径（读不出不等于没有路径）。它是 plan **行**的唯一事实源：对非 `undeclared` 一律取它（读不出也要看得见它去读哪，「派生面读不出」那条 AC 的 plan 行断言）；frontier 输入**不取它**，取下面的 `stationPath()`（见接线段）。类型必须写死成 `string | null`：今日「无 plan 面」的判据就是 `=== null`（`session/pipeline.ts` 的 `#planState` 与 `branchLineOpen`），`PipelineFrontierInput.planPath` 原样吃它；若 `undeclared` 回 `""`，plan 面会从「无」变成 `{ type: "plan", id: "", plan: "" }`，在 argv 字节不变的幌子下悄悄改掉派生路由。
- `stationPath(): string | null` — **frontier 可引用的路径**，`PipelineFrontierInput.planPath` 的唯一取处。判据是「这份文档读得出来（front matter 可解析）」，不是「解析得成图」：`undeclared` → `null`（没有文档）；`unreadable` / `io` → `null`（连 slug 键都没有，面装配不出来，plan 面不可能是下一面——§2.3 的 `io` 边界）；`unreadable` / `syntax` → 那条路径（front matter 已经读出来了，plan 面装配得出，它的 doc-contract 拒绝正是应当被指向的下一面）；`ready` → 那条路径。这正是今日 doc 面的值分布：今日 `planPath` 取自 `index.planOf(slug)?.path`，而索引把「front matter 读得出来」当入册前提（`infra/slug-index.ts` 的 `#scanRoot`），所以 `syntax` 输入今日的 `planPath` 本就非 `null`、图却是 `null`（`face/board-view.ts:892-901` 的 `planGraph` 捕获回 `null`），落到 `PIPELINE_NEXT.plan`；`io` 与 `undeclared` 今日回 `null`。这条访问器因此把今日的分布落成一个**值行为**，消费者不写 `switch (read.kind)`，也不改任何 `next:` 字节；与 `graph()` 的差别只在图——`syntax` 的图仍是 `null`。
- `failure(): { readonly path: string; readonly cause: "io" | "syntax"; readonly field: string | null } | null` — 失败三件的**唯一取处**（`unreadable` 时非 `null`，`undeclared` 与 `ready` 回 `null`）：`path` 是派生/argv 路径，`cause` 是失败种类，且是**值上的一等字段而不是代理**——`stationPath() === null` 同时答得出 `io` 与 `undeclared`，答不出这二选一，而场景装配要的正是「读不出」与「没有」的区分（`#sceneOf` 只在 `cause === "io"` 时走 usage 通道，§2.3）；`field` 取 `DocSyntaxError#field`（`io` 没有字段，回 `null`）。**诊断文案不在本值里**（D26 一事实一处）：`DocSyntaxError#message` 已是那条语法事实的唯一来源（判定面的 `Finding` 从它取，§2.2），读取值再存一份既无生产消费者、又在 `io` 上重复了 `face/cli.ts` usage 的 `cannot read file: <path>` 字节；读者看见的那句话由词端口 + `path` + `field` 合成（本节末「诊断行合成」）。**取件面写窄**：只有 `unreadable` 的 `warnLine()` / `refusal()` 从它取 `path` / `cause` / `field`；`spec-absent` 孤儿的 `failure()` 恒为 `null`——那份读是 `ready`——它的报文取 `planOrphanSpec`（§2.7）；`slug-absent` 取 `planSlugMissing()`。（类型是 `field: string | null`，不是 `field?: string`：可选会让「没有字段」与「没读」在类型上不可分。）
- `text(): string | null` — wave brief 与 `#targetSlug` 的原文；非抛，非 ready 返回 `null`。
- `doc(): PlanParsed | null` — brief 的数据面（§2.6 的 `render` / `taskBody` 第二个入参）；非 ready 返回 `null`（`undeclared` 与 `unreadable` 一律没有已解析文档）。
- `graph(): TaskGraph | null` — 门禁 / frontier / 板面的唯一图输入。`ready` 里 **eager** 派生于同一次解析（一次解析只产一份派生，不留第二重惰性事实源）。
- `document(): { readonly text: string; readonly doc: PlanParsed }` — `text()` + `doc()` 的**成对交回**，给「先以 `kind === "ready"` 守卫、再在分支里取两者」的调用点用：`ready` 上取出对值，非 ready 调用**即抛**。它是**编程不变式**而不是可观测状态（调用点的守卫已经把非 ready 挡在外面，抛出即契约破损），因此不参与任何降级矩阵、不产字面量、不进 `PlanReadWords`；存在的理由是把 §2.6「不写 `!`、不写 `?? ""`」从调用点纪律变成类型契约——调用点因此不重窄，契约破损也不静默降级成「没有 brief」。
- `orphan(): PlanOrphan | null` — 反查的读取事实（§2.7），**只由 argv 面（`readPath`）产生**：`ready` 且解析出的 front matter `slug` **合法**（`SlugIndex.isLegalSlug`，纯谓词、不需要索引）而盘上找不到 `<slug>-design.md` 时回 `{ cause: "spec-absent" | "slug-absent"; specPath }`；`slug` 非法（如 `slug: "Foo Bar"`）时回 `null`——非法 slug 派生出的路径不存在，那是**身份破损**而不是 spec-absent，行交回 `#entryMark` 的 `MARK_SLUG_INVALID`（§2.7）；派生面（`readFor`）恒回 `null`——那里的 entry 就是身份文档，`spec-absent` 结构性不可达（`specPath` 只在 `slug-absent` 时为 `null`——没有 slug 可派生），健康 `ready` 与非 ready 一律 `null`。`spec-absent` 是 §2.7 折叠（`! no-spec`）与 `refusal()` 的触发因；`slug-absent` 只是身份破损的读取事实，消费方不折叠（行交回 `#entryMark`，§2.7）。与 `spec-absent` 无关的第三种身份破损——**重复 slug**——不归本访问器管：`readPath` 手里没有 `SlugIndex`，重复是索引的事实，由板面装配先看 `#entryMark` 定（§2.7 的第二层）。它与 `graph` 同层：一次读取里算一次，不派生第二条读取路径；消费点因此不写 `switch (read.kind)`，也**不**把它变成 `Finding`——不登记规则，阻塞走 `refusal()`（只对 `spec-absent`；`slug-absent` 走 `#targetSlug` 的身份通道，§2.7）。
- `waves(): readonly TaskBatch[]` — 板面 wave 段的数据面；非 ready 返回空集。**它不是渲染信号**：`waves()` 为空既可能是「这版 plan 还没写 task」也可能是「读不出」，doc 面渲什么字面由 `degradedWaveRow()` 决定（§2.4）。
- `degradedWaveRow(words: PlanReadWords): string | null` — **doc 面**只负责**降级字面量**（§2.4 的四语义减一），外加 §2.7 的 `spec-absent` 字面：`undeclared` → `(none)`；`ready` 且零 task block → `(empty plan)`；非 ready → `! unparseable` / `! unreadable`；**`ready` 且有波次且无 `spec-absent` 折叠 → `null`**，表示「健康行不由本访问器负责」；`orphan()?.cause === "spec-absent"` → `! no-spec`（先折叠，§2.7）；`slug-absent` → `null`（身份破损不折叠，交回今日的健康行）。`#waveLines` 仍是装配者：先问 `degradedWaveRow`，得 `null` 才按今日路径渲健康行（`waves()` + `graph.report(ledger.closedWaves())` 的标记 + `#rowRounds(progress, key)` 的轮次段 + `LineCarriers.ofLedger(ledger, "wave", key, rounds)` 的 carried lines，一字不改）；`#nodeBoard` 同源。健康行的字节基准因此留在装配者手里，「健康 plan 的板面与 `next:` / `reason:` 逐字节不变」那条 AC 仍是字节断言而不是愿望；`#waveLines` **不再**以 `waves()` 是否为空作为渲 `(none)` 的信号。
- `cell(words: PlanReadWords): string | null` — **程序面**波次格的字面（§2.4 的四语义，外加 §2.7 的 `spec-absent` 字面；`undeclared` → `""`；**`ready` 且有波次且无 `spec-absent` 折叠 → `null`**，表示「健康格不由本访问器负责」；`orphan()?.cause === "spec-absent"` → `! no-spec`（§2.7；`slug-absent` 回 `null`，身份破损不折叠），`#programBoard` 得 `null` 才按今日路径渲 `waves[0]!.label.split(" ")[0] + "…"`，即 `W1…`），不接面参数——同一份 `undeclared` 在两面渲不同字面，靠**调哪个访问器**区分，不靠传参分支。
- `planLine(words: PlanReadWords): string | null` — plan 行的**格内容**：非 ready 时返回降级格内容（`<repo 相对路径> · <标记>`，标记 `! unparseable` / `! unreadable`）；`orphan()?.cause === "spec-absent"` 时返回（标记 `! no-spec`，§2.7）；`slug-absent` 回 `null`（身份破损不是孤儿，行交回 `#entryMark` 的既有记账，退出码不动，§2.7）；降级时形为 `<repo 相对路径> · <标记>`；**健康的 `ready`（`orphan() === null`）只返回 `<repo 相对路径>`**，不带分隔符与标记——一个分支一个返回，形状句只属降级分支。索引成员性**不在本值里判**：`readFor` 收 `DocEntry | null`、不收 `SlugIndex`，「ready 且已索引」是 `PlanRead` 观测不到的限定语；`#entryMark` 非空（`MARK_SLUG_INVALID` / `MARK_SLUG_DUPLICATED` / `MARK_SLUG_MISSING`）时装配者**根本不问本访问器**——身份破损先于读取值（§2.7 的第一层与第二层）；身份干净时才由装配者按**先判读取值、判完才问索引**（§2.1 的优先级）决定：`非 ready` 与 `spec-absent` 孤儿不经索引，`slug-absent` 不经 `planLine`（回 `null`，走 `#entryMark`），索引只裁决健康的 `ready`——裸路径因此只属「健康的 `ready` 且未入索引」那一格——标记复用波次格同一个词（`! unparseable` / `! unreadable`；`spec-absent` 孤儿用 `! no-spec`，§2.7；不另造），格子不经 `#docCell`；标签与 `LABEL_WIDTH` 的 padding 仍由 `#nodeBoard` 的 `  ${row.label.padEnd(LABEL_WIDTH)}${cell.text}` 负责（不搬进本访问器），降级 plan 行的完整字形因而是 `  plan     <repo 相对路径> · ! unparseable`（`LABEL_WIDTH = 9`，`trimEnd` 后无尾随空格）。`undeclared` 返回 `null`，plan 行照旧走索引派生的那一项；**两个入口面都生效**（`--plan` 与 `--spec` 同一条规则，不加面条件——少一个 if 就少一处将来的分叉），读失败不是 slug 缺失，不参与 `#entryMark` 记账，板面消费点因此不写 `switch (read.kind)`。
- `specLine(words: PlanReadWords): string | null` — **spec 行**的格内容，`spec-absent` 孤儿专用：`orphan()?.cause === "spec-absent"` → `! no-spec`（端口成员 `planOrphanWord()`），其余情形（健康 plan、非 ready、`slug-absent`、反查判不出的未判态）→ `null`，spec 行交既有的 `#docCell`。与 `planLine` 同形：只管格内容，标签与 `LABEL_WIDTH` 的 padding 仍由 `#nodeBoard` 负责；且**不经** `#entryMark` / `#docCell` 的记账——落进 mark 通道即 `blocked: true`，`#nodeBoard` 会 `return blocked ? 2 : 0` 出 exit 2，而孤儿板面要求 exit 0（§2.7）。
- `warnLine(words: PlanReadWords): string | null` — board 的 `CDD_WARN:` 行，**`unreadable` 产行**（`io` / `syntax` 两个 cause 同一词行），**`spec-absent` 也产行**（报文取 `planOrphanSpec`——`<slug>` 与派生路径同进报文；格字面 `! no-spec` 只属格，§2.7）；`slug-absent` 也产行，但用 `planSlugMissing()` 的词（身份破损，§2.7）——三个 cause 在 stderr 上按各自词行可分，行形见本节末「诊断行合成」；`undeclared` 与健康 `ready` 一律返回 `null`——「还没写 plan」是正常态而非读取失败，不产诊断行，`null` 面因此与 `refusal()` 的 `null` 面同宽。
- `refusal(words: PlanReadWords): { gate: "doc-contract"; reason: "doc-contract"; message: string } | null` — preflight 的拒绝通道入参：`unreadable` 与 `spec-absent` 孤儿各回拒绝（报文按「诊断行合成」取：`unreadable` 是 `${planReadWord(cause)} ${path}[: ${field}]`，`spec-absent` 取 `planOrphanSpec`，§2.7；不带 `warnPrefix`）；`slug-absent` **不**回拒绝——它在场景装配处就被身份通道（`#targetSlug` → `#slugBlocked`，exit 1）拦下，到不了这条腿；健康 plan 与反查判不出的未判态返回 `null`。它不产 `Finding`、不登记规则——阻塞来自读取值的拒绝腿（§2.3），与 `ctx.doc` 是否为 doc 形状无关。

`PlanReadWords` 是 `infra/plan-source.ts` 自己声明的词表端口（`planReadWord(cause)` / `planEmptyWord` / `planOrphanWord` / `planOrphanSpec` / `planSlugMissing` / `cellEmpty` / `warnPrefix` …），由 `face/words.ts` 的 `Words` 实现——依赖方向仍是 face → infra，词表仍旧单源。`warnPrefix` 保留，但契约写死：它**委托** `words.stations.warn`（`face/words.ts:201` 的 `CDD_WARN:` 行），字面单源，不另立第二份前缀——实现体读的是那个既有成员，不是第二份 `CDD_WARN:` 字面。

**诊断行合成**（三条，一处写死——`warnLine()` 与 `refusal()` 都从这里取件，不在各自分支里另拼）：`unreadable` → `${warnPrefix} ${planReadWord(cause)} ${path}[: ${field}]`（四件全取 `failure()`；`io` 无字段故无尾段，`syntax` 带 `: <field>`）；`spec-absent` → `${warnPrefix} ${planOrphanSpec(slug, specPath)}`；`slug-absent` → `${warnPrefix} ${planSlugMissing()}`。`refusal()` 的 `message` 是同样三条去掉 `warnPrefix` 前缀——前缀只属 stderr 通道。字面单源且可判：`planReadWord(cause)` 只产 `! unparseable` / `! unreadable`（`face/words.ts` 的 `CAPSULE_WORDS.planRead` 行），`warnPrefix` 是**访问器**而不是常量字面量——`get warnPrefix(): string` 的实现体返回 `this.stations.warn`（同一文件里的 `CDD_WARN:` 行）；测试因此钉端口成员与这一份前缀，不另造 `plan unparseable` / `plan unreadable` 这类第二份字面。

接线（一次读取、一个事实源）：`PlanSource` 在**命令前奏**（`#rootOf()` 解析出仓库根之后）构造一次，作为该命令的单一实例下行；`Cli.create()` 阶段没有根，不在那里构造（与 §2.1 首段同一条约束）；`Cli#runBoard` 在**自己内部**构造 `PlanRead`（`--plan` 走 `readPath`、`--spec` 走 `readFor`；两个旗标同时给出时**`--spec` 胜**——板面的 `PlanRead` 是 `readFor(specEntry)`，`--plan` 只保留既有的两项职责（判定 ① 的存在性探针与 `no docs match` 的旗标归因），与 `face/cli.ts:521` 的 `const entry = specEntry ?? planEntry` 同序；`readPath(planRel)` 只服务 `--plan` 单独给出的调用。overall 视图逐相位读取走同一个实例，按 `index.phaseSpecsOf(slug)` 的行序形成一张有序值表），并以**参数**传给 `BoardNext.of` 与 `BoardView.pipelineFacts`。`BoardView.render` / `#programBoard` / `#waveLines` 仍是静态方法，但改为**收值不再自读**（node 板收一个 `PlanRead`，程序板收逐相位的有序值表）——`BoardView.planGraph` 删除后，板面没有第二个读取点。工作路径上 `PlanRead` 随 `WorkScene` 下行（取代 `planText: string | null` 这个第二重事实源），`PreFlight#vet` 从场景取值，不各读一次；板面不建 `WorkScene` 是既有事实——`PlanRead` 是值，不是场景成员，不为此新增场景。反查与读取同一次，但**只在 argv 面**：`readPath` 在返回 `PlanRead` 前做那一次 `DocFs.exists` 探针；`readFor(entry)` **不反查**——它手里的 entry 就是那份身份文档，`spec-absent` 结构性不可达（§2.7）。因此每张板只算一次、没有第二条派生路径：派生面上零探针，argv 面上一份 plan 一次。三个 doc 面（`phase-spec` / `overall` / `single-spec`）的 `PlanRead` **同样取自 `readFor(entry)`**：今日它们手里的图来自 `face/cli.ts` 的 `const hopPlanPath = planPath ?? index.planOf(slug)?.path ?? null`，那正是同一相的派生路径上的同一份文档，所以「同一次读取」在 doc 面上也成立，不存在只造 `undeclared` 的第二条构造路径。doc 面只吃 `graph()` / `waves()` / `doc()`，不调用 `refusal()`——拒绝腿按**面**（plan 携带面）开，不按值开。`path()` 与 `stationPath()` 的分工在此写死：plan **行**对非 `undeclared` 一律取 `read.path()`（读不出也看得见它去读哪，「派生面读不出」那条 AC 的 plan 行断言）；**frontier 输入**（`BoardView.pipelineFacts` 的 `planPath`）一律取 `read.stationPath()`——`ready` 与 `unreadable`/`syntax` 非 `null`，`undeclared` 与 `unreadable`/`io` 回 `null`。这恰是今日 doc 面的逐 cause 分布：派生路径上的 `syntax` 坏结构今日 `planPath` 非 `null`、图 `null`，落 `PIPELINE_NEXT.plan`（它的 doc-contract 拒绝是应当被指向的下一面）；`io` 与 `undeclared` 今日 `planPath` 为 `null`。本段的「今日行为逐字节不变」因此按 cause 分开成立，`pipelineFacts` 也不再回落到 `index.planOf(slug)?.path`。路径与图在两处各取所需是**设计**，不是分叉事故：渲法（plan 行）给证据位置，路由（frontier）给证据本身——没有图就没有可推进的**波次**，而 `syntax` 的 plan 面指向的是它自己的拒绝。

doc 行的 plan 项与 wave 行同源，规则是一句可判定的话：**plan 行的事实源恒为 `PlanRead.path`**，优先级指向 §2.7 的三层编号——**身份破损先于读取值，读取值先于索引**：先看 `#entryMark(index, entry, "plan")`（`face/board-view.ts:308-314`，marker 在 `:141-143`），非空（`MARK_SLUG_INVALID` / `MARK_SLUG_DUPLICATED` / `MARK_SLUG_MISSING`）时 plan 行与 spec 行**不绕开** `#docCell`、按既有标记渲并 exit 2，`! no-spec` 一律不出现；身份干净才看读取值：**先判读取值、判完才问索引**——`非 ready`（`unreadable` 两 cause）或 `orphan()?.cause === "spec-absent"` 时一律用 `PlanRead.planLine(words)` 渲（repo 相对路径 + 标记）；`slug-absent` 不走这条（`planLine` 回 `null`，行交回 `#entryMark` 的既有身份记账，§2.7）——**`spec-absent` 孤儿在索引里是常态**（`cdd board --plan <孤儿>` 能到板面就说明它已入册，「argv 面归类顺序」那条 AC 把未入册的 `--plan` 送进 `no docs match`），若先问索引就必然落进 `#docCell`、渲成 `name  version · status` 而丢掉标记，`planLine` 的孤儿分支在两侧都成死代码，而 §2.7 的「不留半个格」也随之落空；索引**只裁决健康的 `ready`**：该路径解析到索引里的 `DocEntry` 就用既有的 `#docCell` 渲（今日字节不变），否则用裸路径（未入册的健康 plan）。三个面因此一致：相位文档有 plan 且派生路径解析到索引里的 `DocEntry` 时走 `#docCell`，健康对照逐字节不变，「健康 plan 的板面与 `next:` / `reason:` 逐字节不变」那条 AC 不受影响；`ready` 但派生路径未被索引收进去（plan 文件缺 `doc-type: plan`，或新 plan 覆盖旧 entry）时，plan 行渲该派生路径，而不是 `(none)` 或旧文档的 `name  version · status`；非 ready 时同样渲该路径加读失败标记（`--plan` 面走 `readPath` 的同一条规则）。由 `planLine` 渲出时，plan 行不构造 `DocEntry`、不参与 `#entryMark` 记账、不进 `#docCell` 的 blocked 判定，`#nodeBoard` 照常打 overall / spec / plan / branch 四行，只把 plan 行换成 `PlanRead.planLine(words)` 渲出的这一行。反向约束同源：**不许**把无身份的值包成 `DocEntry`——`face/board-view.ts` 的 `#entryMark` 读 `entry.slug`，空 slug 回 `MARK_SLUG_MISSING`，`#docCell` 随即 `blocked: true`，`#nodeBoard` 的 `return blocked ? 2 : 0` 把这次降级误判成 exit 2。于是「plan 行与波次格一分为二」在任何 kind 上都不发生：同一个 `PlanRead` 供两边，`plan` 行渲声明路径、波次格渲 `! unreadable`；`ready` 而声明路径未入索引时，plan 行渲声明路径、波次格照常渲健康波次行。argv 面由索引成员性裁决的判定（§2.4 判定 ③）不变——它决定的是**拒绝还是成板**，不是行的来源。

`WorkScene` 携 `plan: PlanRead`（`planText: string | null` 这个第二重事实源已退休）；brief 的交接在 `Cli#runWork`：`!parsed.dryRun && type === "wave" && scene.plan.kind === "ready"` 守卫内取 `scene.plan.document()` 的 `text` / `doc`，作为参数交给 `CliGate#renderBrief(scene, parsed, text, doc)`——`face/gate.ts` 自己不取 plan，也没有 `null` 分支可判。

#### 2.2 坏结构升级为类型化错误 `DocSyntaxError`

在 `contract/doc.ts` 的 `DocType` 基类旁定义 `DocSyntaxError`（携带 `field` / `message` / `fix`），不设 plan 专属类；plan grammar 抛它，其余 doc 型可复用。`contract/task-block-grammar.ts` 的 `TaskBlockGrammar#assertNoDuplicateKeys` 改抛它，不再抛裸 `Error`；`parse(): PlanParsed` 的签名不变，`assert` 从此只承载编程不变量。

物化只发生在**有消费者**的地方——判官边界：`contract/judge.ts` 的 `#contextOf` 只**把 `DocSyntaxError` 带出来**（它返回 `JudgeContext`，物化不在这一层），`Finding` 由 `validate` / `validateLedger` 物化——`path` 取 `ContractInput.path`、`field` 取错误自带的字段、`fix` 取错误自带的修复提示。`infra/plan-source.ts` **不物化** `Finding`：`unreadable` 自带的 `path` / `field` / `cause` 就是失败值本身，`refusal(words)` 直接交出 `{ gate, reason, message }`——同一事实不在同一对象图里携带两遍（D26「一事实一处」）；`DocSyntaxError` 的 `fix` 因此只服务判定面的 `Finding`。`kind` 字面量统一为 `"doc-syntax"`（`Finding.kind` 是不变量类名词汇，不是 station 的 reason token，故不新增令牌）。两个字面量必须逐字节相同，由测试钉住。

`path` 不进 grammar：文件身份是读者的事实。`contract/judge.ts` 一侧的路径来自 `ContractInput.path`（`Finding.path` 的既有归因源），因此 `validate` / `validateLedger` 对 `#contextOf` 的调用包在 try/catch 里：捕获 `DocSyntaxError` → 产一行 `Finding`，而不是穿透判定门。

""` 都不是可接受写法。

#### 2.4 降级显式：视图面与 preview 面

四语义一格不多一格不少：

| 语义 | doc 面 wave 行 | 程序面波次格 |
| --- | --- | --- |
| 真 undeclared（该相位没有 plan） | `(none)` | `""`（`""` 只属于这一种语义） |
| `ready` 但零 task block（skeleton 刚生成） | `(empty plan)` | `(empty plan)` |
| `unreadable` / `unparseable` | `! unreadable` / `! unparseable` | 同 |

§2.7 的 `spec-absent` 孤儿**不是第五种读取语义**：`read.kind` 仍是三态，孤儿是 `ready` 上的身份破损，只把 plan 派生的字面折叠成 `! no-spec`（§2.7）；`slug-absent` 是另一回事——身份破损但 plan 体面解析得成，不折叠任何字面，也不短路 `next:`（§2.7）；四语义表与 `(empty plan)` 的分界一字不动。

doc 面的 wave 行分两段：`PlanRead.degradedWaveRow(words)` 只产降级字面量（`spec-absent` 另有 `! no-spec`，§2.7），`ready` 且有波次且无 `spec-absent` 折叠时返回 `null`，由装配者 `#waveLines` 按今日路径（`waves()` + `graph.report(ledger.closedWaves())` + `#rowRounds` + `LineCarriers`）渲健康行；程序面的波次格由 `PlanRead.cell(words)` 生产，它只产降级字面量与空串（`undeclared` → `""`；`spec-absent` → `! no-spec`，§2.7；`slug-absent` → `null`，不折叠），`ready` 且有波次且无 `spec-absent` 折叠时同样返回 `null`，由 `#programBoard` 按今日路径渲 `waves[0]!.label.split(" ")[0] + "…"`（即 `W1…`）——健康 doc 行与健康程序格都「不由本访问器负责」，两面成对。同一份 `undeclared` 在两面渲不同字面，靠**调哪个访问器**区分，`cell` 不接面参数；`#waveLines` / `#nodeBoard` 渲 doc 面波次行时**从不**以 `waves()` 是否为空作为渲 `(none)` 的信号。

格面字面按 `LABEL_WIDTH`（`face/board-view.ts`）对齐：真 undeclared 那一行是 `  wave     (none)`（前导两空格 + `wave` 补齐到 9 列），验收逐字节对照这条字面，不写活动格。

`(empty plan)` 走**独立端口成员** `planEmptyWord()`（与 `cellEmpty` 并列的同级 station，仍是 `PlanReadWords` 的一员），不进 `planReadWord(cause)`——后者只承担 `io` / `syntax` 两种读失败。理由：健康但空的状态不是读失败，塞进失败词法会让测试从同一处推出字面量而永不红。该字面不得回落 `(none)`，也不得回落空串——它是「有 plan、还没写 task」的正常态，与「没有 plan」不是一件事。

board 收到**读取失败或 `spec-absent` 孤儿**的 `PlanRead` 时额外打一行诊断：`CDD_WARN:` + 对应词行，走 **stderr**（`face/lifecycle.ts` 与 `face/cli.ts` 的现有一律 stderr，`words.stations.warn` 是诊断锚）；stdout 的 wave 块零字节变化（只差那一格），退出码仍 0（`slug-absent` 不在退化面：它走 `#entryMark` 的身份通道，exit 2 不动，§2.7）。写者是 **`Cli#runBoard`**：`BoardView.render` 是纯函数（静态返回 `{ lines, exitCode }`，不持有 io 通道），不承担写盘——`Cli#runBoard` 在打印渲染行**之前**调用 `read.warnLine(words)` 写 stderr；overall 板由它按 §2.1 那张有序逐相位值表，对**每个读取失败的相位**各写一行（行内带相位 id）——`undeclared` 的相位不写（`warnLine` 对它返回 `null`），故诊断行数恒等于坏 plan 数、`spec-absent` 孤儿数与 `slug-absent` 数之和（`slug-absent` 那行用 `planSlugMissing()` 词，§2.7）。把诊断放 stdout 会让一个站牌词跑上没有站牌走的通道。

程序面（`BoardView.#programBoard`）一条降级、两处落点：每个坏 plan 的相位各出一行 `CDD_WARN:`（行内带该相位的 `slug:`，多相位板上才定位得到），打 **stderr**；波次格只渲 `! unparseable` / `! unreadable` / `! no-spec`（真 undeclared 仍是 `""`；`spec-absent` 用 `! no-spec`，§2.7），健康相位行的波次格仍按今日路径渲 `W1…`（`cell(words)` 对它返回 `null`），不在格内另造标记，相位行其余列零字节变化。

`cdd board --plan <存在但读不出>` 是 argv 面，**不出板面**：读取失败即拒绝，保持 exit 2，但报文必须点明是读失败而不是「没有这份文档」——`cdd board: cannot read --plan <path>`（**不带原因尾段**：`DocFs.read` 只回 `string | null`、不携带 errno，接缝上已经没有原因可取，硬造一个就是消费者可见的臆造字面——`cause: "io"` / `"syntax"` 的区分走 `CDD_WARN:` 那行与 `planReadWord` 词行，不进这条报文）；`#boardNotFound` 的 `no docs match` 只留给**判定 ① 的存在性失败**与**判定 ③ 的索引缺员**两种非读取失败——后者含并发面的 X：两个旗标同时给出时它的字节不读，读不出的 X 因而不可入册、由成员性归类到这里；`cannot read` 只属「`--plan` 单独给出且字节读失败」这一格）。没有板面就没有 `next:`，charter ④「读不出不得授权下游 `next:`」自动满足。exit 0 的 `! unreadable` 渲染只经相位文档的 slug 派生面到达（§2.1：`docs/kairos/plans/<slug>.md` 存在但读不出），两条面各归各的通道，不复用同一个身份。读得成功但索引里没有这份文档（不是两个 doc root 下的扫描面）仍走既有 `#boardNotFound`（exit 2）。

归类顺序一句写死——四个判决不在同一层，重叠时必须有序，且**判定 ① 是存在性探针**（与今日代码同序，零文档读取）：① **`SlugIndex.insideDocRoots` + `existsSync`** → 不存在（不在 doc roots 内或盘上无此文件）→ 既有 `#boardNotFound`（`no docs match`，exit 2；`face/__tests__/cli.test.ts` 的 ghost-path pin 不变）；② 存在 → **读字节**（**只在 `--plan` 单独给出的调用上**——两个旗标同时给出时 X 的字节不读，所以这一路**永不**出 `cannot read`：读不出的 X 由 ③ 的成员性归类，`no docs match` 正是它的面；供值的 `PlanRead` 恒取 `readFor(specEntry)`），读失败即 `cdd board: cannot read --plan <path>`（exit 2，不带原因尾段——理由见上句）；③ 字节读到后**由索引成员性裁决**，不在索引即既有 `#boardNotFound`（`no docs match`，exit 2）；④ **只有已入索引的 plan 才走文法判决**，坏文法渲 `! unparseable` 板面、exit 0。重叠情形取此序：**存在但读不出 ∧ 不在索引 → `cannot read`**（存在性已过、io 失败先于成员性；这只对 `--plan` 单独给出的调用成立——并发面 X 的字节不读，同一份 X 在那里走 ③ 得 `no docs match`）；读得到但不在索引的非 plan 文件一律 `no docs match`，其文法如何不参与裁决。值来源不参与这个顺序：两个旗标同时给出时判决仍逐条走（① 探两者的存在性、③ 判任一成员性），而供值的 `PlanRead` 恒取 `readFor(specEntry)`（§2.1），`--plan` 单独给出时才取 `readPath(planRel)`——`cdd board --plan X --spec Y` 里 X 的内容不进任何一格。

`--dry-run` / preview 与真派同批：preview 在坏 plan 上同样返回 BLOCKED，不降级。preview 的卖点是「先看这一轮会做什么」，让它照常输出等于把同一个谎报搬到第二个面。

#### 2.5 缺证据不得授权下游

`session/pipeline.ts` 的 `#waveState` 与 `#wavesExhausted`、`session/dispatch-authority.ts` 的 `#waveStation` 改吃 `PlanRead`：`undeclared` 保留今日语义（未进入 / 没关门 / 无站牌）。两个 `unreadable` cause 与 §2.7 的 `spec-absent` 孤儿在可达路径上不进这三处——真派路径由 §2.3 的结构拒绝先一步拦下，板面路径由 `BoardNext.of` 的同一对短路条件先一步拦住；`slug-absent` 更早：plan 携带面在场景装配处就被 `#targetSlug` 的身份拒绝拦下（§2.3 的第二条「没有键」）；因此「不授权」成立、`PipelineFaceState` 不必多出第四个值、令牌表不动。frontier 的图与路径输入**不同界**，且两边都以今日为准：图只见 `ready`（`graph()` eager 于同一次解析），路径取 `stationPath()`——`ready` 与 `unreadable`/`syntax` 非 `null`，`undeclared` 与 `unreadable`/`io` 回 `null`。于是「有路径没图」这一格只对应 `syntax`，而它**不构成一次推进**：plan 面拿到同一条路径，它自己的 doc-contract 拒绝（§2.3）就是前沿指向的那一面，`#waveState` 因 `planGraph === null` 照旧读作未进入——这正是今日的形状（今日该输入 `planPath` 非 `null`、图 `null`、落 `PIPELINE_NEXT.plan`），不是本相位新开的路。`io` 与 `undeclared` 的 `planPath` 回 `null`，路由面拿到的仍是今日的回落语义。

`session/run.ts` 的 `Lifecycle#recordPlanSnapshot` 改吃 `PlanRead`：非 ready → 不记快照；「缺快照读作 stall」原样保留。账本是记录面，为一个坏 plan 把已完成的 wave 卡死在闭合点，会把读取缺陷升级成流程死锁，而 stall 已经给出了保守的正确答案。

#### 2.7 反查：plan 必须命名一份相位 spec

前向（相位 → plan）缺失是**正常状态**：一个相位可以注册了、还没写计划，读作 `undeclared`、渲 `(none)`。反向则不同——plan 是**为一枚相位写的**，那份 spec 就是它存在的理由。plan 的 slug 找不到 `docs/kairos/specs/<slug>-design.md` 时，身份已经破了，不能像前向那样降级成 `(none)` 了事。

- **反查只问存在性，不问内容谓词**：派生式与前向是同一个表达式换一个根——`${ENGINE_DOC_ROOTS.specs}/${slug}-design.md`，只经 `DocFs.exists` 探「这份文档在吗」。slug 的来处分两条：**反查只在 argv 面成立**：`readPath` 没有 entry，故由解析后的 front matter `slug` 派生 `<slug>-design.md` 并用 `DocFs.exists` 探一次（前提是那个 slug **合法**——非法 slug 连派生都无从谈起，`orphan()` 直接回 `null`，见下条三层优先级）；`readFor(entry)` **不反查**——它手里的 entry 就是那份身份文档，`spec-absent` 结构性不可达，只剩 `slug-absent`（`entry.slug === null` 时，而那已归 `undeclared`）。理由写在字面上：`#scanRoot` 索引的是 doc root 下任何可读的 `*.md`，`-design` 后缀只是本仓的布局惯例（P15/D59 已退役文件名身份），所以一份合法声明 `slug: X`、文件名却不带 `-design` 的 spec 是正常入册的 entry——若派生面也探，它读自己的 plan 时会算出 `spec-absent`，`cdd board --spec` 把自己的 spec 行渲成 `! no-spec`、`review --type plan` 对一份完全健康的 pair 报 `CDD_BLOCKED`，这就是造出假孤儿，反查就是读取的一部分。不得用 `SlugIndex#phaseSpecsOf` / `#planOf` 的反向拼装实现：索引把「读得出」当入册前提（`infra/slug-index.ts` 的 `#scanRoot` 丢掉不可读候选），那样写会把「存在但读不出」误判成「缺失」，凭空造出一批假孤儿。探针**每张板只算一次**，从同一个 `PlanSource` 缝取（§2.1 的接线仍是唯一入口），不派生第二条读取路径。
- **事实落在读取值上，不登记新规则**：反查的答案不是 doc 形状的违规，而是「这份 plan 有没有命名一个相位」的读取事实，因此 `contract/rules.ts` / `contract/invariants.ts` 一行不改、不产 `Finding`、`kind` 词法零新增（`"doc-syntax"` 仍是唯一新增的词，§2.2）。`PlanRead` 仍只有三态；`ready` 额外携带 `orphan(): PlanOrphan | null`（§2.1）——`spec-absent` 是盘上没有 `<slug>-design.md`（`specPath` 即该派生路径），`slug-absent` 是 argv 面那份 plan 自己没写 `slug`（谁也没命名，无处派生，`specPath` 为 `null`）。阻塞仍走 §2.3 那条**不挂门的腿**，但只对 `spec-absent`：`refusal(words)` 在 `spec-absent` 时回拒绝（`gate: "doc-contract"` / `reason: "doc-contract"`），拒绝来自场景里的 `PlanRead`、与 `ctx.doc` 是否为 doc 形状无关，所以 `plan` / `wave` / `branch` 三个面加各自 `--dry-run` 一律 `CDD_BLOCKED`——没有命名相位的 plan 不该被评审，更不该被实施。`slug-absent` **不走这条腿**：它是身份破损而不是孤儿，工作面上由 `#targetSlug` 的既有身份通道拦下（`CDD_BLOCKED:` + 「the doc declares no slug: key …」、exit 1），板面上由 `#entryMark` 记账（exit 2，见下条），`refusal()` 对它回 `null`。报文两个词行仍然同族且可分：`spec-absent` 取 `planOrphanSpec`（`<slug>` 与派生路径都进报文），`slug-absent` 取 `planSlugMissing()`。
- **三个观测点各自的落点**：① **spec 行**走非阻塞通道——**仅当身份干净（`#entryMark` 为空）时**，`spec-absent` 字面量像 `planLine` 一样绕开 `#entryMark` / `#docCell` 的记账（落进那条通道 mark 即 `blocked: true`，`#nodeBoard` 会 `return blocked ? 2 : 0` 出 exit 2），所以 **exit 0 由通道选择决定，不由字面量决定**；`#nodeBoard` 在 spec 行上先问 `#entryMark`（非空即按既有标记渲、exit 2），为空才问 `PlanRead.specLine(words)`，非 `null` 就渲它、不再进 `#docCell`。② **hop-less `next:`** 把短路谓词收成**一对**条件：`read.kind === "unreadable" || read.orphan()?.cause === "spec-absent"`，`BoardNext.of` 与 §2.3 用同一对，`spec-absent` 不另开第三条短路，`next:` 渲已有的 `  next:    (none)` 且不出 `reason:` 行。③ `planOrphanWord()` 的家是 `PlanReadWords`（与 `planEmptyWord()` 并列，因为它与其余降级词法同属 cell 载荷那条缝）；`MARK_*` 是身份记账通道，两者不许混。**只有 `spec-absent` 折叠**：格字面 `! no-spec` 只属它；`slug-absent` 的 `planLine` / `specLine` / `degradedWaveRow` / `cell` 一律回 `null`（行交回 `#entryMark` 的既有身份记账，exit 2 不动），它的诊断只走 `warnLine` 的 `planSlugMissing()` 词行——两个 cause 在报文与 stderr 上同族而可分。
- **身份破损先于读取值（三层优先级）**：第一层在**值里**——`orphan()` 在 slug 不合法时回 `null`（`SlugIndex.isLegalSlug` 是纯谓词，不需要索引），非法 slug 派生出的路径不存在，那不是 spec-absent 而是身份破损；第二层在**装配里**——板面先看 `#entryMark(index, entry, "plan")`，非空（`MARK_SLUG_INVALID` / `MARK_SLUG_DUPLICATED` / `MARK_SLUG_MISSING`，`face/board-view.ts:141-143` / `:308-314`）则 plan 行与 spec 行**不绕开** `#docCell`，按既有标记渲并 exit 2，`! no-spec` 一律不出现；第三层才是「先判读取值、再问索引」（§2.1）。这三层是硬要求，不是风格：`#runBoard` 只经 `index.entryAt(planRel)` 放行（`#byRel` 收录每一份可读文档、只过滤 `#bySlug`，`infra/slug-index.ts:145`），非法 slug 与重复 slug 今日都到得了板面、并由 `#entryMark` → `#docCell` → `return blocked ? 2 : 0` 判成 exit 2；若让 `planLine` 绕开这条通道（绕行只对 `spec-absent` 孤儿开），两个既有的 exit 2 会被翻成 exit 0，真正的缺陷被报成「没有 spec」——把身份破损报成孤儿与把 exit 2 翻成 0 是同一个病，两个已有的身份面各被拆掉一半。
- **板面降级到既有纪律**：`spec-absent` 孤儿上，从 plan 派生出来的每个字面都由**既有访问器**折叠而不是新增分支——`degradedWaveRow(words)`、`cell(words)`、`planLine(words)`、`warnLine(words)` 一律回 `! no-spec`（`planLine` 仍是 `<repo 相对路径> · ! no-spec`），spec 行由 `specLine(words)` 回同一个字面；折叠判定**先于** `(empty plan)` / 健康行，`ready` 且零 task block 的 `spec-absent` 孤儿同样是 `! no-spec`。`Cli#runBoard` 写一行 `CDD_WARN:` 到 stderr，**exit 0**——视图可以退化，但不能静默。`slug-absent` **不在此列**：那是「plan 体面解析得成、自己没写 `slug:`」的身份破损，不是孤儿——`planLine` 回 `null`，plan 行交回 `#entryMark`（`MARK_SLUG_MISSING`，`blocked: true`，`#nodeBoard` 的 `return blocked ? 2 : 0` → **exit 2 不动**），wave 行与 `next:` 按今日字节渲（不折叠、不短路），stderr 多写一行 `CDD_WARN:` + `planSlugMissing()` 词行——不加这一行，`no-spec` 与 `slug: missing` 两个 cause 在板面上就分不开。
- **未判态不假装判过**：反查只判「盘上有没有 `<slug>-design.md`」。存在但索引给不出身份文档（缺 `doc-type: phase-spec`，或读不出被 `#scanRoot` 丢掉）时——不拒绝、不渲 `! no-spec`，spec 行照今日渲 `(none)`，这是**未判态**（读得出、索引给不出身份），不是「相位没有 plan」那个合法态，也不新增第二个字面量。界限因此是一句话：**凡是反查判得出的情形，plan 面上不再出现半个格**（spec 行 `! no-spec`、plan 行带同一标记、波次格同字面），判不出的情形照旧渲 `(none)`，不冒充「判过且没问题」。
- **不留豁免**：这条门的判据是「每份 plan 的 slug 都解得到 `<slug>-design.md`」，**不是**今天的快照——它从落地第一天起就绿（当下语料 34 份 plan ↔ 34 份 spec，0 孤儿、0 份文件名与 slug 不符），并在这条不变量被打破的第一份孤儿上变红；因此没有历史债要还，也不接受白名单。

### 3. 失败面

#### 3.1 裸崩面的残留路径

场景装配先于 preview 与 usage 校验执行，`#renderWaveBoard` 又在拒绝分支之后。所有读取点都必须改吃同一个 `PlanRead`，否则会出现「门禁已拒绝、渲染先崩」的顺序漏洞。验收要求 stderr 不再出现 `cdd: ` 前缀的文法报文。

usage 校验的 `planIds` 成员判定在非 ready 时**跳过**——它今日排在 `#renderPreflightBlocked`（`face/cli.ts:779`）之前，若让非 ready 的空集跑到 `face/cli.ts:706-716`，每个请求 id 都会走 `this.#usage(node, …)` 报出 `cdd <verb>: task <id> not found in the plan`（`#usage` 返回 `never`，`error:` + exit 2），「`implement --tasks --plan` 上 `reason: doc-contract`」那条 AC 的 `CDD_BLOCKED:` 就没机会渲出。落法：该循环以 `read.kind === "ready"` 为**执行前提**（不是以「集合为空」为信号）——结构拒绝拥有裁决权，usage 只校验一个可解析 plan 内部的 id 成员性。`BriefRenderer` 不再是这条要求上的风险面：默认参数删除后它**已无解析可抛**（§2.6），`render` / `taskBody` / `extract` 收的是 `PlanRead.text()` 与 `PlanRead.doc`——因此这条要求不再依赖「被前置拒绝挡住」的时序论证；§1.1 的顺序事实仍由 pin 钉住（doc-contract 拒绝先于 brief 渲染），但它现在是冗余保障，不是唯一保障。

#### 3.2 `(none)` 与退出码的既有 pin

`cli.test.ts` 把 `(none)` 降级与 exit 0 绑在一起，`board-view.test.ts` 钉着合法的 `  wave     (none)`。降级面重构后这两处 pin 必须仍绿——它们是「不误伤健康路径」的证据。

#### 3.3 IO 与语法分叉后的报文覆盖

`DocFs.read` 返回 `null` 已是 IO 面的事实（读不出），与文法坏结构（读得出、判不过）是两件事。两条词行各自被至少一条测试覆盖，避免只测其中一条就让另一条裸走。

#### 3.4 判定面的路径归因

`contract/judge.ts` 的 `#contextOf` 只把 `DocSyntaxError` 带出来，物化在 `validate` / `validateLedger`；两侧都必须补上 `ContractInput.path`，否则 `Finding.path` 会出现空串或读者路径，判定面的锚定失效；这个分支由 `contract/__tests__/judge.test.ts` 的新增用例（跑 `validate`）覆盖。
