## Design

本 phase 承接 P6 收口后的连续重构（程序六 phase 收口后的续 phase · 2026-10-13 cdd-design [P7] 会话注册 D23 · grilling 裁定 D24/D25 全按落定 · v0.5 六前提重审整个 phase 折入 dogfood 修复 D26）。**统一命题——单一实况判定面（a fact, one place, read at judgment time）**：引擎对任一事实只持一处实况、判定时刻现读，**永不信任派生副本**。P7 起初把它表述为「评测面从检查 commit 转为基于代码实况」——但那只是**第一个病例**。同一 dogfood 会话（P7 自举踩出）又暴露 round/key/field 三个同病副本，与 commit-sha、brief 汇成**五个副本同一条法条**（下列动作集含副本修复、结构决定与随附清理）：① 评测面 **commit-sha 整体退休**（R2/Q1 · sha = 冻结的树身份副本，胜过 live tree → review 审错范围）· ② 所有 child 派发前的物料准备 **无条件 extract**（R1/R3 · 盘上旧 brief = 计划面副本，胜过当前 plan → implement 读旧、review 读新）· ③ wave 三 face（implement/review/fix）**单输入 = 完整计划镜像 brief**（Q4(a)）· ④ **review 基准 = 最新 brief + live tree**（Q2）· ⑤ **branch review-fix 基于 base→head 方向**（R4 · base = 分支名，非双 commit sha）· ⑥ **changes[] 同退役、改动面由 review 自判**（Q3）· ⑦ **I7 撤除** · **⑧ dogfood 修复（D26 · 同一法条的另三个副本）**：**round verdict 单源化**（Q1 · 磁盘草稿副本胜过内存 read-back → `BLOCKED` 却渲 `next: done`）· **doc 线键实况化**（Q2 · argv 字符串副本胜过规范键 → round 计数重置 · 两派生点同修：run.ts `#lineKey` + gate.ts `#lineKey`）· **postflight 字段单裁**（Q3 · 校验器第二套裁决 vs materialize 单源 → 未声明字段 drop-or-reject 自相矛盾）。设计输入：kairos:cdd-design [P7] 会话（D23 注册 · D24 grilling Q1/Q2/Q3 裁定 · D25 Q4(a) 裁定 · D26 dogfood 修复裁定）· overall v2.22（D23）→ v2.25（D26）· recon 报告（commit-sha 触点全谱审计 · changes[]「引擎对账」prompt 虚构实证 · wave/doc/branch 三线 round context 逐 token 对比 · GitClient 生产调点枚举 · 载体残余字段调点复核 · P7 spec review-fix dogfood 现场取证：spec-fix-1 被拒草稿 + progress.json 双行键）。六前提重审整个 phase 后：命题收敛为**一条纪律的五个副本**（sha · brief · round · key · field），整体转向为「一事实一处 · 判定时刻现读 · 副本仅缓存且可失效重建」；**I7 撤除与收尾扫为随附清理动作，不计入副本数**。

### 1. 目标与边界
#### 1.1 设计输入与授权
- 设计输入：kairos:cdd-design [P7] 会话（D23 注册 · D24 grilling Q1→评测面 commit-sha 全退役 / Q2→review 基准=最新 brief / Q3→changes[] 同退役 · D25 Q4(a)→brief=完整计划镜像+三 face 单输入 · overall v2.24）· recon 报告（2026-10-13 · commit-sha 触点全谱 + changes[] 对账虚构实证 + 三 face round context 逐 token）
- **授权（六前提 · D23）**：允许破坏性变更、重写代码重组目录 · 从高维思考、OOP 抽象统一、零裸函数 · 最佳实践、不留技术债务、避免散文堆砌、避免声明再抄 · 高内聚低耦合、死代码空壳全清 · 消费者心智负担优先 · 最大程度重构整合、最大程度精简系统
- **授权（Q4(a) · D25）**：wave 三 face 单输入 `INPUT_WAVE_BRIEF`（brief = 任务段 + `## Constraints` 段完整镜像）· `OUTPUT_BRIEF` 折叠（brief 纯输入）· `INPUT_PLAN` 退役 · `INPUT_RANGE` token 整体退役（doc 锚 → `INPUT_DOC`）· 保留 `INPUT_FINDINGS`(fix) + `OUTPUT_EVIDENCE`(implement/fix)
- **不发布**（与 P1–P6 一致）：变更集归并落 pending · tag / publish = 独立动作
#### 1.2 退役判定模型（审定的根前提）
- **统一法条 = 单一实况判定面**：任一事实（树身份 · 计划面 · round verdict · 线身份 · 字段处置）只有**一处实况源**，只在**判定时刻现读**；任何**派生副本**（冻结 sha · 盘上 brief · 磁盘草稿 · argv 字符串 · 第二套 schema 裁决）都不具权威——副本胜过实况之处，即为漂移。副本若为性能/缓存而存在，必**可失效重建**，判定面永不读它。本 phase 的五个副本（sha/brief/round/key/field）全是该法条的一次实例化，非五条独立规则；I7 撤除与收尾扫为随附清理动作（不计副本数）。
- **commit sha = 传话筒不是裁判（树身份副本）**：GitClient 无任何 diff 方法（recon 实证 · git.ts 六 seam 全枚举）· templates.ts:485 的「引擎 reconcile `git diff <base>..HEAD`」是 **prompt 虚构**（引擎从不执行对账 · lifecycle.ts:549 只是 copy-through）· `scope_base`（ledger.ts:121）死字段无人写 · `snapshotSha` 恒 null（lifecycle.ts:507）· `addAll`/`commit`/`log` 三个 git seam 生产面零调点（recon）
- **sha 的唯一职责 = 告诉 review child diff 哪个范围**——恰是漂移源：base/head 传错 → review 审错范围。替代：review 基于 **live tree + 最新 brief + base 分支名** 自判（child 自己跑 `git diff`）——评审面全部落在代码实况，零 sha 携带
- **同一法条的 dogfood 副本（v0.5 · D26 · P7 自举踩出）**：**round verdict**（§2.8）——磁盘上被拒的草稿（副本）胜过内存 read-back 的 outcome（实况）→ `BLOCKED` 却渲 `next: done`；**线身份键**（§3.7）——`--spec/--plan` 的 argv 字符串（副本）胜过规范键（实况）→ 同一 doc 两行 ledger、round 计数重置；**字段处置**（§8.7）——校验器的 `additionalProperties:False`（第二套裁决）胜过 materialize 的单源声明读取（实况）→ 同一字段既 drop 又 reject
#### 1.3 保留面（冻结 · 非提交 sha 的实况携带者）
- **clean-tree gate 保留**（preflight.ts:129-133 · review 基线 = committed tree · 脏 → BLOCKED）· **doc_revision 内容指纹保留**（ledger 记录被评 doc 内容的 sha1 · run.ts:551-563 · 最新计划 reopen gate —— 非 commit sha · 内容实况）· **base set/get 语义不变**（新增 review 面读它 · 见 3.2）· doc-contract 判定语义不变（gate 零例外）· `WAVE`/`tasks`/`OUTPUT_REPORT`/`OUTPUT_HANDOFF`/`OUTPUT_EVIDENCE`/`INPUT_DOC`/`INPUT_FINDINGS` 保留 · 六命令功能语义不变（除 review 面 ref 退役）· `mattpocock-skills` 分派表零动

#### 2.8 round verdict 单源化（dogfood Q1 · 同一法条：verdict 的磁盘副本胜过内存实况）
- **缺陷现场（P7 spec 自举取证）**：child 写的 `spec-fix-1.json` 带 `status`（`engineOnly`）→ `#reconstruct` 的 `schema.violations` 命中 `additionalProperties:false` → `#reject` 返回 `{status:"BLOCKED"}` 且**故意不覆盖草稿**（on-failure no-overwrite · lifecycle.ts:446-513）→ `#bookkeep`：`blocked=true` 且 `carrier===undefined` → **不 persist、不 recordRound**（run.ts:494-543）——**但** `advance()` 的 `route = #routeNext(frame)` **从磁盘重读** round（run.ts:591-596）：`ledger.round("fix","spec",…,1)`（ledger.ts:767-778）读到被拒草稿**存在** → fix Round `status="APPROVED"`（**child 的脏副本**）→ router（next.ts:103-123）绕过 `FAILED_STATUS` 守卫、`blockerCount=0` → `#close(EMPTY_RUN_STATE)` → **`{kind:"done"}`** → `cli.ts:537-540` 在 BLOCKED 分支照样打印 → stdout **`status: BLOCKED · next: done`**（自相矛盾面）
- **修法（verdict 单源 · 无记录即无判决）**：**`ledger.round()` 的 round-read 以进度计数（`recordRound` 的记录）为门控**——一个**未被 `recordRound` 记入进度**的 round 不是 round，返回 `null`（无论磁盘草稿是否在）；`op==="fix"` 腿与 `op==="review"` 腿同判。**门控读「该 `op` 的被记录 mode」而非字面 `rounds.review`**：review 腿读 **`rounds[reviewLead(type)]`**（wave/spec/plan→`review` · branch→`branch-review`，faces.ts:95-109 · `recordRound(frame.key, frame.phase)` run.ts:524 记的正是 `frame.phase` = reviewLead）——若按字面 `rounds.review` 门控，run.ts:401 `#roundRoute` 发出的 `round("review","branch",…)` 将恒返回 null → `#nextLinePhase` 的 fix-awaits 判定恒空 → branch review 后无法打开 fix 轮（整条 branch 线冻结）；`op==="fix"` 腿读 `rounds.fix`。**根因同时消除**「磁盘草稿存在 ≠ round 完成」的语义混淆——`ledger.round()` 的契约从「读磁盘草稿」改为「读已记录 round 的载体」，与 `recordRound` 单源。**route=null → failure face → 零 `next:` 行**（router 自身契约 next.ts:12 · BLOCKED → null），与 `cli.ts:544` 的「completed non-failed round 无 next = hard error」正交（BLOCKED round 走 `:537` 早退，不触及 `:544`）
- **连带**：此修法使 Q1 的 `#reject` 不覆盖草稿（合理保留：child 工作不丢）**不再有副作用**——脏草稿留在盘上无害，因为它不被当作 round 读回

#### 8.7 postflight 字段单裁（dogfood Q3 · 同一法条：校验器的第二套裁决胜过 materialize 单源）
- **缺陷现场**：`#materialize`（lifecycle.ts:521-554）建 carrier 时**只读声明字段**（`draft.artifacts/commits/findings/changes/notes/failure_category`）——**未声明多余字段本已被丢弃**；但 `violations`（handoff-schema.ts:252-258）的 `#check` 命中 `additionalProperties:false`（:322-345）即**整体 BLOCK**——**同一批字段两套裁决**（builder drop · validator reject）。尤其 `status` 是 `engineOnly`（handoff-schema.ts:118-134 · CARRIER_FINDINGS `engineOnly:["status"]`）：引擎**无条件覆写**它（`carrier.status = status`, lifecycle.ts:548）——child 写 `status` 是写了一颗引擎注定丢弃的字段，为其 BLOCK 是**纯摩擦**（p3/p5/p6/p7 的 crash 记录全是这一类：`status: not a declared field`）
- **修法（单裁 · 声明即权威）**：postflight 违规**分类裁决**——**(a) 语义错保留 BLOCK**：缺 `required` 字段 · 类型不符 · `enum` 越界 · `COMMITS` 的 8-char 长度违例（如 p5 的 `commits.base` 40 字符 = 真误读）· child 对**必需面**的误读必须 BLOCK；**(b) 非声明多余字段与 `engineOnly` 字段归一化 drop（不 BLOCK）**：`#materialize` 已 drop，校验器**对齐之**（同源同判）· 至多一条 **WARN booking** 落 carrier `notes`（`lifecycle.ts:558` 的 notes 写点 · 引擎活跃 notes 承载 reason/evidence-note —— §8.1）——**WARN 可审计、不中断 round**，取代「BLOCK + crash-resume + reopen churn」三重代价链
- **原则（防再漂移）**：**校验器与 materialize 必须同源同判**——校验只对「materialize 会保留的字段」判语义，对「materialize 会丢弃的字段」同判 drop（可带 WARN）；两处对同一字段的处置**永不背离**。`engineOnly` 的 read-back 拒绝语义因此**并入归一化**（该 key 是声明上的 engine-reserved，drop 即闭合，非可写拒签）
#### 8.8 判定面 ⊥ 输入面（v0.7 · D27 · D26 补完 · v1.30 载体单声明面收口）

#### 8.9 round 身份单源（v0.9 · D28 · D26 家族）
- **缺陷现场（W10 实测）**：fix 轮的**身份**是它**修的 review 周期号**（fix-K ⟷ review-K），由 `#roundFor("fix") = reviews` 派生（`run.ts`）→ fix 载体名 `tasks-10-fix-2.json`（= 修 review-2）与 `next:` 的 `--findings ...tasks-10-review-2.json` **同源**。但 `progress.rounds` 记的是**计数**（`{fix: 1}`）——`round()` 的门控读 `roundCount(1) < round(2)` → **读不回该轮 → 路由 null → HARD_ERROR**（fix 结论 `APPROVED` 却渲 `CDD_BLOCKED: ... no next: line`）。**根因**：review 周期恒连续（1,2,3…）计数==身份；**fix 会跳号**（review-1 被 drift 作废 → 首个 fix 是**周期 2**、计数却是 **1**）→ 同一事实（fix 的周期号）**两处各派一份**（载体名 vs 计数）→ 分叉。**这正是 D26：一事实一处。**

  - **`#roundFor("fix") = reviews` 保留**——fix-K ⟷ review-K 配对不动（身份仍由 review 周期给）。
  - **迁移**：progress 是缓存、**载体名是实况源**（D26）→ 按现存 carrier 名重建周期号（W10：`review-1/-2` + `fix-2` ⇒ `{review:[1,2], fix:[2]}`）。

## Constraints

- **六前提（D23）**：允许破坏性变更、可重写代码重组目录、不保守不打补丁；从高维思考、OOP 抽象统一、零裸函数；最佳实践、零技术债务、避免散文堆砌、避免声明再抄；高内聚、低耦合、死代码空壳全清；消费者心智负担优先（不为完成任务而设计）；最大程度重构整合、最大程度精简系统
- **单一实况判定面（D26 · 统一命题）**：引擎对任一事实只持**一处实况源**，只在**判定时刻现读**；**派生副本永不具权威**（冻结 sha / 盘上 brief / 磁盘草稿 / argv 路径串 / 第二套 schema 裁决）——副本若为缓存必可失效重建，判定面永不读它。**校验器与 materialize 同源同判**（§8.7 · 对同一字段的处置永不背离）。**判定面 ⊥ 输入面**（§8.8 · D27）：引擎的 round 结论是派生事实，**不落 child 可读的载体**（findings 载体零 `status` · 结论判定时刻经单源 `conclusionOf` 现读）——引擎输出面永不污染 child 输入面。**round 身份单源**（§8.9 · D28）：round 的**周期号**（身份）一处记录（`progress` 记周期号集合），载体名 / `--findings` 路径 / 门控同源——fix-K ⟷ review-K 的配对永不分叉。本 phase 的 sha/brief/round/key/field/verdict/round-identity 诸处收口皆此一条法条的实例，非多条独立规则
- **保留面冻结**：clean-tree gate（review 基线 = committed tree）· doc_revision 内容指纹（doc sha1 · run.ts:551 · 最新计划 reopen gate —— 非 commit sha）· doc-contract 判定语义（gate 零例外）· base set/get 语义不变 · `WAVE`/`tasks`/`OUTPUT_REPORT`/`OUTPUT_HANDOFF`/`OUTPUT_EVIDENCE`/`INPUT_DOC`/`INPUT_FINDINGS` token 保留 · 六命令功能语义不变（除 review 面 ref 退役）· `mattpocock-skills` 分派表零动 · branch 线稳定键 `"branch"` 保留
- **引擎 vitest 全绿**（recon：五面测试套件 14 pin 文件 · deliberate 重锚 · 零跳过零容错）
- **child prompt 组装面一致性**——六 face prompt 的 shell 壳文与 round-context 布局必须逐 token 对齐（新壳文-布局一致性断言 · 复用 `#contextLines` 槽位 regex · 构造成立级 · 双 gap 零复发）
- **kairos 消费面字面同步**：cdd-dev/cdd-plan skill 文本 + 行为树 pins 随 engine 语义更替（consumer 环境无 monorepo 布局；消费面纯度：零程序史）
- **语言策略**：本 spec 为内部开发者文档（Strategy B · 中文）· 引擎源码/skill/发布面 English-primary 不变
- **skill ⇄ engine 黑盒边界（D29 · §8.10）**：**skill 层对引擎是消费者 · 引擎对 skill 是黑盒**——skill 文本只承载引擎的**行为契约**（唯一派发路径 · 后台派发读全量 · `next:` 即分派 · BLOCKED 携因上报），**零内部实现镜像**（类名 / 波次推导内部 / round-context 槽 token / 输出字节名 / 崩溃机制 + 失败分类学 / 会话旗标 / flag 逐 verb 复述 / skeleton 语法）。**派发纪律统一**：background 执行 + 等完成通知 = 全六 skill 公共纪律，`timeout + poll otherwise` 能力分支退役。**入口 bootstrap 例外**：每 flow 入口节点保留唯一字面命令。**pin 同步**：`skill-anatomy.test.ts` 的 `CDD_BLOCKED:` 断言改行为断言；`status-routing-convergence.test.ts` 的 `next:` 锚定保留（黑盒行为）
- **EOF**：仓库文本文件以且仅以一个换行符结尾（字节级）
- **不发布**（与 P1–P6 一致）
