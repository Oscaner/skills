## Design

引擎在 child 存在之前拒绝一次派发时，落下的是**另一种事实的形状**：`ledger` 记一条 `grade: hard`、`cause: contract-violation` 的轮记录，`board` 因此念 `crashed: review 1·a1 contract-violation`，而 `waves[n].rounds` 里那一轮的号被永久占用——重派读作 `review 2·1`，即「第 1 轮跑过并死了」。诊断因此指向一个从未存在的孩子：读 `contract-violation` 的人会去找孩子的 stdout 与 handoff，真相是 `base.json` 缺失。

病根不是判据错，是**归属错**。引擎有两个拒绝通道，各记各的账：pre-flight 的 `DispatchAuthority` structure 腿（`tree-clean` · `in-flight` · `graph` · `plan-ledger` · `doc-contract`）拒绝后零记录、零轮号；派发体里的四道门（no-host · carrier · dispatch-input · artifact）拒绝后记账成 crash。而后者自带注释——它们停在这个 round 的 in-flight 记录被获取**之前**——它们是 pre-flight 性质的，只是被放在了派发体里，于是恰好落在了记账之后。

本相位把那四道门搬回它们本来的位置，于是「一次没跑的派发写了一条轮的账」这件事**不可表达**：没有代码路径能到达它，而不是靠「记得在记账之前返回」。拒绝这件事随后落在它自己的名下：**树**的事实（这棵树此刻没能通过门前判定），与「这棵树正在跑」的 in-flight 事实同级、互斥、同寿。

### 1. 归属：两个拒绝通道并成一个

#### 1.1 四门成为 structure 腿的第 6–9 行
- structure 腿的行集是一张闭集：`session/preflight.ts#PreFlightGateName` 今天给五行（`tree-clean` · `in-flight` · `graph` · `plan-ledger` · `doc-contract`），`session/dispatch-authority.ts#DispatchAuthority.structureRefusal` 把拒绝的 gate 原样重述为腿的 reason。四道门并入为它的第 6–9 行，行 id 即拒绝的站名——no-host · carrier · dispatch-input · artifact。行集因此由五扩到九，而**站名闭集就是这张行集**（3.2）：站名不是与行并存的第二套词汇。
- 判定顺序：四行排在 `doc-contract` 之后。输入面是否合格，需先有合格的文档；一条判据的门槛若低于它依赖的判据，它给出的绿是空的。四行**同时排在 line 腿之前**：四道门今天在派发体里，跑在 `DispatchAuthority#verdict` 与循环的下一帧展望**之后**，并入结构腿之后它们跑在那两条**之前**。一条同时不合格的派发因此改念结构腿那一行——这是本相位的具名变更⑥（Constraints），不是被悄悄保留的旧序；line 腿的拒绝在九行通过之后照旧可达。**让位条件（唯一一处）**：四行判的是编排者欠的**输入面**，而一次预测批为空的 wave 派发没有输入面——`WAVE` 与 `INPUT_WAVE_BRIEF` 都是引擎从并不存在的开放前沿自己推出的值（`DispatchIdentity.tasks` 是空串），编排者无从供给，判它们的空值只会盖掉 line 腿的真答案（这棵 plan 没有可派的 wave：`split`）。四行因此**一起**让位：不判、不记 `checked:`、不参与拒绝归属，这条派发交回 line 腿；条件只有一条、住在一处（`session/preflight.ts#PreFlight#hasInputFace`），不是每道门自己判，也不是一张 per-face 表。
- 判定输入（值来源）：四格输入，不是一行一格（ArtifactCell 同时供 carrier 与 artifact 两行判定；`(cycle, attempt)` 是这条拒绝事实自己的身份，不是任何一行的输入），全部由装配好的派发输入推得，门自己去读场景不在其中——① `TemplateValues`（`INPUT_WAVE_BRIEF` 的路径值由 `session/round-naming.ts#RoundNaming` 的 `brief()` 命名，与 `--dry-run` 预览同一条推演）；② ArtifactCell（fix 面的 `--reviews` 路径与 requesting carrier 取自本行已记录的上游轮）；③ 将落的 `(cycle, attempt)`（同一命名面从 ledger 的下一轮参数渲染，合成点即 2.1 的 `session/ledger.ts#ConsumedRound#of`；记录的 `op` 同一来源见 2.1）；④ 主机探测事实（`no-host` 行的唯一输入，今天由 `face/lifecycle.ts#CliLifecycle#detectHost` 在 `#runDispatch` 顶部现算）。前三格是**只读推演**：不建相位工作区目录、不写 brief、不开本轮 carrier 名、不取 in-flight 记录。第四格是 composition root 填进 `PreFlightContext` 的**已判事实**（一个值，不是一次调用）：seam 读事实，绝不 import face 的 host 模块——否则这条接缝在落地第一天就破了本程序要立的 plane 方向（P39）。那份事实在**派发路径上**只探一次，且**读者逐一点名**——否则「只探一次」是一句核不动的话：composition root 探一次，把值交给三处：（a）`PreFlightContext`（no-host 行），（b）lifecycle 的 spawn（念 `HOSTS[值]`，不再二次探测），（c）`face/preview.ts#Preview` 的 `child:` 行（构造器收值）。**划界**：这句只覆盖派发主机事实，不覆盖 `src-next` 里全部 `HostDetect.detect` 读取——派发路径之外另有三处（`face/gate.ts#CliGate` 的 `#renderer`（`next:` 路由渲染器）· `face/cli.ts#Cli#runBoard` · `face/cli.ts#Cli#runWork` 的 `Capsule`），它们读的是各自面的主机拼写，不是这一格；本相位不动它们，1.3 与验收的源码断言都按这条分界读。判词（包括 no-host 的措辞）住在 seam 读取的词表里（`face/words.ts`），第二份拷贝不是「并存的实现」，而是会漂移的重复。发布命名空间的 keep-out 标记（`infra/workspace.ts#WorkspaceRoot#ensure`，见 2.2）不算「建工作区」：它只写 `<repoRoot>/.kairos/.gitignore` 与 `.kairos/cdd/`，不建 `<slug>` 目录、不写 brief。
- 判定点不后移（条件）：门必须在轮记录被写之前、也在 `--recover` 的接管判定之前给出结构腿的裁决（4.1）。把工作区创建或 brief 渲染提到门之前，会让一条被拒的派发留下工作区与 brief，并让接管判定先于拒绝读到一条陈旧的持有者——两条都是本相位要消除的形状。因此 `PreFlightContext` 多收这些输入格，而不是门自己去读场景。
- 复用既有值类型与适配器，不新增：`DispatchRefusal`（`leg` 仍取 `structure`）与 `DispatchAuthority.structureRefusal`。`DispatchLeg` 的三值闭集不动——分腿的依据是**问题不同**（树是否就绪 / 上游面是否到达 / 这一行在哪），不是代码放在哪。
- `checked:` 面随门增长：`session/preflight.ts#PreFlight#vet` 把每跑过的门同时压进 `gates` 与 `checked`，`face/cli.ts#Cli#renderChecked` 把这份清单印出来——四行一起并入，一次 approved 派发的 `checked:` 块就多出对应行，按**同一把尺**计：一行印出的条件是**它的门跑过**，不是它判到了东西——四道门在每一个**有输入面**的派发上都被调用（无输入面的派发四行一起让位，见上一条），`carrier` 与 `artifact` 在非 fix 面上以空格短路返回 null（没有可比的 carrier、没有可读的 sidecar），那仍是一次跑过的判定，因此四行都记 always，没有 fix-only 这一档；哪一面日后真的**不调用**某道门，那一行才按面名声明并写明理由。既有 `checked:` 的钉读字节（`face/__tests__/cli.test.ts` 的 approved 路径块）因此移动；这是具名变更，与三行站名前缀同批登记（Constraints · 验收 · changeset）。
- 判定本体里唯一被本相位改动的一格是 `INPUT_WAVE_BRIEF`，且这条改动是具名的：门要判的是**编排者欠的输入**，不是**引擎自己要写的产物**——brief 的路径名就是这一格的完整答案，而那个文件由引擎在 child 读它之前自己渲染（`face/gate.ts#CliGate#renderBrief`，调用点在 `face/cli.ts#Cli#runWork`，在门之后、`scene.workspace.ensure()` 之后）。因此这一格在声明面上改成它真实的意思：**引擎写的**（新声明字段 written: "engine"，裸词：本相位新建，落地前不构成 pin 坐标），释义只有一条——引擎保证该文件存在，因此**任何**路径都不做存在性读。作用面是**该格的每一处声明**，不是一行：`render/templates.ts` 的 `TEMPLATE_PROMPT` 把 `INPUT_WAVE_BRIEF` 声明三次——implement 行（`requiredOn: always`）、review 行与 fix 行（各 `requiredOn: [wave]`）——三处一起由 `preview: "satisfied"` 改为引擎写；只改一处，另两行就留着一个没有判定读的字段（判定看的是同一格，声明表却给出两个意思）。
  随之：face/lifecycle.ts#CliLifecycle#inputRefusalOf 的 `mode === "preview"` 守卫与 face/lifecycle.ts#CliLifecycle#answeredByNaming 的 `decl.preview !== "satisfied"` 守卫一并消失（只剩「这一格是不是命名行写的那一格」的 token 守卫），inputRefusal 的 `mode` 参数退场。`TemplateAssembler` 的构造期断言保留并换判据，换成一条不变量：**凡声明为引擎写的格子必须是 `NAMED_BRIEF_CELL`**，按**槽**判——一个槽在一处被断言，三行声明同一槽不构成三格，而「另一格也称引擎写」是构造期红。
  这条与「判定点不后移」不冲突：门仍在 brief 渲染之前，判的不是文件在不在，而是编排者有没有欠它的名字；于是 P38 §2.4 在这一格上的 per-mode 例外作废，同帧镜像规则收紧成「两面对同一帧报出逐字节相同的拒绝串」。**这条作废不在本相位的自裁范围内**——它退的是 P38 交付的判据一格，因此同批回填章程（D96 与 Phase inventory P40 的非目标从「改门判据（P38 交付）」收窄为「四门判什么不变；这一格的模式豁免按本轮登记改为引擎写」，行为在册增量按 Constraints 的具名变更①–⑥ 逐项补齐（站名前缀 · `--dry-run` 上的入口与流 · 无 harness 树里 `--dry-run` 的 `exit 0 → exit 1` · 有输入面的派发上 `checked:` 面的新增行 · board 的两行 · 两腿同时不合格时的报文归属——六项，与 Constraints 是同一份清单，本节不另立一条），并在 P38 的 spec 上追加一条**换向记录**指向本相位：历史行不改，指向不重写。
- 门判据本体不动（唯一例外是上一条的 `INPUT_WAVE_BRIEF` 一格）：`dispatch-input` 的判据（`requiredOn` 与 `absent` 两维声明、`when` 臂、四态渲染）由 P38 交付且正确；本相位只改它被判定的位置与失败后的归属。

#### 1.2 拒绝在轮记录被写之前返回
- 轮记录的写入点是 `session/ledger.ts#Ledger#recordRound`，经 `session/run.ts` 的无条件记账。structure 腿的拒绝发生在它之前，因此一条被拒的派发**不产生** `RoundRecord`：无 crash 记录、`cycle` 不推进、`attempt` 不递增、`waves[n].rounds` 长度不变。
- 条件而非快照：本相位之后，任何 pre-flight 拒绝都不得让 `recordRound` 被调用一次。可核方式是「拒绝后 `waves[n].rounds` 长度与拒绝前相等」，不是「今天恰好没写」。

#### 1.3 carrier 开名挪到门之后
- 今天派发体的 pre-flight 半程先开本轮的两个 carrier 名，四门里的**三道**（carrier · dispatch-input · artifact）拒绝时调 `face/lifecycle.ts#CliLifecycle#sealRoundCarriers` 封回。no-host 是第四道却站在例外一侧：它在 `face/lifecycle.ts#CliLifecycle` 的 `#runDispatch` 顶部返回，早于开名，从不封回。门前移后，四道拒绝都发生在开名之前，封回这一步因此从拒绝路径上消失。
- 条件：拒绝路径不得留下「已开名、未封」的 carrier；由于开名在门之后，这条由顺序保证，不再由一次补封保证。
- 同一批退役：`#runDispatch` 顶部那次 detectHost() 调用、它那个提前 return 与它印的 no-host 字面（`CDD_BLOCKED: no host harness detected …`，`face/lifecycle.ts`）——门挪到 seam 之后，那里已无判定可做；留下它是同一件事实判两次，而死掉的字面会与词表里的活措辞各说各话。措辞搬进 seam 已经收到的那张词表（`face/words.ts`），`PreFlightContext` 只收值。同批还有 `face/preview.ts#Preview` 的 `child:` 行：它今天在构造期自己探一次主机（`HostDetect.detect`），并在空值上印 `(no host detected — real run would BLOCK)`。探一次之后那份事实作为值从 composition root 同时交给 `Preview` 的构造器与 lifecycle 的构造器（spawn 念 `HOSTS[值]`，没有第二处 detectHost()），于是 `child:` 行直读那张表；no-harness 树里结构腿先拒、`#render` 从此不可达，那句字面与钉它的那条测试一并退役——留着它等于宣称「五行预报仍覆盖无 harness 的树」，而那张表只预报能过门的树。生产代码里因此只剩**派发路径上的一次**探测——CliLifecycle#detectHost 这个只被 `#runDispatch` 调用的适配方法随它的唯一调用点一并退役（钉它的那条测试同批退），留一个无调用者的方法就是留一条能被复用的第二探测路径。派发路径之外的读取照旧各读一次（`face/gate.ts#CliGate` 的 `#renderer` · `face/cli.ts#Cli#runBoard` · `face/cli.ts#Cli#runWork` 的 `Capsule`）：它们拼的是各自面的主机词面，不是这条派发事实，因此「全树恰好一次」不是本相位的断言（1.1 的划界）。

### 2. 事实：一条树级拒绝记录

#### 2.1 形状与位置
- 位置：工作区根的 `.kairos/cdd/` 下，`in-flight.json` 的邻居，文件名 refusal.json（裸词：本相位新建，落地前不构成 pin 坐标）。
- 形状：一条记录对象，字段为 `at`（写入时刻）· `slug`（相位工作区名）· `op`（`implement` / `review` / `fix`——九行记录的 `op` 一律取**这次派发本将消费的那一轮**：`face/cli.ts#Cli#runWork` 在裁决之前就已算出的那个 `expected` 相位（`verb` 是 `implement` / `fix` 时即该动词，其余面取本面的 `reviewLead`），**不是任何已开的帧**——pre-flight 点上还没有帧，2.4 也不许为一个拒绝造第二个帧源；`(cycle, attempt)` 两格取 `session/ledger.ts#ConsumedRound#of`——implement 恒取 1、fix 取上游 review-lead 最近一条**已完成**轮的 cycle、其余面取下一轮，两格都按 `--recover` 折叠后的记录切片算，也就是会话帧在 `#roundFor` 里读到的同一对值；不各自从半截来源拼，也没有任何行自造身份规则）· `type`（面）· `cycle` · `attempt` · `station`（闭集，见 3.2）· `detail`（站内原因，自由文本，**不以站名开头**——站名已由这一行自己印出，串首再重复一遍就是同一事实说两次；站名出现在句子中间不在本相位可改的范围：`face/words.ts#CAPSULE_WORDS` 的 `inFlight.corruptLocked` / `corruptUnlocked` / `lockOnly` 三条措辞把 `in-flight` 写在句中，而措辞按章程非目标冻结）。八格就是全部，没有第九格，也没有第二个名字：`detail` 是这一格在章程、本相位与 board 行里唯一的名（站内原因，自由文本）。
- `detail` 是**派生的单行**：写入时取 seam 那一刻判词的**首行**、剥掉它已印出的串首站名（dispatch-input 门的报文以它自己的站名开头，剥后 `detail` 从 `review · INPUT_OVERALL · target-absent` 起算；carrier 门的 `carrier-mismatch` 与 artifact 门的 `artifact-identity` **不是站名**——3.2 已把它们判为这两道门的原因词面——因此留在 `detail` 里），行内换行折叠为空格，` · ` 视作行内分隔符而非第二个 token。判词的**后续行**（`derived:` · `found:` · `identity:` · `repair:`——artifact 门的四段修法报告就在其中——以及一条次行的 detail，见下一条）**不进文件**：它们陈述的是这次拒绝没做的事（或第二条判定的正文），属活判词，不属于这棵树的持久事实。
- 多行同时失败：四行**一趟判完、不短路**（`contract/preflight-rows.ts#PreFlightRows#judge` 交出全部失败行），行序即 tie-break——`PreFlightGateName` 里排在前的第一条失败行拥有 `gate` 与 `message`，**也拥有记录的两格** `station` / `detail`；其余各行随 `details` 逐行原样印出（`session/preflight.ts#PreFlight#vet`），各自以本行的 detail 起算、不再补站名头。因此一次两行失败的派发先念首行那一句，再跟次行自己的 detail 作为续行，记录里只有首行的站名与原因；次行的正文因此是 §3.3 后续行清单里的**第二类**——它不是 `derived:` · `found:` · `identity:` · `repair:` 那种同一条判定的后续段，而是第二条判定的正文（它若以 `dispatch-input · …` 开头，那是该行词面自己带的站名，与首行那种补回的头是两件事）。
- 两个值，三个消费者：seam 的**活判词**是一条多行报文，首行已是 `station · detail`，后续行原样跟随——命令面与预览面逐字渲染这一条；记录的**对**（`station` + 单行 `detail`）由 board 渲染。一次已声明的派生（活判词首行 → 记录的两格），没有第二处拼装，也没有 per-face 抑制规则（3.3）。站名只在一处**补回**：四行的 `PreFlightVerdict.message` 是**剥掉站名的余下部分**（`dispatch-input` 的词面 `face/words.ts#CAPSULE_WORDS` 的 `dispatchInput` 行本身仍以它自己的站名开头——那张词面不改，站名在装配判词时剥掉），`DispatchAuthority#message` 是把 `station · ` 放回串首的**唯一**位置。于是命令面与预览面念的是同一条值（`message()` 的首行），而 `dispatch-input` 的命令行与预览行都与今天逐字节相同：既不会「站名重复一次」，也不会「预览行丢掉 `dispatch-input` 这个头」。
- 归属类：一个新类 tree-refusal，住在 session/refusal.ts（两者都是裸词：本相位新建，落地前不构成 pin 坐标），与 `InFlight`（`session/inflight.ts`）同构——一条记录、一次原子写、一个 `inspect` 式的状态读——守「一棵树任一时刻最多一条拒绝事实」。它不持有轮的状态，也不参与轮的任何判定；写入与清除都是别的面的动作（2.2），它只交出事实的读写与那一行（`station · detail`，3.1 · 3.3）。
- 名字进 `round-artifacts.ts` 的拼写矩阵，与 `in-flight` 行并列——矩阵是名字的唯一语法，不在矩阵里的名字对清扫与判定都是隐形的。

#### 2.2 生命周期：一条，两个到期触发点
- 写入：**任一** structure 腿拒绝时覆盖写入——九行一视同仁，不留豁免。`tree-clean` · `in-flight` · `graph` · `plan-ledger` · `doc-contract` 的拒绝与四道门的拒绝同样写：本相位要治的正是「一次拒绝不留痕」，而「只让迁移过来的四行写」是给旧行开的豁免层（Constraints 禁止）。
- 写入点：**门口，不是门里**——`face/cli.ts#Cli#runWork` 拿到 `DispatchAuthority#verdict` 的结构腿拒绝、在 `#renderPreflightBlocked` 之前写；**不**写在 `session/preflight.ts` 的门里。理由是可判的，不是风格：同一个门由真派发与 `--dry-run` 共用（预览那一支问的就是同一批判定），写进门里会让每次预览拒绝都落盘、每次预览通过都清除，直接与 2.4 的「不写、不清」和验收⑤的零写入相反。
- 写入的顺序与 `InFlight` 同一条：先发布命名空间的 keep-out 标记（`infra/workspace.ts#WorkspaceRoot#ensure` 写 `<repoRoot>/.kairos/.gitignore` = `*` 与 `.kairos/cdd/`），再做原子写。理由是一条拒绝的前置条件：它是唯一跑在 `scene.workspace.ensure()` 之前的路径，没有这条，一次拒绝就会成为某棵树的第一个 `.kairos` 条目；而 `infra/git.ts#GitClient#isClean` 读 git 自己的判断、零引擎侧排除，untracked 的 `.kairos/` 立刻弄脏这棵树——下一次派发被 `tree-clean` 拒并覆盖同一份记录，这棵树从此为引擎自己的一个文件拒绝每一次派发。发布标记不是「建工作区」（1.1）：不建 `<slug>` 目录、不写 brief。
- 清除：**与写入同一个门口、同一个谓词、同一个模式守卫**——`face/cli.ts#Cli#runWork` 在 `session/preflight.ts#PreFlight#vet` 返回之后、`--recover` 的接管判定之前，`!parsed.dryRun && this.#authority.structureRefusal(preflight) === null` 时清除。逐条说清为什么不能晚到派发体：`face/lifecycle.ts#CliLifecycle` 的 `#runDispatch` 只在**整条**裁决通过后被调用，而整条裁决在结构腿之后还有 line 腿——一棵九行全过、随即被 line 腿拒掉的树若等到派发体才清，board 就会继续念一句已经不成立的话（`refused: …` 说这棵树没过门，而它过了）。因此写者与清者同住门口，各占结构腿的一支：写入在结构腿拒绝的那一支（接管判定被那条拒绝挡下，两者不重叠），清除在结构腿通过的这一支。同样不在门里清：预览共用同一批门，而清除本身是一次写——`!parsed.dryRun` 这一个守卫同时管住两侧（2.4）。
- 第二个到期触发点：**派发体的释放点**——`session/inflight.ts#InFlight#release` 的唯一调用点（`face/lifecycle.ts#CliLifecycle` 的派发体，紧接 `#reconstruct` 之后），持有解除处清除。理由与上一条同样可判：一条记录陈述的是「这棵树**此刻**未通过门前判定」，而「树被占」（`in-flight`，腿的第 2 行）正是最常见的拒绝原因之一；持有者一释放，这句话就不成立，而凭它写下的那条记录会让 board 在同一张板上同时念 `in-flight: free — no dispatch holds this tree` 与 `refused: … in-flight · …`。这一处**不是**把门口的清除挪进派发体：门口那次按整条结构腿判（九行全过、随即被 line 腿拒掉的那一次仍必须在门口清，见上一条），释放点只收回它自己那次持有带来的树状态。释放点的清除带一个谓词：**只清 `station` 为 `in-flight` 的那条**——释放唯一会证伪的树事实就是「这棵树正在被占」，其余站名的记录它管不着：持有者运行期间任何并发派发都被门口拒下（九行全过才进得了派发体），其中一次 `tree-clean` 拒绝写下的记录陈述的是「树此刻是脏的」，持有者释放并不让这句话变假——它要站到下一次派发通过结构腿、在门口被清为止（上一条）。记录不可读时释放点**不动它**：谓词要读 `station`，而 `session/refusal.ts#PreFlightRefusal#readRaw` 的第三态是 `corrupt`（没有 facts），谓词无从成立，§4.2 也不许静默吞掉一条拒绝——那一条站到下一次结构腿通过、在门口被清为止（上一条）。所以这里不是「有记录就清，无条件」：释放点不是豁免层（「不留豁免层」管的是拒绝路径，每一条结构腿拒绝都照样写事实），它只是陈述了站着的各站记录里，哪一站的寿命由释放终结。
- 两处触发点各管一次树的状态变动：结构腿通过（门前判定被证明通过）与持有解除（树的占用状态改变）。因此一条记录的寿命不超过它所陈述的那次树状态。
- 边界（**具名**，不是遗漏）：引擎只在它自己跑的时候观测这棵树。两次调用之间由作者 commit 掉一条 `tree-clean` 拒绝的成因，那条记录会站到下一次派发真正通过结构腿为止（门口的清除点）——本相位不给它造第三条触发点：一次开命令即做的树状态重判会让 board 成为第二个判官，而判据面属于 pre-flight（P21 · P35）。所以语义句读作「**引擎最近一次判定时**这棵树未通过门前判定」：门一过、或写下它的那次持有被释放，这句话就不成立。
- 因此任一时刻最多一条，且**不留下历史**。拒绝的历史在命令输出里逐次可见（每条拒绝行都把自己的站名印在第一个位置，行外层按 3.3 的通道归属），轮的历史在 `rounds` 里（拒绝不在其中）。第三个历史源是禁止的：它会与 `rounds` 永不同步。

#### 2.3 不变量：最多一条 · 两个到期触发点
- 三条可核不变量：① 任一时刻最多一条拒绝事实（覆盖写入 + 两个到期触发点共同保证）；② 一次结构腿九行全过、真跑（非 `--dry-run`）的派发之后，拒绝事实不存在——**含**九行全过、随即被 line 腿拒掉的那一次（清除在门口已经发生，不等派发体，2.2）；③ 一次持有 in-flight 的派发**正常结束（释放）**之后，不存在以 `in-flight` 为站名的拒绝事实——`in-flight: free` 与 `refused: … in-flight · …` 不得同时在场（释放点的清除，2.2）。
- refused 行与 `in-flight:` 行**可以并存**，且不构成矛盾：`in-flight` 门就是腿的第 2 行，「树正在跑」正是一棵树此刻被拒的合法原因之一。把两者说成互斥，会让「因为正在跑而被拒」这条最常见的拒绝无法同时陈述两个事实。
- 方向仍然成立，只是换成两个到期点：拒绝后跑一次合法派发 ⇒ 拒绝事实消失、`in-flight:` 出现；该派发正常结束 ⇒ `in-flight:` 消失，拒绝事实不因结束而出现（除非真的又被拒了一次）；而拒绝若是在某次持有期间写下的，那次持有释放时它一并消失（释放点的清除是唯一一个不经过门的到期触发点）。

#### 2.4 预览：镜像判定，不写不清
- `--dry-run` 走同一批门前判定（P38 §2.3 的镜像规则），渲染「如果你真跑，会在这里被拒」，但**不写、不清**拒绝事实：预览不是一次派发，无权宣布这棵树通过了门，也无权覆盖一条真实拒绝。
- 入口收成一个：结构腿拒绝在 `--dry-run` 上**一律由 preview 面陈述**，不再分「哪个渲染器」。今天的分岔就在 `face/cli.ts#Cli#runWork` 的 `verdict.leg === "structure"` 那一支——`in-flight` 且带 `holding` 事实的拒绝（`session/preflight.ts#PreFlightVerdict` 的 `holding`，活主 · 死主 · 锁在盘上的不可读记录三种形状都带它）走 `Preview#heldBlock`，其余全走 `#renderPreflightBlocked`；本相位之后这一支在 `--dry-run` 上只留一个出口，覆盖整条腿而不止迁移过来的四行。
- 形状与**帧来源**：结构腿拒绝发生在 `OpenFrame` 存在之前——帧出自 `session/run.ts#Lifecycle` 的 `peekNext()`（公开访问器，`run` 构造之后、派发循环内以 `run.peekNext()` 调用），而 `run` 在裁决通过之后才构造，pre-flight 点上没有任何帧可借。因此预览的拒绝块**不是**五行的预报，而是 `Preview#artifactBlock` 今天已有的那一形：`cdd <verb>: preview (no repo changes)` 头 + 一行 `  refused:  <station · detail>`（活判词的首行）+ 报文自己的后续行（artifact 门的四段修法报告就在这些后续行里），再跟 seam 自己的 details 行与 `#renderChecked` 的 checked 面。本相位不为一条拒绝造第二个帧源，也不为它重算一帧。
- 循环里镜像的退役：派发循环的 `--dry-run` 臂今天自带一份三门镜像（`carrierRefusal` → inputRefusal(frame, "preview") → artifactRefusal，随后渲染 `Preview#artifactBlock`）——判定既已收归门口一处，循环里再问一次就是第二个判官，这份镜像**退役**：该臂收窄为只渲染五行预报，循环侧 `Preview` 的构造改收 §1.1(c) 注入的主机值（不再自探）。镜像里的 inputRefusal(frame, "preview") 调用也随 `mode` 参数的退场（1.1）而不可能按原样存活。
- 流与随行行：拒绝块与 checked 面都走 **stdout**（`--dry-run` 的 checked 面今天在活主臂上就是这样走的——同一写作器），因此旧五行在 `--dry-run` 上的拒绝从 stderr 的 `CDD_BLOCKED:` 行改成 stdout 的预览块；details 行与 checked 面**保留**（「哪些门跑过」是既有生产读面，P21 §3.4 的两路径规则不因入口合并而破）。这是本相位对 `--dry-run` 面的具名变更，验收有对应对。
- 唯一保留自有形状的臂：**`in-flight` 且带有 `holding` 事实的拒绝**——判据是 `face/cli.ts#Cli#runWork` 今天测的那个条件（`session/preflight.ts#PreFlightVerdict` 上有没有 `holding`），不是「持有者活着」：`session/preflight.ts#PreFlight#vet` 给三种 `in-flight` 拒绝都带上它（活主 · 死主 · 锁在盘上的不可读记录），而 `--recover` 在预览里不改变这一支（`face/cli.ts#Cli#runWork` 的 `recover` 由 `!parsed.dryRun && …` 推出，`--dry-run` 上恒为 false，因此 `--recover --dry-run` 照样停在这道门上）。三种形状今天都走 `Preview#heldBlock`（`lock:` 行 + 接管提示，**没有** `refused:` 行），本相位不动——那一臂陈述的是一个持有者的事实，不是一个站名；把它折进 `refused:` 块会替换一个既有面，而本相位没有换它的理由。
- 预览的 `refused:` 行保持自己的既有形状（`  refused:  ` 两空格 + 内容，无轮标识），payload 是 seam 的活判词（首行即 `station · detail`，后续行原样跟随——2.1 已声明后续行不进记录）：`dispatch-input` 与五行既有报文因此与今天逐字节相同，`no-host` · `carrier` · `artifact` 三行的首行多一段站名前缀（3.3 的具名变更），后续行不动。board 念的是记录派生的那一行，没有后续行（3.1）。
- no-host 上的第二个具名后果：它在预览的预报里今天没有自己的格（3.1），因为它在 `#runDispatch` 顶部返回、不在门里；门一前移它就成了一道门，于是**没有 harness 的树里 `--dry-run` 从「五行预报 + exit 0」变成「预览块 + exit 1」**。树内有 harness 的 `--dry-run` 仍旧预报、仍旧 exit 0。验收成对断言这两个面。

### 3. 露面：board 的一行与命令的一行

#### 3.1 board 行：复用 preview 已经说出的那个词

- 词不是本相位新造的。`Preview.artifactBlock` 今天已经在为**同一批门**渲染一条 `refused:  <原因>` 行——预览说「如果你真跑，会在这里被拒」。这里要说清「同一批」是几道：预览镜像的是 **carrier · dispatch-input · artifact 三道**；no-host 没有它的预览格（它在 `face/lifecycle.ts#CliLifecycle` 的 `#runDispatch` 顶部返回，预览的预报里没有这一格）；`--dry-run` 上它照样以 `refused:` 行露面（2.4，且在无 harness 的树里就是拒绝本身，exit 1），只是没有一行预报可镜像。board 要加的是**同一个词在持久面上的那一份**：**同词**，不是同形——两个面共用词面与**那一行**（`station · detail`，3.3；预览念活判词的首行，board 念记录派生的那一行），行内排布各按自己已声明的形状（预览是 `  refused:  ` 两空格、无轮标识；board 是树级事实块之后的独立一行、带轮标识）。新造一个词反而会让两个面各说各话。
- 位置：树级事实块的块尾——`face/board-view.ts#BoardView#inFlightRows` 一次落完 `in-flight:` · `orphan:` · `crashed:` 三行，`BoardView#refusalRows` 排在其后，块尾即 `refused:` 行的位置（块里没有 `orphan:` 与 `crashed:` 时它紧跟 `in-flight:` 之后）。位置只在此处陈述一次，验收按整块顺序断言。
- 形状：

```text
  refused: {op} {cycle}·a{attempt} {station} · {detail}
```

- 为什么这一行可以直接含 ` · `：这一行只有**一个轮标识**（`{cycle}·a{attempt}`），`station` 取自九值闭集、永远先于第一个 ` · ` 出现，因此行内的 ` · ` 只是「站名 / 原因」与原因自身片段之间的分隔；`crashed:` 的 ` · ` 是**跨轮**分隔符（多个 token 之间），两者的活儿不同。行也不靠切分解析：站名从闭集取，`detail` 是剥掉站名与规范化（2.1）之后剩下的部分。
- 构造点：两个值、三个消费者，各自说清念哪个。`session/dispatch-authority.ts#DispatchAuthority#message` 在结构腿今天做的就是 `reason · detail` 这件事，而结构腿的 reason 就是行 id；本相位让它念的 reason 与记录里的 `station` 是同一个值。**值一 · 活判词**：`DispatchAuthority#message` 产出的那条多行报文，首行即 `station · detail`，后续行（`derived:` · `found:` · `identity:` · `repair:`）原样跟随——命令面的 `CDD_BLOCKED:` 行与预览的 `refused:` 行渲染这一条，逐字，不改写、不折叠：它们判的是一次活派发，后续行描述的是那次判定没做的工作。**值二 · 记录的对**：tree-refusal 存的两格（`station` + 单行 `detail`，2.1 由活判词首行剥掉前缀派生），board 念这一对。三个面各自只加自己的**外层**（命令面的 `CDD_BLOCKED: …`——`graph` · `plan-ledger` 两行另有 `cdd <verb>: …` 一支，通道归属见 3.3 / 预览的 `  refused:  ` / board 的 `  refused: {op} {cycle}·a{attempt} `）。一份存储、一次派生、三个外层；记录里没有第二份报文，活判词不进文件。
- 渲染归属：board 只在拒绝事实的 `slug` 与本次观察的工作区相同时渲染它。别的相位工作区的拒绝不是本次观察对象——但它在自己的 board 上照常可见，且被下一次写入覆盖即消失。读取点就在渲染 `in-flight:` 行的同一处（`face/board-view.ts`），不新开第二次扫描。

#### 3.2 站名闭集与穷尽断言
- 站名闭集就是 structure 腿的行集，九值一张表（`session/preflight.ts#PreFlightGateName`）：

```text
tree-clean · in-flight · graph · plan-ledger · doc-contract · no-host · carrier · dispatch-input · artifact
```

- 后四个里只有 dispatch-input 已成词，且它是 `face/words.ts#CAPSULE_WORDS` 的 `dispatchInput.station`（拒绝行的行首，不是 `stations` 那张前缀表——那张表是 `next` · `reason` · `blocked` · `warn` · `cliMissing` 的行首锚）；no-host · carrier · artifact 是本相位新立的判别值，落地前不构成 pin 坐标。`carrier` 是站名，报文里的 `carrier-mismatch` 是这道门的原因词面，不是第二个站名。
- 一条编译期断言守它，且只守站名这一半：structure 腿的每一行都必须给得出**闭集内的站名**——`session/dispatch-authority.ts#DispatchAuthority#structureRefusal` 把 `preflight.gate` 原样当作 `reason` 交回（`reason` 的类型是 `DispatchReason`），而 `session/next.ts#DISPATCH_REASON` 的 `leg: "structure"` 行就是那九个站名，于是**站名不在那张表里就不通过类型检查**；`session/__tests__/preflight-rows.test.ts` 的 "maps the nine station words onto the reason table's structure rows" 把九值逐字对表。另一半**没有守卫**：`contract/preflight-rows.ts#PreFlightRows#judge` 是一串顺序分支、`RowWording` 的行各占自己的格，往 `RowStation` 里添一个成员而不给判定分支与措辞，今天编译通过、全部测试照绿，那一行于是永不拒绝——detail 来源是评审读的一件事，不是构造期红。新增站名因此仍触发一次有意识的决定（站名进 `DISPATCH_REASON` 是那处编译期红），只是它不被说成「连 detail 来源一起红」。

#### 3.3 一行共享，三个面各自的外层
- 先改正一处事实：`face/cli.ts#Cli#renderPreflightBlocked` 今天念的**就是** `<站名> · <报文>`。它的插值来自 `session/dispatch-authority.ts#DispatchAuthority#message`，后者在结构腿上返回 `<reason> · <detail>`，而结构腿的 reason 正是拒绝的行 id（`structureRefusal` 把 `preflight.gate` 原样重述）。两个分支的差别只在**行外层**，而某个站名走哪一支由 `face/cli.ts#Cli#renderPreflightBlocked` 的 gate 名条件唯一决定——通道归属的家就是那里，与 3.2 给站名闭集的家是同一种写法。九行逐站写清：`CDD_BLOCKED: …`（`Words#station` 的 blocked 行首）是 `tree-clean` · `in-flight` · `doc-contract` **与四条迁移行** `no-host` · `carrier` · `dispatch-input` · `artifact`；`cdd <verb>: …` 是 `graph` · `plan-ledger` 两行。因此加行的动作有两处、缺一即错：在 `session/preflight.ts#PreFlightGateName` 上添行，同时在那个 gate 名条件里添同一个名字——漏掉第二处，`dispatch-input` 的拒绝就会落到 `cdd <verb>: dispatch-input · …` 上，而验收钉的是 `CDD_BLOCKED: dispatch-input · …` 的字节。因此「这一支不带站名」是错的——站名今天就在第一个位置（`CDD_BLOCKED: tree-clean · the working tree is dirty …`），`session/__tests__/dispatch-authority.test.ts` 与 `face/__tests__/cli.test.ts` 各有一枚 pin 钉着这个字节。
- 合成规则：记录只存两格（`station` + `detail`，2.1），三个面**共享的是那一行** `station · detail`——命令面的 `CDD_BLOCKED:` 行与预览的 `refused:` 行念在活判词的首行（后续行原样跟随——同一条判定的 `derived:` · `found:` · `identity:` · `repair:` 与一次多行失败时次行自己的 detail 都原样跟随，不补站名头），board 的 `refused:` 行念记录派生的那一行。共享的是行，不是整条 payload：board 因此从不印后续行，命令面与预览也从不缺少它。没有 per-face 抑制规则，也没有第二份报文来源。旧稿曾想让三行「不带站名」，那需要一条「报文已自带身份就抑制前缀」的判定，而这条判定在 dispatch-input 上无法同时满足两个面：它带站名的串会与命令行重复，它不带站名的串会从预览那一行里丢掉 `dispatch-input` 这个头。站名因此只在一处补回（2.1）：`PreFlightVerdict.message` 是剥掉站名的余下部分，`DispatchAuthority#message` 再把它放回串首——三个面念的仍是那一行，而不是各拼一份。
- 字节账（**具名变更**，与 changeset 同批）：
  - `dispatch-input`：今天的报文以它自己的站名开头，`station · detail` 逐字节复现 `CDD_BLOCKED: dispatch-input · review · INPUT_OVERALL · target-absent`，预览的 `  refused:  dispatch-input · …` 同样不变。
  - 五行既有行（`tree-clean` · `in-flight` · `graph` · `plan-ledger` · `doc-contract`）：今天已是 `station · detail`，逐字节不变。
  - `no-host` · `carrier` · `artifact`：今天念的是不带站名的句子，合成后**多一段站名前缀**——`CDD_BLOCKED: no-host · no host harness detected (run cdd from within a supported harness)` · `CDD_BLOCKED: carrier · carrier-mismatch · line=… · recorded=… · current=…` · `CDD_BLOCKED: artifact · artifact-identity · …`；预览的 `refused:` 行同步多这一段。**detail 的文本一个字不改**（措辞不动），改的只是行首多了它自己的站名。代价换来的是：一行共享、零抑制规则、`carrier` 与 `artifact` 两条不同的修法在输出里可分辨；记录因此不必存一段多行报文，也不会在两个面之间各派一份。
- 与章程的关系：章程的非目标是「改 `CDD_BLOCKED` 报文**措辞**」——本相位不改任何一句措辞，只在三行行首补站名，那条非目标因此不是「字节不变」的承诺。这条变更按章程同批登记为在册增量（D96 与 Phase inventory 的同句），验收里写成对（改前三行不带站名 · 改后带）。
- 三个面各守自己的外层：命令面的 `CDD_BLOCKED: `（`graph` · `plan-ledger` 两行走 `cdd <verb>: …`，通道归属见上） / 预览的 `  refused:  ` / board 的 `  refused: {op} {cycle}·a{attempt} `。外层不是那一行的一部分——把外层也并进一处，board 就会印出 `CDD_BLOCKED:`，预览就会印出轮标识。消费面的守恒因此逐项：五行既有行 + `dispatch-input` 一行逐字节不变；`no-host` · `carrier` · `artifact` 三行的首行加前缀、后续行不动；`--dry-run` 上的整条腿改由预览面陈述（2.4），含无 harness 时的 exit 1；`checked:` 面在每个有输入面的派发上多四行（1.1：四道门在每一个有输入面的派发上都跑，故一律 always；预测批为空的 wave 派发是唯一例外，那里四行一起让位、`checked:` 不带它们）；board 多两行（`refused:` 行 3.1 · 不可读记录的 corrupt 行 4.2）；两腿同时不合格时的报文从 line 腿改归结构腿（Constraints ⑥）。

### 4. 边界

#### 4.1 明确不动
- `RoundStatus` 五值闭集不动：它是**孩子结论**的词汇，五个值住在 `session/ledger.ts#RoundStatus`（镜像 `face/words.ts` 的 status 行）；`session/handoff-schema.ts` 的孩子 enum 只有两值（APPROVED / BLOCKED），是另一件事——它管「孩子能写什么」，不承载这五个值。「孩子说不出被拒」的判据取前者，孩子 enum 不因本相位动一格。
- `RoundRecord` 不加字段：拒绝不是轮的事实，加字段等于承认它住在这里。
- `CrashCause` 与 `RoundViolation` 的 grade 轴不动：前者是孩子之死的词汇；后者被 `targetAction` 判定读取，判据写作一条**条件**——一条拒绝表示不得让 `targetAction` 为 `true`。今天该值在 `face/lifecycle.ts` 由 grade 判：

```text
targetAction: !violations.some(v => v.grade === "hard")
```

软档即 `true`，等于把拒绝记成「本轮完成了任务」——所以拒绝不借软档。
- `--recover` 的措辞不动，但**行为面按改后形面重述**：接管判定跑在结构腿裁决之后（`face/cli.ts#Cli#runWork`：只有 `this.#authority.structureRefusal(preflight) === null` 才进 `#recoverRun`，结构腿一拒它不被调用），而四门并入后正是结构腿在拒绝。因此一次被拒的派发上执行 `--recover`：不认领任何东西、不做任何恢复写入、不写轮记录、`cycle` 不推进，同一拒绝再次出现。而一次被拒的派发**总是**落下那一条拒绝事实（2.2：门口写、九行一视同仁）——所以「无写入」指的是没有恢复写、没有轮记录写、没有 `cycle` 推进，不是连拒绝记录也不写；后者是 §2.2 的普通路径，`--recover` 不构成例外。今天那句「无可接管」（`RECOVER_NOTHING`，住 `face/cli.ts` 的 `#recoverRun`）在这条路径上**不可达**——本相位不承诺那句话，也不改它：它仍属于「结构腿通过、但没有陈旧锁可接管」的另一条路径。
- `#reject` 族不动：那里孩子确实存在（draft 在盘上、形状不合格），`contract-violation` 是真话。

#### 4.2 不可读的拒绝事实
- 拒绝事实损坏或不可解析时，board 念一条**自己的** corrupt 行（unreadable refusal record，裸词：本相位新立），**不静默视作「无拒绝」**。它不借 `InFlight` 的两行：那两行各自声明一个锁事实（lock on disk / no lock behind），而拒绝事实从不持锁，借用会把「无锁」说成一个锁事实，也会让同一张词表里一行有两个意思。一条被吞掉的拒绝，比一条标错的拒绝更难查——本相位治的就是「错的形状」，不能顺手造出「没有形状」。
- 读面不因一条只读产物损坏而整体失败：corrupt 是一行，不是一次退出。

#### 4.3 与 #459 的对账
- #459 是「轮的终止不可与完成分辨」；本相位是「轮的被拒不可与死亡分辨」。同族：**轮的一种状态没有真实表示，于是借用了另一种状态的形状**。
- 本相位只收 pre-spawn 这一半。另一半（终止）留在 #459，且本相位不提供那一半的答案——只把「状态必须有自己名字」这条判据立起来。

### 5. 仓库自动化：提交钩子从 husky 迁到 lefthook

> 本节与 §1–§4 无契约关联，是本相位按用户裁定并入的第二件交付（2026-11-18）。它共用同一个交付分支与同一条门禁，不参与拒绝归属的任何判据。

#### 5.1 现状与迁移目标
- 今天的提交门是两件东西：`.husky/pre-commit` 的一行 `pnpm exec lint-staged`，与项目根的 lint-staged.config.ts（`*.ts` → `biome check`；`*` → `pnpm run precommit`）。`package.json` 以 `prepare: husky` 安装钩子，依赖 `husky` 与 `lint-staged`。
- 目标：提交门改由 lefthook 承担——`lefthook` 作为 devDependency **加入**（今天不在依赖里，迁移必须一并加），`prepare` 改为 `lefthook install`；`biome check` 仍然**不带** `--write`（一条违规必须让提交失败、且不写回），`pnpm run precommit` 仍然每次提交跑一次。

#### 5.2 等价性必须逐条断言，不靠「看起来一样」
- **暂存文件集**：lefthook 与 lint-staged 对**已删除**文件的处理不同——`biome check` 拿到不存在的路径会报错。等价性由**一次真实提交**判定（删除一个 `.ts` 后提交必须不红），不为它新增自动测试文件；不等价则在命令里过滤存在性。
- **全量那一条**：`pnpm run precommit` 挂在 `*` 上、每次提交跑一次，两套机制都如此；这条等价不需要新判据，但需要一次真实提交证明它确实跑了。
- **顺序**：`biome check` 先于 `pnpm run precommit`（今天的 lint-staged 任务序），迁移后 must 保持同一顺序，否则一条格式违规会在全量测试跑完之后才被发现。这条不是意图而是被验收钉住的条件：同一次真实提交里放一条格式违规 ⇒ 运行停在 `biome check`，该次提交的日志里**没有** `pnpm run precommit` 的运行记录（提交门等价那一行，见 Acceptance criteria）。顺序因此可核，不靠「看起来一样」。

#### 5.3 移除面与文档面
- 移除：`.husky/` 目录（含 shim）、lint-staged.config.ts、`husky` 与 `lint-staged` 两个 devDependency；`prepare` 改为 `lefthook install`，`lefthook` 的 devDependency 一面见 5.1。依赖面因此**读两个方向**：两个旧名字零命中，一个新名字有命中。
- 文档面：**不改**。`AGENTS.md` 的两句提交钩子（Commands 下的 `pnpm run precommit` 一行、约定下的 `biome check` 不带 `--write` 一行）只写规则、不写机制名，机制换了它们也不动；规则本身不变（`biome check` 不带 `--write`）。这是可核的事实而不是省略：交付后那两句逐字节不变，且三个机制名 `husky` · `lint-staged` · `lefthook` 在 `AGENTS.md` 里零命中。
- 本条不产生 changeset：它不改任何 first-party package 的行为，改的是仓库自身的提交门。

### Acceptance criteria

- `dispatch-input` **拒绝不写轮记录**：在没有 `base.json` 的工作区派发一次 wave 评审 ⇒ 命令输出 `CDD_BLOCKED` 且站名取自 structure 腿的九值行集；随后 `board` 无 `crashed:` 行、`waves[n].rounds` 长度与派发前相等、重派仍是 `review 1·1`。同一断言在改前必须红（今天读作 `review 2·1`）。
- `board` **拒绝写树级事实**：同一派发后 refusal.json 存在且八格齐全（`at` · `slug` · `op` · `type` · `cycle` · `attempt` · `station` · `detail`，缺任一格即红）；`board` 出现 refused 行，形状合 3.1，位置在树级事实块之后（带 `crashed:` 与 `orphan:` 的板上断言整块顺序：`in-flight:` · `orphan:` · `crashed:` · `refused:`）。同一条 pin 带跨工作区方向：`slug` 指向别的工作区的拒绝事实在本树的 board 上不渲染，而在它自己的 board 上照常渲染。
- `refused` 事实**最多一条 · 两个到期触发点**：拒绝后跑一次合法派发 ⇒ refused 行消失、`in-flight:` 出现；该派发正常结束 ⇒ `in-flight:` 消失且 refused 行不因结束而出现。第三条方向（释放即到期）：派发 A 持有 in-flight 时，派发 B 被 `in-flight` 门拒绝并写下 `station: in-flight` 的记录；A 随后正常结束、释放 in-flight ⇒ board 上 `in-flight:` 消失，**且** refused 行随之消失——不得出现 `in-flight: free — no dispatch holds this tree` 与 `refused: … in-flight · …` 同时在场（2.2 的第二个到期触发点）。第四条方向：树被 `in-flight` 门拒绝（有活主）之后、持有者释放之前，board 上 `in-flight:` 与 `refused:` **同时**存在——改前结构上不可能（拒绝不写事实），两行各自只陈述自己的事实。第五条方向（清除点不在派发体里，只有门口那一次负责它）：拒绝记录由一次 `tree-clean` 拒绝落下，随后把树弄干净，再跑一次**九行全过、而 line 腿拒绝**的派发（一个进入 `implement` 相位的 wave 上用 `cdd review`）⇒ 命令 exit 1 且念 line 腿那一行，board **不**印 `refused:` 行——一次通过整条结构腿的派发之后拒绝事实必须已经不在（2.2 · 2.3 ②）。第六条方向（释放不清别的站）：派发 A 持有 in-flight、树上有未提交改动时，派发 B 在 `tree-clean` 行被拒并写下 `station: tree-clean` 的记录；A 随后正常结束并释放 ⇒ board 上 refused 行**仍在**——释放只收回 `in-flight` 站的记录，不得清除任何其他站的记录，那一条站到下一次派发通过结构腿为止（2.2）。
- `DispatchAuthority` **行集即站名闭集 · 穷尽断言**：四道门各实测一次拒绝，落下的 `station` 分别是 no-host · carrier · dispatch-input · artifact 之一，且取自 `session/preflight.ts#PreFlightGateName` 这张九值表；穷尽断言只守站名这一半：给 structure 腿新增一个不在 `session/next.ts#DISPATCH_REASON` 里的站名 ⇒ 编译期红（一处：`session/dispatch-authority.ts#DispatchAuthority#structureRefusal` 的 `reason` 类型），`session/__tests__/preflight-rows.test.ts` 的九值对表同时红；detail 来源今天没有构造期守卫（`contract/preflight-rows.ts#PreFlightRows#judge` 的顺序分支与 `RowWording` 都靠人手补），断言不声称它。成对（多行失败）：两行同时失败时，行序在前的那一行拥有记录的两格 `station` / `detail` 与判词的 `gate` / `message`，次行只随 `details` 印出、不另立记录。
- **两腿同时不合格时报告结构腿**：一条夹具同时让某道门与 line 腿不合格（例：在 `implement` 相位的 wave 上跑 `cdd fix --type wave --tasks 1`，而 fix 面的 `INPUT_REVIEWS` 解析不到任何文件）⇒ 改后念 `CDD_BLOCKED: dispatch-input · fix · INPUT_REVIEWS · target-absent`，改前念 line 腿的 `cdd fix: cannot dispatch a fix round — <hop>`（成对，同一夹具）；把门修好之后 line 腿的拒绝照旧可达。这是具名变更⑥（Constraints）：门的顺序变化因此不是隐含的。
- **不可读的拒绝事实**：把 refusal.json 截断或写成非法 JSON ⇒ board 印一条自己的 corrupt 行（`unreadable refusal record`）、**不**印 `refused:` 行、仍 exit 0（4.2），board 其余行不受影响；同一夹具上写回一条合法记录后 `refused:` 行恢复。成对（释放不清不可读的记录）：一条在持有者运行期间写下的 corrupt 记录，在持有者正常结束（释放）之后仍在盘上、board 仍印 corrupt 行——释放点的谓词读不到 `station`，它不动这条记录（2.2）。
- `--recover` **不认领被拒的派发**：对一次被拒的派发执行 `--recover` ⇒ 不认领、无恢复写入、不写轮记录（`waves[n].rounds` 长度不变）、`cycle` 不推进、无接管戳，且同一拒绝再次出现（`face/cli.ts#Cli#runWork` 在结构腿拒绝上不调 `#recoverRun`，所以既有「无可接管」文案在这条路径上不可达——测的是不认领 + 无恢复写入 + 同一拒绝，不是那句话）；同时 refusal.json 仍在、`station` 与被拒那一刻相同——一条断言一件事，拒绝记录既不否认也不隐藏，也不借 `--recover` 开豁免。`--dry-run` 中途被拒 ⇒ 零写入（refusal.json 既不出现也不消失）。
- `lefthook.yml` **提交门等价**：暂存一个格式违规的 `.ts` ⇒ 提交被拦且文件**未被写回**，且同一次提交的日志里**没有** `pnpm run precommit` 的运行记录（违规必须停在 `biome check`，§5.2 的顺序由此成为可核的条件而不是意图）；删除一个 `.ts` 后提交 ⇒ 不红；干净提交通过且日志里出现 `pnpm run precommit` 那一次的运行记录。
- `lefthook.yml` **移除面与依赖面**：`.husky/` 与 lint-staged.config.ts 不在树上，`husky` / `lint-staged` 在 `package.json` 与 `pnpm-lock.yaml` 的依赖面零命中；**且** `lefthook` 在 `package.json` 的 devDependencies 里出现、在 `pnpm-lock.yaml` 里有条目，`prepare` 跑 `lefthook install`（依赖面读两个方向，不只读零命中）；`pnpm run validate` exit 0。
- `.changeset/` **门控**：`pnpm run validate` exit 0；changeset 为 `cdd-engine` **minor**（board 新增两行 · refusal.json 为新增产物 · structure 腿多四行 · 每个有输入面的派发 `checked:` 面多四行 · 无 harness 树里 `--dry-run` 的拒绝 · 两腿同时不合格时报文归属改变，均为消费面可见）；kairos 未动。
- `INPUT_WAVE_BRIEF` **是引擎写的格子**：在一个还没有 `tasks-<n>-brief.md` 的全新工作区派发一次 wave 评审 ⇒ 四道门全过（不是 `target-absent`），真跑路径随后渲染出 brief；同一状态下 `cdd implement --type wave` 的首次派发同样不拒（implement 行的声明同改）；同一状态加 `--dry-run` ⇒ 同一裁决（门不因面而换判据）。构造期断言按**槽**判：三行声明同一槽时绿（引擎写的槽集合恰好 `{NAMED_BRIEF_CELL}`），而「另一格也声明引擎写」即红——一个断言点，不是三个计数器。
- `CDD_BLOCKED` **一行共享 · 两个值 · 一处具名变更**：四道门各拒绝一次，真跑分别念 `CDD_BLOCKED: no-host · no host harness detected (run cdd from within a supported harness)` · `CDD_BLOCKED: carrier · carrier-mismatch · …` · `CDD_BLOCKED: dispatch-input · …` · `CDD_BLOCKED: artifact · artifact-identity · …`；artifact 门的活判词后续行（四段：`derived:` · `found:` · `identity:` · `repair:`，`repair:` 占两行）逐字跟随首行，而 refusal.json 里**没有**这四行（2.1：记录的 `detail` 只由首行派生）。成对：五行既有行与 `dispatch-input` 一行逐字节同改前，`no-host` · `carrier` · `artifact` 三行的**首行**比改前多一段站名前缀（改前三行不带站名、改后带），且三行的 detail 文本与改前逐字节相同（只加前缀、不改措辞）；board 念记录派生的那一行 `station · detail`（无后续行），三个外层各守自己的形状。
- `--dry-run` 上的结构腿拒绝**由预览面陈述**：脏树上三动词各跑一次 `--dry-run` ⇒ stdout 出现预览头 + 一条 `  refused:  station · detail` 行，`CDD_BLOCKED:` 不出现在任何流上，details 行与 checked 面仍在 stdout，refusal.json 零写入；`in-flight` 且带 `holding` 事实的 `--dry-run` ⇒ 仍是 `lock:` 面 + 接管提示、无 `refused:` 行，三种形状各断言一次：活主（`lock: held by pid <live>`，无 `--recover` 提示）· 死主（`lock: held by pid 999999` + 接管提示；`--recover --dry-run` 下仍不接管，记录与锁一个字节不变）· 锁在盘上的不可读记录（`lock:` 行 + corrupt 提示）（成对：入口合并前后两个流都被断言）。
- `--dry-run` 上的 no-host **是具名变更**：在没有 harness 的树里 `--dry-run` ⇒ 预览块 + exit 1（成对：改前是五行预报 + exit 0）；树内有 harness 的 `--dry-run` 仍预报、仍 exit 0。源码断言（**只覆盖派发主机事实**）：派发路径上恰好一次探测——composition root 的那一次，其值同时交给 `PreFlightContext`、lifecycle 的 spawn 与 `Preview` 的 `child:` 行；`face/lifecycle.ts` 不再持有那句 no-host 字面，也不再持有 detectHost() 调用，CliLifecycle#detectHost 这个只被 `#runDispatch` 使用的适配方法随其唯一调用点一并退役（钉它的那条测试同批退）；`face/preview.ts#Preview` 的 `child:` 行不再自带 `(no host detected — real run would BLOCK)` 分支（no-harness 树里结构腿先拒、`#render` 不可达，那句字面与钉它的测试一并退役），措辞只住在 seam 读的词表 `face/words.ts`。成对：`rg 'HostDetect.detect' packages/cdd-engine/src-next -g '!**/__tests__/**'` 在交付后仍给出**四处**匹配——composition root 一次 + 派发路径之外三处（`face/gate.ts#CliGate` 的 `#renderer` · `face/cli.ts#Cli#runBoard` · `face/cli.ts#Cli#runWork` 的 `Capsule`，1.1 的划界），断言因此不许写成「全树一次」。
- `checked:` **面随门增长**：一次 approved 的 wave 评审在改前印既有的 `checked:` 行（`tree-clean` · `in-flight: free — no dispatch holds this tree` · `graph` · `plan-ledger`），改后同一派发在这些行之下再印 no-host · carrier · dispatch-input · artifact 四行；`cdd implement`、`cdd review`、`cdd fix` 三个面**各断言一次行名集合**——四道门在每一面都跑（`carrier` 与 `artifact` 在非 fix 面上以空格短路为 null，仍记一行），故三面各四行、没有 fix-only 这一档，适用面本身因此是被测的事实。成对：一次正常 wave 派发（批非空）的 `checked:` 面带这四行；一次预测批为空的 wave 派发（plan 无开放 wave）上四行**全体让位**——`checked:` 面不带它们、结构腿不拒（`structureRefusal` 为 null）、由 line 腿给出自己的拒绝（1.1 的让位条件）。断言写行名与适用面（有输入面的派发一律 always），不写整块快照。
- refusal.json **落在被忽略的命名空间里**：在一棵 `.gitignore` 不含 `.kairos` 的临时仓库里拒绝一次 ⇒ `.kairos/cdd/` 下出现 refusal.json（裸词，见 2.1）且 `git status` 干净（标记先于写入发布）；紧接着的第二次派发仍按自己的事实判定，而不是在 `tree-clean` 上被引擎自己写的文件拒掉。

## Constraints

- **零裸函数**：`packages/cdd-engine/src-next` 下不新增 `function` 声明，状态与行为落进类（`check:no-bare-functions` 是门）。
- **pin 写法**：行为断言引模块路径 + 符号名，不引行号；尚未在源树出现的词汇写裸词或进围栏块——反引号即成 pin，未落地即红。
- **单事实单份**：拒绝事实只有一个家（树级记录）；命令面与预览面念 seam 的活判词（首行即 `station · detail`，后续行原样跟随），board 念记录派生的那一对（3.3），三处只各自加外层，不各自持有第三份副本。
- **消费面守恒（逐项列举，不给计数）**：逐字节不变的是五行既有拒绝行（`tree-clean` · `in-flight` · `doc-contract` 在 `CDD_BLOCKED: ` 通道上，`graph` · `plan-ledger` 在 `cdd <verb>: ` 通道上——通道归属的家是 3.3，这里只列名、不重述规则）· `dispatch-input` 一行（含预览那一行）· 既有 `crashed:` 语义 · `in-flight` 带 `holding` 事实那一臂的 `lock:` 面（活主 · 死主 · 锁在盘上的不可读记录）。具名变更六处，逐项：① `no-host` · `carrier` · `artifact` 三行的首行多一段站名（3.3），后续行不动；② `--dry-run` 上的结构腿拒绝改由 stdout 的预览块陈述（2.4）；③ 无 harness 树里的 `--dry-run` 因此从「五行预报 + exit 0」变成「预览块 + exit 1」（2.4）；④ 每一次**有输入面**的派发的 `checked:` 面各多四行，适用面一律 always（预测批为空的 wave 派发是唯一的让位例外：四行一起不判、不记，1.1）——门跑过就记一行，`carrier` 与 `artifact` 在非 fix 面上空格短路仍是跑过（1.1）——于是既有 `checked:` 的钉读字节随之移动，这是具名变更而不是回归；⑤ board 的两行：`refused:` 行（3.1）与不可读记录的 corrupt 行（4.2）；⑥ 两腿同时不合格时的报文归属：四门并入结构腿后排在 line 腿之前，一条同时不合格的派发从念 line 腿改为念结构腿那一行（改前 line 腿先判），line 腿的拒绝在九行通过之后照旧可达。新增的读面因此是：board 的两行 · 新产物文件（refusal.json，2.1）· 三个拒绝行的一个前缀 · `--dry-run` 上一个入口与一条流 · 每个有输入面的派发新增的 `checked:` 行（四道门四行）。① · ④ · ⑤ · ⑥ 同批登记进章程的在册增量（D96 与 Phase inventory 的同句）与 changeset。
- **不留豁免层**：不引入「pre-flight 拒绝走一条特殊路径」的分支——门前的返回本身就是普通路径，拒绝不需要例外。
- **引擎只拒不改**：拒绝不移动、不改写、不删除任何既有产物；门的前移不得让任何已被写的文件变成孤儿。
- **类的规模**：新增类守一条不变量（一树最多一条拒绝事实），方法读作 ≤10 行，参数 ≤4；超过即说明它守了两件事。
