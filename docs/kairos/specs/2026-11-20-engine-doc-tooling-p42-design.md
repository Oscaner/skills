## Design

`nit` 跨过两个相位，却从未有过权力：`session/handoff-schema.ts#rollup` 只数 blocker，`warn` 与 `nit` 到达同一个结论。第三档唯一在场的语义是跨轮降级记账（`session/handoff-schema.ts#HandoffSchema.#tierRankOf` 的三级阶梯），而它在两档下同样成立——`blocker` 降到 `warn` 就是一次降级。故词表收两档，`nit` 承载过的观察改走载体已有的 `notes` 槽；同批把任务块的两条结构判据立为门。

### 1. 档位收口

#### 1.1 `rollup` 数档位，结论对 warn 与存量 `nit` 逐字节不变

- `session/handoff-schema.ts#rollup` **一格不动**：它的判法本就按档位（`blockers > 0 ? CHANGES_REQUESTED : findings.length > 0 ? REVIEW_FIX : APPROVED`），本相位不重写这条判断，只把它钉成守恒条件——词表收窄之后，它是让存量 `nit` 的结论逐字节不变的那唯一一处，验收因此四臂全挂在这条判断上，源码不欠改动。四臂：`blocker` 命中 ⇒ `CHANGES_REQUESTED`；**任一非 `blocker` 的 finding** ⇒ `REVIEW_FIX`；零 finding ⇒ `APPROVED`。非 blocker 臂的取值集是「非空且不含 blocker」，不是「`warn` 计数」——这条臂就是守恒臂，`warn` 与存量载体里已退休的 `nit` 都落在它上面。
- 退休档的读法写在这里，不留空：存量 `nit` 行没有迁移，也不需要迁移——`session/ledger.ts#Ledger` 的每轮结论经 `session/handoff-schema.ts#HandoffSchema` 的 `conclusionOf` → `rollup` 派生，故一份 findings 全为 `nit` 的载体 ⇒ `REVIEW_FIX`，与收缩前逐字节相同。同一投影面必须分开写侧与读侧。**写侧收窄，两处声明同批**：`session/handoff-schema.ts#CARRIER` 的 `findings.items.severity` 枚举只留 `blocker` / `warn`，新草稿的 `nit` 在形状面上被拒，报文点名取值集；同一文件 `session/handoff-schema.ts#CarrierValue` 里 `findings` 那一格的 `severity` 是这份 schema 的手写孪生（`Carrier` 由它映射出来），同批缩成两值——只收枚举会留一枚照收 `nit` 的类型给下一任作者照写。**读侧不收窄——但那枚三值联合是本相位要落地的工作项，不是树上已有的一个**：`session/handoff-schema.ts#HandoffSchema.findingsOf` 的取值集照旧是 `blocker` / `warn` / `nit`。读侧此刻借的正是写侧 `FindingSeverity`：`session/ledger.ts#RoundFinding.severity` 的声明、`session/handoff-schema.ts#HandoffSchema.#tierRankOf` 的入参、以及 `findingsOf` 里 `severity as FindingSeverity` 那一枚 cast，三处指向同一枚即将收窄的词表——照下一条「改变的只有词表」改而不动这三处，读侧就跟着收窄，第三值只剩 cast 后面的一次运行时幸存，本节「读侧不收窄」的保证在类型面上没有一处可以指。工作项一条、三处改挂同一枚联合：在 `session/ledger.ts` 声明投影面自己的三值联合（`"blocker" | "warn" | "nit"`，名字随实现、本文不钉字面——钉一个尚不存在的符号就是给交付树留一枚死 pin，与 §8 的 `seat` 常量同一条纪律），`session/ledger.ts#RoundFinding.severity` 与 `#tierRankOf` 的入参改挂它，`findingsOf` 的那枚 cast 随之换成这枚联合；写侧词表 `FindingSeverity` 只表达两档。理由不是「只读磁盘」——`findingsOf` 同一条路径也投影本轮自己的 `draft.findings`（`face/lifecycle.ts#reconstruct` 在 read-back 之后把它交给这个投影）；真正的理由是写侧枚举在 read-back 先拒掉新 `nit`，投影面因此只会从存量载体读到第三值。`#tierRankOf` 的三级排名 2 / 1 / 0 逐字节保留：把 `nit` 并进 `warn` 会静默丢掉存量 `warn → nit` 的降级标记，那是登记表外的展示字节变化。未知档位的丢弃本来就是投影的规则。这条不是装饰：`session/ledger.ts#Ledger` 的 `#findingsOf` → `Round.findings` → `session/next.ts#NextStepRouter.next` 的 review 臂按投影条数分流（`findings.length > 0` ⇒ `#fixRoute`，零条 ⇒ `#close`），读侧若跟着收窄，一份 findings 全为 `nit` 的存量载体就会在结论为 `REVIEW_FIX` 时被直接关线——正是「`next:` 字面逐字节不变」要拦的那一处。
- 改变的只有词表：`session/ledger.ts#FindingSeverity` 与 `contract/review-criteria.ts#CriteriaTier` 都收成 `blocker` / `warn`，载体的 `severity` 枚举同批收缩。存量载体与侧车不在迁移面——`nit` 的写者只有 review 的 child，本相位之后不再有写者。
- 破坏性字节登记六处，一律随 changeset 走 minor（D74）：① `severity: "nit"` 的载体被拒（`contract-violation`，报文点名取值集）· ② `contract/review-criteria.ts#TIER_ORDER` 的取值集 · ③ `render/templates.ts#REVIEW_ITEM_HEAD` 里 `blocker → CHANGES_REQUESTED · warn/nit → REVIEW_FIX · none → APPROVED` 那一句（这句不住 `REVIEWS` 里，`REVIEWS` 只载 `lensEnum` / `pinLens` / `axesGuide`）· ④ 同一文件 `SEVERITY_RUBRIC` 的整张表——它由 `CRITERIA.renderRubric()` 渲染、每一条 review 指令都带着它，故 §1.2 两行正文的改写落在每条 prompt 上 · ⑤ `render/templates.ts#FIX_SHELL` 的 `Fix ALL findings (blocker/warn/nit)` · ⑥ `session/handoff-schema.ts#HandoffSchema.schemaText` 渲染的 `## Handoff schema` 围栏——该围栏由 `#writable(plane)` 过滤 `CARRIER` 现渲染，`findings.items.severity` 的 `enum` 因此随 ① 变成两值：它是同一编辑的第二处落点，不是 ① 的重复，也只有 judge 面的围栏带 `findings`（work 面的可写子集没有这个字段）。①② 是形状面与判据面，③④⑤⑥ 是 prompt 字节面；档位收口的登记到此为止，没有第七处——本相位合计十处，另四处在 §7（⑦ 修轮 prompt 的写约束句 · ⑧ 收口拒绝面）、§8（⑨ 收回一条误报）与 §6（⑩ 新增顺序判据），逐处列在 `## Constraints` 的例外里。

#### 1.2 删档不删行

- `contract/review-criteria.ts#CRITERIA_ROWS` 保持 `census:criteria.rows = 6` 行——删的是档，不是行。两条 `nit` 行改判 `warn`，正文重写成「这条观察该去哪」：
  - `expression-only`：从「pure expression 是 nit」改判 `warn`；三格的替换字节（`body` · `duty` · `counterExample`）在下一条的五格清单里按英文原样给出，不在此处分述，免得两份措辞各自漂。`duty` 收两半：它改变的那项判断，**以及这一档的代价——欠一个 fix 轮，且不对它复评**。代价写在这一行而不是新起一行：这一行本就在教「轻的东西去哪」，而代价正是同一条分界的另一半；新起一行要动 `census:criteria.rows` 与两份已闭合 P37 文档的四处引用，为一个句子付两次账。改名（把 `warn` 换成 `fix`）同样不做：那会把判档从「它是什么」改成「它要多少」，且让存量载体的读侧欠第二张映射表。
  - `regrade-mark`：教学保留（降档要写理由），结论不变——标记是展示事实（`face/board-view.ts#LineCarriers` 的 `regradeNoteOf` 与 capsule 那一行），不是一条 finding。
- `render/templates.ts#SEVERITY_RUBRIC` 就是 `CRITERIA.renderRubric()` 的整张表渲染，每一条 review 指令都带着它——「词表收两档」因此是**整张表**的正文改写，不是两条退休行的改写。表内带 `nit` 字面的格恰五格，逐格点名，不留一格给实现者补。**逐格的替换字节按英文原样钉死，不写中文意译**：这张表经 `CRITERIA.renderRubric()` 渲进每一条 review 指令，是英文散文，用中文转述等于把语种留给实现者——而零命中扫面只找 `\bnit\b`，句子换成哪种语言它都看不见。五格逐格（现写 → 替换）：
  - `evidence-missing`（`blocker`）的 `counterExample`：`` A warn or a nit may leave `evidence` out — nobody adopts its conclusion on its word — so the absence is legal there, while the same absence on a blocker ships a decision nobody can check. `` ⇒ `` A warn may leave `evidence` out — nobody adopts its conclusion on its word — so the absence is legal there, while the same absence on a blocker ships a decision nobody can check. ``
  - `debt-consequence`（`warn`）的 `counterExample`：`` Dead code that nothing calls today and no output depends on is a warn, not a nit: it changes what the next reader believes, which is the warn / nit boundary itself. `` ⇒ `` Dead code that nothing calls today and no output depends on is a warn: it changes what the next reader believes, which is the warn boundary itself. ``——**整句两端都换**：`nit` 在这句里出现两次，开头的否定式与斜杠式是同一处判档校准的两半，只换尾半句就是让实现者自己发明开头换成什么。
  - `expression-only` 的 `body`：`` A finding is a nit when it is pure expression: naming, line-wrapping, comment wording, ordering inside one file — it changes neither behaviour nor anyone's judgment. `` ⇒ `` Pure expression — naming, line-wrapping, comment wording, ordering inside one file — is a `notes` line, not a finding: it changes neither behaviour nor anyone's judgment, and a finding that stays must name the judgment it changes. ``
  - 同一行的 `duty`：`` A nit owes why it is not a warn: one sentence saying which judgment it leaves untouched. `` ⇒ `` A warn here owes two halves: the judgment it changes, and this tier's price — a fix round owed, and no re-grade of that round. ``
  - 同一行的 `counterExample`：`` A naming inconsistency that stays self-consistent inside one file is a nit, not a warn: no cross-surface reader is misled. `` ⇒ `` A naming inconsistency that stays self-consistent inside one file is a `notes` line, not a finding: no cross-surface reader is misled. ``——它正是回答「这类观察现在去哪」的那一格，而验收的零命中扫面读的是整张 `SEVERITY_RUBRIC`，漏陈述它就让这句判档校准落进实现者的自由裁量。
- 两行的 `tier` 由 `nit` 改判 `warn`（`expression-only` 与 `regrade-mark`），`regrade-mark` 的三格一个字节不动。同表的 doc comment 不是只改 `nit` 那一句而是整句重写：那份注释按档数行（`blocker` 两行 · `warn` 两行 · `nit` 两行），两条行改判 `warn` 之后 `warn` 是四行、`nit` 零行，故只改 `nit` 那句会让同一块里的 `warn` 计数当场失真——而 `\bnit\b` 扫面根本到不了那一行。写法取「去掉逐档计数、只留恒真的那一句」：每档至少一行，改档之后的边界名**四条全列**——`blocker` 档两条（functional impact · reproduction gate），`warn` 档四条（the debt · the pin parseability gate · 以及随 `expression-only` 与 `regrade-mark` 一起改判过来的 the expression boundary · the downgrade mark），不写数字——逐档计数会被下一次改档推翻，而扫面读不到它。只列改档前那两条，就是把同一份注释里另外两条边界留成无名：这一句是下一任作者读这张表的唯一索引，而它数不到 `warn` 的后两条。`contract/review-criteria.ts#CriteriaRegistry` 的两处档序注释（类注释与 `renderRubric` 的文档注释，各一句「the tiers run blocker → warn → nit」）同批改。漏一行的代价不是措辞不美：评审照着 prompt 判 `nit`，收缩后的枚举在 read-back 硬拒整份草稿（`contract-violation`），这一轮就白跑。
- 路线与章程注册的「删掉两条 `nit` 行、回填 `census:criteria.rows`」不同，理由在同一句里：两条行的教学价值（一条教「什么不该进 findings」，一条教「降档要写理由」）删行后无处可去，而保留行既不移动 census 也不动 `contract/__tests__/census.guard.test.ts` 的既有对账。章程那几格的回填见 §5。
- `contract/review-criteria.ts#TIER_ORDER` 收成 `blocker` → `warn`；`contract/review-criteria.ts#CriteriaRegistry.renderRubric` 的「每档至少一行」保持抛错语义，**同批新增第二条守卫**：任何一行的 `tier` 落在 `TIER_ORDER` 之外 ⇒ 抛错。既有装配只遍历 `TIER_ORDER`，落在表外的行被静默跳过、正文消失而不报，故「出现第三档即抛」是新守卫，不是既有行为。**这道守卫是防御纵深——类型面造不出它的输入**：`CriteriaRow.tier` 挂 `CriteriaTier`，而 §1.1 把它收成两值，故一份合类型的注册表里第三档不可构造；守卫拦的是**绕过类型到达注册表**的行（一份 JSON 装出来的表、一枚陈旧的编译产物、一次 `as unknown as` 的构造）。成对臂因此只能显式撒谎，而这一点要写进臂里：`as unknown as CriteriaRow` 造一行 `tier: "nit"` ⇒ 必红，删掉那一行 ⇒ 正常渲染。臂既不能省（省了就只剩「每档至少一行」，而它对表外的行静默），也不能假装类型面造得出它（那会写出一枚编译不过的字面量）。
- `session/handoff-schema.ts#HandoffSchema.#tierRankOf` 不动：它排名的是投影面的三值联合（§1.1 新声明的那一枚，入参不再是 `FindingSeverity`），三级 2 / 1 / 0 逐字节保留。写侧只剩两档，新 finding 的降级因此只有「`blocker` → `warn`」这一档——「唯一的一档」这句写进 `CRITERIA_ROWS` 的 doc comment（§1.2 正在重写的那张边界榜，与 `warn` 档的 the downgrade mark 同处），不写进排名函数，也不写进 `regrade-mark` 的任何一格：那一行三格逐字节不动，而它的正文经 `SEVERITY_RUBRIC` 进每一条 review prompt，动一格就是登记表外的第十一处字节变化。`regradeNote` 的两个调用点（`face/lifecycle.ts` · `face/board-view.ts#LineCarriers`）不动。

### 2. `notes` 转正

#### 2.1 承载面：wave 线下一轮的 brief 与每条线的板面 token

- `session/handoff-schema.ts#CARRIER` 的 `notes` 槽从「声明但无人读」升为承载面，两个面各有一个名字：
  - **板面（每一条线）**：`face/board-view.ts#LineCarriers` 增一个 `notesOf(record)` 投影，与 `countOf` / `findingsOf` 共用同一次载体读与解析（`#contentOf` 缓存），读 `CARRIER` 的 `notes` 槽。这个投影覆盖**两种 plane** 的载体（`judge` 与 `work` 都算）：M 是这个 token 报告的那几条记录各自的 note 条数之和（求和面就是 `#summaryToken` 收到的 `run`，与 `+N` 同一处），既不是整条线的 note 总数，也不是判官面的条数——`face/board-view.ts#LineCarriers.#readFresh` 现有的「无 `findings` 数组 ⇒ `EMPTY_CARRIER_CONTENT`」早退必须同批放宽成「无 `findings` 且无 `notes` ⇒ 空」，否则 work 轮的 note（引擎自己在 `render/templates.ts#DOCS_FIX_SHELL` 里让 child 写进 `notes` 的那一条：`else BLOCKED + the reason in notes`）永远读成零。`face/board-view.ts#BoardView` 的行 token 在既有 findings 的 `+N` 之后追加 `notes +M`：M 是这个 token 报告的那几条记录各自的 note 条数之和——`#summaryToken(verb, body, mark, run, carriers)` 拿到的 `run` 是什么就数什么，与 `+N` 的 `countOf` 同一个 `reduce` 面（成功面合一的 token 数它的那组成功记录，失败面的 token 只数那一条记录），故一条线上 review 载体与 fix 载体各带一条 note 时两个 token 各读 `notes +1`，不是各自 `notes +2`；计数逐条以 `REGRADE_NOTE_SEPARATOR` 同一分隔符紧随其后——与降级标记同一处、同一行，不新起行、不新起段；两者同时在场时**降级标记在前、`notes +M` 在后**（`#summaryToken` 先拼 `+N` 再拼标记，notes 段接在标记之后）。**每条 note 上板前先过降级理由同一道展示折叠**：`contract/review-criteria.ts` 的 `displayReason` 从模块私有升为导出（`regradeNote` 与板面共读这一个 fold，不复制第二份），` · ` 折成 `; `、连续空白（含换行）折成单空格——`notes` 是无约束字符串数组，原样上板的一条带换行或 ` · ` 的 note 会把板面的一行拆成两行、把一条 note 读成两格。折叠只发生在展示面，不落回载体：`carrier.notes` 存的是 child 的原文。
  - **brief（只 wave 线）**：`render/brief.ts#BriefRenderer.render` 与 `face/gate.ts#CliGate.renderBrief` 的入参是 plan 文本、那一份 plan 解析与任务号，不含任何载体，**故 brief 读 `notes` 是一条新读**。三处各钉一句：**读哪一条**——本线（同一 `(line, key)`）上最后一条已完成的 **review 载体**（`(cycle, attempt)` 最大）；**经哪个读面**——`face/gate.ts#CliGate.renderBrief` 从 `face/lifecycle.ts#DispatchScene` 的 `ledger` 取，经 `face/board-view.ts#LineCarriers` 的 `notesOf(record)`（归属判定 + `CarrierIntegrity.read` 摘要校验，与板面同一次读）拿到投影，随文本与解析一起交给渲染器——不新起裸 `readFileSync`（那是「单事实单份」禁止的第二台读机）；**落在哪**——`BriefRenderer.render` 在 `## Constraints` 镜像**之后**拼 notes 段，`render/brief.ts#BriefRenderer#taskBody` 的字节一字不动（`session/ledger.ts#Ledger#briefDrifted` 两侧都哈希 `taskBody`，notes 落进 `taskBody` 会让散列投影与 child 实际读到的 brief 字节分家）。brief 的 notes 段逐条原样列出——不改写、不附加动作要求。doc 线（phase-spec / plan / overall）的评审轮没有 brief 段可承载，note 在那些线上只走板面。
- 不进 `rollup`：一条 note 不改变结论、不产生 fix 需求、不欠 `dispositions`。转正的是「可读」，不是「可判」。
- **不跨线**：note 不继承到下一条线，因为它的引文指向本线那份文档的具体一句。
- 派发输入表零新增行：`notes` 走 brief 渲染器的入参，不新起 `INPUT_*` token，P38 的必填表不动。这是范围收窄不是遗漏——新 token 会让每条派发线都欠一个值。

#### 2.2 引擎自己不搬进 notes

- 降档标记（`contract/review-criteria.ts#regradeNote`）保持展示事实；`face/lifecycle.ts` 注入的 pin 违约 finding 保持 `warn`。两条都不搬进 `notes`——一个是标记、一个是真断言，搬任一都会把「可判」与「可读」再混一次。
- 引擎自己写进 `notes` 的**三族**（`face/lifecycle.ts` 的 `#materialize`：`observations`——落在声明形状外的装饰槽——· `reserved`——被丢弃的非声明键——· `#canonicalArtifacts` 压进同一个数组的 artifact 偏移句）**不进两个面**。artifact 那一族按 slot 实例化，不是一句话：`artifact ${key}: declared path ${value} deviates from the prescribed ${canonical} — the canonical path is booked`，而 `#prescribedArtifact` 只 prescribe 两个 slot（`report` 与 `test_evidence`），故这一族恰两形。落法一条：`carrier.notes` 只装 child 的 `draft.notes`，三族全改骑已有的软违规通道（`observations` 本就落在 `RoundViolation.soft` 上；`reserved` 与 artifact 偏移句同批并进同一条通道，偏移因此仍是可审计的 record 事实，只是不再冒充 child 的观察）。这条通道**不静默**，两笔后果写在这里而不是留给实现者发现：`face/lifecycle.ts#materialize` 把软项交回 `judged.violations`，`#warnSoft` 把每条软报文拼成一行 `CDD_WARN:` 打到 stderr，`session/ledger.ts#Ledger#counterOf` 的退休键分支（`counterOf` → `softViolations` → `#softOf` 的逐行求和）又把它数进派生的 `contractViolationCount`（同文件的 `softViolationsOf` 是单个 key 的兄弟读面，派生 key 不读它，这条链不钉在那一格上）——故本相位之后，一个只带非声明键或只带 artifact 偏移的轮会多一行 stderr 警告、该行的派生软计数 `contractViolationCount` 抬一。板面**不**读这个值：`face/board-view.ts` 的 token 与 `#crashed` 判的是 `record.violations` 里 `grade === "hard"` 的项，软项一条也到不了那一路，故板面字节不变——本相位唯一变的观测面就是那行 stderr 与那个派生计数。判决、退出码与 `CDD_BLOCKED` 通道不动：软项从不触达这三者。**同一次编辑改掉 `#materialize` 自己的两句反话**：`face/lifecycle.ts#materialize` 的文档注释现写「materialize drops them and books AT MOST ONE WARN on the carrier's notes」，同函数的 family 注释现写「A non-declared key is §8.7's own face: ONE note and nothing else（the drop is silent on the warn channel …）」——两句与本节落法相反，且都不带 `nit` 字面，§4 的登记-扫面门到不了它们，只能在这里点名：文档注释改成新落法（三族骑软通道，`carrier.notes` 不因此多一条），family 注释改成声明的两笔后果（每个受影响的轮一行 `CDD_WARN:`、派生软计数抬一）。漏改的代价不是措辞：下一任读注释会先读到「静默通道」，再去找一个不存在的软通道第二写者。两个面因此读到的就是 child 写的 note 逐条原文——brief 与板面 token 同一个过滤、同一份来源；否则下一轮 brief 会把「dropped non-declared draft field(s): … — engine-reserved, never written」当 note 印出来，板面会把一条 artifact 偏移读成 child 写的 note。
- **存量载体上的同一句由读面挡，不等写侧的承诺**：上一条只覆盖本相位之后写出的载体；盘上已有的载体照样会把引擎那几句带进下一轮 brief——本工作区的 P8 `tasks-1,2,3,6,8-review-1` 就是一份，它的 `notes[0]` 逐字节就是 artifact 偏移句。故过滤落在读侧那一处：`face/board-view.ts#LineCarriers` 的 `notesOf(record)` 投影里加一道逐字节前缀谓词，逐条丢掉以上述三族开头的 note——两条装饰族字面（`dropped decorative draft field(s)` · `dropped non-declared draft field(s)`）加 artifact 族的**句形**而不是一处实例：`artifact ` + slot + `: declared path ` 前缀，slot 取 `report` 与 `test_evidence` 两个字面 stem（那是 `#prescribedArtifact` 仅有的两个 prescribe 值），板面与 brief 都经这个投影，一处谓词两处生效，不各写一份。句形而非单例有盘上的反例：本工作区 p24 `tasks-4-fix-2` 的 `notes` 是五条——两条引擎 artifact 句（`report` 与 `test_evidence` 各一）加三条 child note；谓词只写 `report` 那一形，同一份载体的两条兄弟行就被区别对待，两个面读四条，而上板的那条引擎合成句正是本节要拦的。谓词是**逐字节前缀**而不是子串（同样几个字出现在一条 note 中间不折），且只折展示面、不改写载体：`carrier.notes` 存原文，审计副本留在 soft violation 上。代价写明：child 若逐字节写出同一前缀，读面无法把它与引擎那几族分开，那条 note 一起被折——那几族都是引擎声明的固定句（artifact 一族的两形是同一句的实例），同形即同一事实。

### 3. 任务块判据

#### 3.1 `Create:` 唯一且最早

- 读面分两处，极性不许合并：
  - **pin 表保持 Create-only**：`contract/pins.ts#ForwardPaths` 的 `#declaredPathsOf` / `#pendingOf` / `skips` 只认 `- Create:` 声明，因为只有 `Create:` 声明可以豁免一条尚未落地的 pin（`PinAudit` 的三处判定点读的都是 `skips`）。把 `Modify:` / `Test:` / `Delete:` 喂进这张表，会让 `- Modify: <未落地路径>` 成为待落地声明，pin 审计就此静默。
  - **投影归既有读面，不是新读面**：`contract/task-blocks.ts#PlanTaskBlocksReader` 已经在解析 `Files` 行，并且已经把动词标签（`FILE_ROW_LABEL`）剥掉——剥完就扔。它改成保留那段标签并切出（任务号 · 动词 · 路径）三元组，`single-create` 读这份三元组投影，pin 豁免那一面**不读**它——两个面共用的只是行首那个字面 `Create`，不是一张表、也不是一份行集：三元组的任务号按 `### Task N:` 关联（判据计数的那一格），而 pin 豁免读的 `contract/pins.ts#ForwardPaths#declaredPathsOf` **保持它现有的全身扫面**（`/^\s*[-*]\s+Create:/` 是**行选择器**，块内块外同读；它不是第二条路径形状正则，形状判定在 `PinVocabulary.pathOf` 手上，§9 只把这句话钉住）。**两个面不合并读面**：`single-create` 那一面按 `### Task N:` 关联任务号并读整张动词词表（四词表加 `other`），pin 豁免那一面不读投影、认得只有 `Create:` 行——共用的只是那个词，不是表、也不是行集。收窄是显式拒绝的，理由是**结构**、不是经验：pin 豁免的单位是整份 plan（`declaredPathsOf` 读全文，块内块外同读），`single-create` 投影的单位是任务块（`### Task N:`），两者只共用 `Create` 这个词，从不共用一张行集——把豁免收窄到块内，等于让豁免改读一张它从不读的行集。本相位要的是词表的唯一性，不是范围收窄。**语料这一半不能当理由，得说准**：`docs/kairos/plans/*.md` 的 bullet `Create:` 行全落在 `### Task N:` 块内（引擎自己的块读面量过），故收窄不改变任何 pin 判决；点名树里不存在路径的那批声明同样全在块内，同样不免证。故「只有 `Create:` 能豁免未落地 pin」是行选择器的事实，不是一条待实现的词表映射，也**不是**一个被本相位拓宽的集合：`Add:` 与 `新建：` 不豁免未落地 pin（它们在声明集里算认领，在 pin 表里不算声明）；`single-create` 那一面才按任务号关联，块外的 `Create:` 行不参与唯一性与顺序的计数（它没有任务号可比）。
- **投影的行语法两级判**：`Files` 的每一行先剥 bullet（`-` / `*` / `+`），再定动词——① 行首 ASCII 标签剥得出（`contract/task-blocks.ts#PlanTaskBlocksReader.FILE_ROW_LABEL` 的既有规则只认 ASCII 字母开头的标签）⇒ 标签**第一个词小写化**就是动词，**但四词表（`create` / `modify` / `test` / `delete`，大小写不敏感）之外的一律记 `other`**——① 与 ② 出口同一张五值词表（四词表 + `other`），没有第三格让表外的标签词落空；② 标签剥不出 ⇒ 先剥 `**Files**:` 这类字段前缀，余量的首词落在四词表里就是动词，否则记 `other`。语料正是用表外的标签写建文件：`- Add:`（`docs/kairos/plans/2026-10-10-engine-doc-tooling-p35.md` 四行，其中声明 `packages/cdd-engine/src-next/infra/plan-source.ts` 的那一行建的正是一个由该相位落地的文件）· `- Confirm:` · `- Not in this task:` 一类，全部落在 `other` 这一格。记 `other` 的行照旧命名一条路径，但**它是否构成该路径的声明**由下一条「认领」钉准——词表判动词、声明集判认领，两个面各答一个问题；路径 token 沿用 `PlanTaskBlocksReader#fileTokensOf` 的既有规则（反引号内的 span，没有引号时余量算一个 token），不另立第二个 tokenizer——但一段的余量没有反引号 span 时要按同一组分隔符再切成多个 token：否则第四类的 `Create: a.ts、b.ts、c.ts` 只给出一个合成 token，而 `PinVocabulary.pathOf` 会把它当**一条**路径收下（带 `/` 且以 `.ts` 结尾，实测不是 null），三个真文件因此一条声明都没有、还多出一条不存在的合成路径。切分落在 `fileTokensOf` 内部（一处 tokenizer，验收波那一面与判据面同吃），并同批改 `filePathsOf` 的文档注释——「an unrecognized remainder is returned as one token」不再成立，改成「按分隔符切分，散文与括号附注由 `PinVocabulary.pathOf` 落掉」；`face/lifecycle.ts` 那一处按 `filePathsOf(block).length === 0` 判「该任务不声明文件」的验收波单元不受影响：切分只会多给 token，不会把一段声明读成零。
- **行内动词把一行拆成多段**：一条 `Files` 行可以先后带多个动词。分段点是 `;` · `；`（全角分号）· `、` · `·`（后两者是段分隔，不必紧跟动词）：自带四词表动词的段用自己的动词，没有动词的段**继承前一段的动词**——`Create: a.ts、b.ts、c.ts` 因此是三条 `create` 声明，不是一条。动词取词前先剥一个末尾 ASCII 冒号（`Create:` ⇒ `create` · `Modify:` ⇒ `modify`），全角 `：` 不剥：`- 修改：` 因此读 `other`，这一行连 ASCII 标签都剥不出。每段各自剥一次标签（第二段起的 `Modify:` 就是这样一个标签），只声明本段内的 span，**且括号里的 span 是附注、不是声明**——`（…）` 既不声明本段、也不跟进后一段（理由与三类静默面见下一条）。语料的**四类**方言因此都落在「声明行不限于 `create` 一种」这一臂，逐类给读法：`- 修改：`（全角冒号加中文动词，标签剥不出、首词不在表内 ⇒ `other`）· `- Modify (diagram evidence):`（标签剥得出 ⇒ `modify`）· 行内 `- **Files**: Create …; Modify …`（字段前缀后首词即动词 ⇒ 两段）· **第四类** `- **Files**: Modify: <path>；Create: <path>、<path>；Test: <path>`（`docs/kairos/plans/2026-10-10-engine-doc-tooling-p4.md` 的十一行，路径不带反引号）：冒号按上句剥掉 ⇒ `modify` / `create` / `test`，`；` 分段、`、` 再分段 ⇒ 每段一个动词、多条路径。第四类不读，「建三个文件」就一条声明都不算，而同一组声明写成第三类（行内反引号）照报——本节要收的正是这个假阴性。只有 `create` 进唯一性计数与顺序臂的「`Create:` 那一端」；`新建：` · `Add:` 与改的那些拼法（`修改：` · `Modified`）因此都不冒充 `Create:`——一条路径先被它们中的任一条认领、后来的任务再写 `Create:`，那个 `Create:` 就是晚的（顺序臂比的是 `Create:` 的任务号与**认领**该路径的那一行的任务号，与拼法无关）。方言不是边角，语料是这套语法的**验收条件**而不是两个计数：`docs/kairos/plans/*.md` 的每一条 `Files` 行都必须在上面这套解析下给出它的动词与路径——写得成第三类的九十一行分布在十二份 plan 上，第四类的十一行在第十三份 `p4` 上（两个计数各自描述一个方言集，不描述同一个集合）。留一类不认，两个任务各自行内 `Create` 同一路径的缺陷一条也报不出来，而同一条缺陷写成 `- Create:` 行则报——同一个瑕疵的两种合法拼法换出两个判决。
- **声明集是认领该路径的行，不是提到它的行**：顺序臂的一端因此写准——认领集是**覆盖整张五值词表的白名单**，没有一格落空：① 四词表动词（`create` / `modify` / `test` / `delete`）算认领。② `other` 那一格靠**两张闭集**判、不靠语义：建集恰 `add` · `新建`，改集恰 `修改` · `modified`。比较前先取标签首词、小写化、剥掉一个末尾冒号（`:` 与 `：` 都剥）——这一步属认领面，动词面照旧只剥 ASCII 冒号，故 `- 修改：` 的动词记 `other`、认领落改集。建集的语料是 `docs/kairos/plans/2026-10-10-engine-doc-tooling-p35.md` 的四条 `- Add:`（其中一行建 `packages/cdd-engine/src-next/infra/plan-source.ts`），验收的两条 `- Add:` 臂靠的正是这一格；改集的语料是 `docs/kairos/plans/2026-10-10-engine-doc-tooling-p31.md` 的三十条 `- 修改：` 与 `docs/kairos/plans/2026-10-10-engine-doc-tooling-p10.md` T5 的 `Script：… · Modified …` 一段（认领来自 `Modified` 那一段，不在四词表内、归改集），验收的 `- 修改：` 与 `- Modified` 臂靠的正是这两形。**两张都是闭集，判据因此是形态判断**（词在不在集里），不是内容判断「首词在说建或改」——`- 修改：` 与 `- Modify:` 因此同一判决，而表外的新拼法**不自动进集**：它落进 ③ 的默认、不算认领，要它算就加一个词加一条臂，不让引擎去猜语义（§6 的「形态可机械化 ⇒ 进引擎」在这一格上成立）。③ 其余一律**不**算认领：`other` 那一格默认不进认领集，`Script：` 一类不在两张闭集里的标签与剥不出标签的散文余量都落在同一个默认里，三类静默面只是这个默认里要逐类说明理由的那三格。三类**不**算，逐类给理由：(i) **免责标签**——`- Not in this task:` · `- Not in this phase:` 的宾语是「这条路径不归我」，把否定读成声明正好把意思读反；语料 `docs/kairos/plans/2026-10-10-engine-doc-tooling-p36.md` T8 就用手写清「这份文件归 T5」，紧接的 `Create:` 因此不晚。(ii) **核对与改名标签**——`Confirm:` · `Verify:` 的宾语是要去读的文件，`Remove:` · `Rename:` 的宾语是散文（语料这两类五行，宾语全是中文对象、一条路径也没有），它们都不声称「本任务动这个文件」。(iii) **括号里的 span**——`（…）` 是紧挨着那条声明的附注：`（cdd-engine minor）` 是 changeset 的登记面、「照同级文件名的写法」是范例引用，两者都不构成第二条声明；语料大量 `Files` 行在括号里写路径形状的 span，把附注读成声明会让 `docs/kairos/plans/2026-10-10-engine-doc-tooling-p10.md` T8 的 `Modify 三线并集 14 个测试文件（…）` 一行吐出十几条 `modify`，那几条里任意一条都把「只提了一嘴」的文件钉成「早于 `Create:`」的第二种读法——同一个 plan 因此读出两个判决。词表与声明集是两个面：词表答「这一段带什么动词」（五值，`other` 兜底），声明集答「这条路径有没有被认领」——`Add:` · `新建：` · `修改：` · `Modified` 在词表里是 `other`、在声明集里是认领，两个面分开，一个格才不会同时回答两个问题。同一个路径陈述的两种拼法（任务 3 写 `- 修改：<p>` 与写 `- Modify: <p>`）因此只有一个判决，而验收的 `- 修改：` 臂与 `- Modify:` 臂正是这两半。
- 判：对**至少带一条 `Create:` 认领**的路径，其 `Create:` 声明恰一条，且其任务号小于认领该路径的任何其他行的任务号。**无 `Create:` 的路径不判**——改既有文件是常态，按「每条路径恰一条 `Create:`」判会把整份语料判红。
- **只数路径形状的 token**：`fileTokensOf` 给的是每个反引号 span，而 `Files` 行的括号里常写包名、符号与占位——`- Create: `.changeset/x.md`（`cdd-engine` minor）` 的两个 span 里只有一个名字是路径（括号里那个上一条已按附注落掉，这一道管括号外的裸词、符号与占位），按 span 计数就会把 `cdd-engine` 当成一个在两个任务里被建的文件。判据因此过一道与 `contract/pins.ts#ForwardPaths#declaredPathsOf` 同一个面：`PinVocabulary.pathOf(token)` 返回 `null` 的 token（`<slug>` 一类模式 · 无分隔符的后缀 · 带 `#` 的成员 · 裸词）不进唯一性与顺序的计数——两个任务各建一份不同的 `.changeset` 文件因此零拒绝，而同一条路径被两个任务 `Create:` 照报。同一行里同一条路径写两遍 = 一条声明（按行去重，不按 span 计）。
- 为什么不是「同一路径出现两次」：`Create:` 之后 `Modify:` 是正常增量结构（一个任务建文件、后一个任务加功能），判死它会让模板本身成为违例。判据因此是**唯一性与顺序**，不是重复次数。
- 两类违约共用一条判据行的两个臂：双 `Create`（两个任务都声称建它）与 `Modify→Create`（后一个任务建一个前一任务已改的文件）。报文点名两个任务号与那条路径。

#### 3.2 悬挂与成环

- 读面：`contract/task-blocks.ts#TaskBlock.fields` 的 `DependsOn` · `Consumes` · `Produces`。

- 成环：`DependsOn` 的值是声明的 id 列表（`contract/task-blocks.ts#PlanTaskBlocksReader.dependsOn` 返回 `readonly number[]`：逗号 / 空白分隔、去重排序），任务是这张一般有向图上的节点——**不是函数图**（单后继）：`DependsOn 3, 7` 是两条边，环可以从第二条边闭合。读面复用树里现成的图判断，取的是它的**公开面**：`session/graph.ts#TaskGraph` 的 `validate()` 已把环判成一条 `GraphIssue`（`kind: "cycle"`），判据读这条 issue 并逐字节复用它的 `task` 与 `message`。`task` 的取值写准：`#cycleMember` 返回的是 Kahn 残值里的最小任务号（`Math.min(...remaining)`），而残值既含环上成员也含传递地依赖环的任务，故它**不承诺是环上成员**——`session/graph.ts` 里 `GraphIssue.task` 的括注（「for a cycle — the lowest task inside the cycle」）是承诺过头的旧注释，判据不建在它上面。`#cycleMember` 是私有成员，不开公开副本。**同一次编辑把这两句注释改成它读到的那个值**：`session/graph.ts#GraphIssue.task` 的括注改成「Kahn 残值里的最小任务号——残值含传递依赖环的任务，故它不承诺是环上成员」，`#cycleMember` 自己的类注释（「the lowest task closing a directed cycle」）同批对齐；`message` 与 `fix` 的字节一字不动（判据与 `graph` 门的 `details` 都逐字节复用它们），改的只是让注释与残值臂的期望一致——残值臂的 `cycle@T1` 里任务 1 不在环上，旧注释读它就是在说一句测试当场反驳的话。出现环 ⇒ 报 `depends-on-cycle`。
- **站位与可达面写清**：`session/preflight.ts` 的 `graph` 门排在 `doc-contract` 门之前，而 `TaskGraph` 读的正是 `DependsOn` 边——一条 `DependsOn` 成环的 plan 在 wave / plan 线上先被 `graph` 门以 `cycle@T{n}` 拒掉，`doc-contract` 走不到这条新规则行。`depends-on-cycle` 因此是**同一判断的文档面表达**，不是抢在 `graph` 门前面的第二道拒绝：它的活站位是直接跑判据的那一面（`contract/judge.ts#Contract` 的 `validate` 判一份 doc key 为 `plan` 的文档），报文逐字节复用那条 `GraphIssue` 的 `task` 与 `message`（`cycle@T{n}: …`），与 `graph` 门的 `details` 同一句。验收因此在 `Contract` 面造环，dispatch 面的拒绝归 `graph` 门——两级对同一个 defect 给同一句。
- 两条判词各占一条规则行（档位可各自不同），**并各占一个不变量类**：`contract/rules.ts` 的契约是 one rule = one strategy，`Invariant.name` 是字面量、`contract/__tests__/rules.test.ts` 逐行断言 `name === declaration.id`，一类只能载一个名字。两条共用一个类，第二条的报文就会带上第一条的判词。两条都不动 `contract/declare.ts` 的 `#### DependsOn` 取值域——本相位判的是图的性质，不是字段的形状。
- **同一处登记表的行数注释**：`contract/rules.ts#RULE_REGISTRY` 的类注释现按 scope 报行数与总数（`doc scope 30 rows + ledger scope 2 rows = 32`），四条规则行落地后两个分值都变（§3 的三条 + §6 的顺序行）；`contract/__tests__/rules.test.ts` 的 `declares 32 rows: 30 doc-scope + 2 ledger-scope` 按构造变红、躲不过，注释那份却会静默留旧数，两份随即读两个分值。写法与 §1.2 的 `CRITERIA_ROWS` 注释同一条纪律：去掉逐 scope 计数、只留恒真的那一句（每一行都带 `scope`，取值 `doc` / `ledger`），或写准新的分值（`doc scope 34 rows + ledger scope 2 rows = 36`，`contract/__tests__/rules.test.ts` 的三条断言同批读 36 / 34 / 2）——二选一，与四条行同一次编辑落地。

- **顺序判据是单调，不是「末行最新」**：历史表的两种方向在语料里都出现，且都合法——故「最新一条在最末」这条判据会把一个合法方向整类判死。真正的缺陷只有一种：**某一行插错位置**，它的形状是**非单调**。判据因此写成「该表的版本序列全升或全降」，方向不论；方向不是一条实测计数，要一个数先在 `contract/census.ts` 记一行 `census:<id> = <n>` 再引用，正文不写分值。读面写准：`contract/invariants.ts#Invariant.historyVersions` 给的正是**行序**序列，判据逐对比较**相邻两行**的大小（`versionRank` 只比邻居，不用来挑出「全表最大版本那一行」），任一对反号即一条 finding。豁免挂 `skipWhenClosed`，坐标与取值给全：声明格是 `contract/rules.ts#RuleDeclarationBase.skipWhenClosed`，本行声明 `true`；生效处是 `contract/judge.ts#Contract.validate` 里的 `if (closed && binding.declaration.skipWhenClosed) continue;`——只有调用方交出 `closed` 时才豁免。语料里已闭合的历史文档因此不再重排（重排是纯翻动，不产生判断），规则抓的是在飞文档里的插错位。
- **能机械化的搬进引擎，不能机械化的删除**：本仓有一条自验断言抓过真缺陷——章程历史表的「末行是最新版本」，而引擎的 `change-history-latest-matches-front-matter` 按版本排序判、不判位置，故它在红的时候仍然绿。这条断言因此**搬**而不是删：新起一条顺序不变量，消费者同享，测试里那条随之退休。这条新行点名完整，不留实现者补：id 是 `change-history-newest-last`，`scope` 是 `doc`，起步 `warn`、本相位末任务同批翻 `block`（与 §3 的三条新行同一条纪律，`## Constraints` 的 warn 起步清单因此是四条）——这个 id 是**历史名**：它记的是本相位接过的「末行是最新版本」那条断言的原名，本行判的是单调，方向不进判据；p42 的 plan 也按这个 id 登记，本轮只改本 spec，改名就是造一处本轮修不了的跨文档漂移；它自占一个 `Invariant` 类（`Invariant.name` 是字面量，`contract/__tests__/rules.test.ts` 逐行断言 `name === declaration.id`）；读面是 `contract/invariants.ts#Invariant.historyVersions` 的**行序**序列上的相邻对（逐对按 `versionRank` 比大小，反号即一条），一份没有 `## Change history` 表的文档它是零候选。成对臂与候选臂就是本节上一段的同一张合成表，每臂点名自己的方向：全升（旧在上）⇒ 零 finding；全降（新在上）⇒ 零 finding（这一臂是方向无关的判别臂——按「末行最新」的旧读它必红）；三行里对调低位的相邻两行、序列因此夹一处反号 ⇒ 恰一条；把对调的两行复原 ⇒ 零 finding（成对：只改一行的位置，方向不动）；没有那张表 ⇒ 候选 0 且零 finding。同一次编辑的账还有两笔：`contract/rules.ts#RULE_REGISTRY` 加这一行、行数面按 §3.2 改分；`contract/rules.ts` 头部那句「Version ORDER stays presentation, not data integrity」改成本相位之后的真实读法——版本排序仍不进判据，被声明的只有「版本序列单调」这一条顺序腿（方向不进判据），漏改它就是让注释与注册表各说一句。判据分两种——形态可机械化（顺序、唯一、形状）⇒ 进引擎；内容正确性（某节该说什么）⇒ 谁也不判，属评审。

### 7. fix 轮的回合内判定

`cdd fix` 的 `checked` 列表里已经有 `doc-contract`，但判定落在**下一次派发**：修复轮写出一份违反形状规则的文档、提交，下一条命令才被拒。写的人在自己的回合里看不到红，代价是一次 hygiene 修复 + 一笔提交 + 一次重发。

- **座位是收口，不是提交之前**：提交发生在 child 的回合里，`cl:atomic-commit` 骑在每条壳的 `LICENSE_ITEMS` 上，引擎拿回控制权只能在 child 退出之后——「写回之后、提交之前」没有引擎的位置，把要求写在那个窗口里，实现者只能拿既有的行为换个名字交差。这条腿因此落在 `face/lifecycle.ts#verdictOf` 的 graded entry 面：与 `#structureViolations` 同一处、同一趟收口判断（基线在 `#dispatch` 取，判定在 `#verdictOf` 做——`face/lifecycle.ts#dispatch` 已经按这两段分开），跑同一条 `contract/judge.ts#Contract.validate`，入参构造沿用派发门那一处（`docKey` · 绝对路径 · 字节 · `root`，闭包事实同读那一个审计 `contract/pins.ts#PinAudit.provenClosed`，plan 目标的 `taskLayers` 与门同读 `session/graph.ts#TaskGraph` 的 `batches()`）——两处一个构造，不新起第二份判决形状。适用范围与门同一行：`face/dispatch-values.ts` 选 `docs-fix` 的 doc 形状目标（`TargetFaceTable.isDocShape`）；wave / branch 轮本来没有 doc 面，这条腿不跑。**不收在 child 的回合里**：那需要一个「打印一份文档的 `doc-contract` findings」的只读调用，八命令 CLI 没有这个面，新起一个 verb 是另一相位的事。
- **差分而非绝对，基准是门测得的 findings 本身**：基准不是摘要——`contract/doc-body.ts#DocBodyProjection` 的投影与 `session/ledger.ts#Ledger#docRevision` 的 sha1 只证明正文动过、说不出哪条 finding 是新的，且那份绑定在本轮**收口之后**才写（`session/run.ts#Lifecycle` 的 `#recordReviewedDocRevision` 读的是盘上此刻的字节），修复轮无从读它。基准因此是门自己的读数：`session/preflight.ts` 的 `docOutcome.findings` 此刻渲进 `checked` 行后即丢（`PreFlightVerdict` 不带这一格，`ok` 分支只留 `order` 与 `checked`），故它随判决面交出来——`PreFlightVerdict` 增 findings 一格（内部接口：零字节、`checked` 行不变、`--dry-run` 预览不读它），由 `session/run.ts#Lifecycle` 的 `advance()` 交给 `#dispatch`，与 `frame.structure` 同一个纪律：只住帧上（`OpenFrame` 一格），不进 `progress.json`、不进载体、不进 in-flight 记录。收口时按 finding 的**整个身份**做多重集差——逐条按 `kind@field@message` 比对、按键计条数，本轮新增的才算；报文用门那一处的 `kind@field: message` 形（那一形只是报文格式，不是比较键）；绝不与 `doc_hash` 比。键不许只取 `kind@field`：`field` 是分节标题（`measure-literal` 取 `ProseFace.fieldOf(record)`，即那条记录的 heading），同一条规则在同一标题下对两个裸字面各报一条、两条都读 `measure-literal@## Design`，故「修好基准那条、在同一标题下写出另一条」会在集合差里正负抵消、差分读成零新增——而那正是本行要拦的那一条。
- **差集不是恒真**：闭合态下这份基准恒为空，理由是可证的——门按 `block` 档拒（`session/preflight.ts` 的 `blocking` 过滤），而 `contract/rules.ts#RULE_REGISTRY` 的每一行都是 `block`（`contract/__tests__/rules-severity.test.ts` 的 `declares no warn row in the shipped registry` 用例钉的就是这条前提），故带任何 finding 的文档先被门拒、到不了修复轮，那时绝对判定与差集判定同值。它不恒真，是因为起步 `warn` 的四条规则行（`## Constraints` 的那张清单：`single-create` · `dangling-task-ref` · `depends-on-cycle` · `change-history-newest-last`——§3 的三条加 §6 的顺序行）：那段窗口里门放过它们，基准非空，差集因此给出与绝对判定不同的读数（绝对判定每轮重报那条既有 `warn`，修复轮永远收不了口）。这也是本行与 `## Constraints` 的「不做：差分恒真」不相冲的地方：那一行拒的是一条永远为真的差分，不是一条有非空基准的差分。
- **红则拒绝本轮的推进**：新增违例 ⇒ 本轮落一条 hard entry（`RoundViolation.hard` 加既有 `contract-violation` 因由，零新枚举、零新通道），报文逐条列出新增违例（`kind@field: message`，与门的 `details` 同一句形）。轮的结论因此是 BLOCKED：既有失败面据此不出 `next:` 行、退出码非零、同一命令重发同一轮——不是「交回 child 同一回合改完」（回合已经结束，而 `docs-fix` 的载体是 work 面，可写子集里没有 `findings` 一格，§1.1），也不是「下一次派发才红」（那正是本相位之前的落点）。
- **不承诺「不出提交」，承诺「不到下一跳」**：child 的提交已经落地（上一条的座位正是这么来的），故本轮之后文档在盘上是新的、提交在树上；引擎拒绝的只是推进。修复归下一次同一命令——`## Constraints` 的「引擎只拒不改」就是这一句：引擎不移动、不改写、不删除文档，恢复归编排器。
- **四条形状规则同批进写入约束**：修轮 prompt（`render/templates.ts#DOCS_FIX_SHELL`）把 `measure-literal` · `line-coordinate` · `live-arithmetic` · `temporal-indicator` 写成写文档时的硬约束，与既有「禁止 `any`」同级——软约束与硬判定同源，否则只是建议。这条是本相位的第七处消费面字节（`## Constraints` 的例外登记）。
- **同批改掉一句反向注释**：`session/run.ts#PlanStructure` 的类注释现写结构面「不登记 doc-contract 规则行，因为引擎唯一的 doc-contract 判定点是派发门」——本相位之后有两个判定点（派发门 + 收口腿），那句要在同一次编辑里改成它读到的两个点，否则下一任作者会照它先删这条腿。


### 8. 形状面的一处收口、一列座位与一条指针

本相位顺带修掉 P41 交付的形状门里一处「判据比名字宽」的误报——坐标文法把 `4.5:1` 一类小数比值读成 `path:line`——并给判据声明加一列 `seat`，另留下一条不修的指针（契约数字的红落在第二个家）。本节因此是一处修、一列新声明、一条不修的指针，外加一条被撤回的加宽记录（读数门保持窄域，见本节第二条）；符号 pin 的成员半不在本节交付（§9 做），本节对它的那一条是 §9 必须满足的条件，不是待办。

- **座位是规则声明的一列（新增）**：判据在三个位置生效——派发门 `session/preflight.ts`、收口 `face/lifecycle.ts#verdictOf`、语料守卫 `*.guard.test.ts`。`contract/rules.ts` 的声明行加 `seat`，取值是闭集 `dispatch` · `close` · `corpus` · `ledger` 的**非空子集**（多值，一行写下它生效的每一个座位）。**没有 `close` 专属的那一族**：§7 的收口腿跑的是同一张 `contract/judge.ts#Contract.validate`，§6 的语料守卫也跑它，故注册表里每一行 doc 面规则三处都生效、一律声明 `dispatch` · `close` · `corpus` 三值——把既有行写成只 `dispatch`、再把「收口那一族」声明成 `close`，会让收口腿看起来不判任何既有规则（与 §7 相反），而那一族并不存在。**ledger 面的两行占闭集里的第四格**：`closed-wave-fits-depends-on-layers` 与 `planned-tasks-vs-recorded-tasks` 只在 `session/preflight.ts` 的 `plan-ledger` 门经 `contract/judge.ts#Contract.validateLedger` 生效，从不进 `validate` 的 doc 面、也不进任何语料守卫——原有三格没有一格描述它们，故闭集补 `ledger` 一格，两行各声明恰好这一个值；把 `dispatch` 与 `close` 也盖到它们头上是一条假声明，下一任读者会照它去派发门找这两条规则。**谁读它、错了什么红**：读它的是 `contract/__tests__/rules.test.ts` 新增的一组断言加上那张**逐 id 的字面表**（从注册表抄一次、此后靠漂移变红，与 `contract/__tests__/rules-severity.test.ts` 钉 `PRE_GATE_DOC_IDS` / `PRE_GATE_LEDGER_IDS` 是同一形；不每次从注册表现算——现算就是拿注册表跟它自己对账，那一格永远绿。常量名随实现命名、不在本文钉字面：钉一个尚不存在的符号就是给交付树留一枚死 pin）。那张表按 §3.2 的新分值取全集：三十四条 doc 行（含六条形状行）各写 `dispatch` · `close` · `corpus` 三格、两条 ledger 行各写 `ledger` 一格，共三十六行——六条形状行与两条 ledger 行**都在表内**，不靠「本节的逐行清单」这只不存在的清单。断言三条：每个取值落在闭集内（表外值即红）· doc 行三格齐而 ledger 行恰一格 `ledger`（多一格或少一格即红）· 注册表与那张字面表逐 id 逐格相等（漂移即红）。**它不是过滤器**：三处消费者跑整张注册表、不看这一格，故一格写错不会让哪条规则静默跳过，只会让那条对账用例红。加这一列不是新层：它与既有的 `scope` 与 `severity` 是同一份声明的第三列。
- **读数门的窄域是设计，不是缺口（撤回加宽）**：`measure-literal` 只认阿拉伯数字配八词闭集。曾计划把域加宽到「数词 + 量词」，实测撤回：中文里「一条判据」「两处修改」是普通量词用法，与读数不可区分，加宽会把整片正常散文判成违例——英文的闭集成立，是因为英文散文里「阿拉伯数字 + tests」罕见。故这门只抓**无歧义**的形态；中文读数的收法在作者侧（不写读数）与 `census:<id> = <n>` 的约定里，不在文法里。
- **比值被读成坐标（修）**：`contract/invariants.ts#LINE_COORDINATES` 的第三条（`path:line` 那一形）把 `4.5:1` 逐段读成 `path:line`——`4` 吃前缀、`.` 吃点号、`5` 吃扩展名、`1` 吃行号。修法是要求冒号前至少含一个字母：文件名的必要条件，而小数比值没有。成对臂：`4.5:1` · `2.25:1` · `1.5:1` 三种比值一律通过，`cli.ts:41` 与 `contract/declare.ts:12` 照报——三项都带小数点、修前各报一条，故三枚探针同向；`3:1` 不带点、修前就已经通过，作探针两态同绿，不取。
- **符号 pin 的成员半归 §9（本相位交付，不是指针）**：`contract/pins.ts#PinAudit` 的 `symbol` 形状分两半判。**载体半是判过的**：载体解析不出来就报一条 `its carrier … resolves nowhere in the tree`（报文中段是该 pin 写的载体路径），歧义与行号范围同批判——载体解析不出来的成员 pin 报一条，报文点名那个载体。实例给在围栏里、正文不写：本 spec 自己就在 pin 语料里（`corpusOf` 含 `docs/kairos`），一行内代码段就是一整枚活坐标，写进来就是给语料守卫留一条死 pin——围栏是示例代码，`PinSpans.tokensOf` 只读围栏外的行内代码段：

```
no/such/dir/missing.ts#PinAudit  ⇒  its carrier `no/such/dir/missing.ts` resolves nowhere in the tree
```

占位形 `<absent>/missing.ts#PinAudit` **不是**这条的实例，臂不许建在它上面：`PinVocabulary.pathOf` 对带 `<>` 的 token 返回 `null`（模式不是坐标），`PinVocabulary.memberOf` 又要求两半各自过筛，故整枚是散文、报零条——拿它当夹具，臂在 §9 落地前后两态同绿，正是 D98 ① 要杀的惰性臂。**成员半不是**：它在全树符号并集里找，从不进载体内部，故一枚载体写作 `contract/review-criteria.ts`、成员写作 `PinAudit` 的 pin（`PinAudit` 的唯一声明处在 `contract/pins.ts`）在本相位之前零 finding。这一枚不写成行内的一整枚 pin：那条坐标在语料守卫下就是一条待迁移的死 pin，而本 spec 的正文不留要自己改自己的坐标。**缺的那一半是成员 pin 的载体半，不是裸 `symbol` 形**：裸 `symbol` 不声称任何文件，file 归位对它无话可说（整 token 判据本相位不动）；被 §9 接过去的是两具带载体的写法——路径载体与裸类名载体（裸类名是更大的那一半，且本相位之前没有任何文件可查）。语料因此按载体分两栏核，两栏都是条件而不是计数：路径载体里成员写在错误文件上的那些，与裸类名那一整具（一枚也不进文件、全部读的是全树并集），合起来就是迁移面，§9 落地后由 §9 的判据与反查把它们逐枚落到声明文件上。本 spec 自己就在 pin 语料里（`corpusOf` 含 `docs/kairos`），故正文里每一枚成员 pin 都要在 §9 落地后的判据下零 finding——交付态的臂是既有的语料守卫（`pins.guard` 的零 finding 断言），不留「门已经严了、语料仍写错文件」的中间态。
- **数字的红落在「第二个家」而不是数字本身（留指针）**：契约数字（阈值、比值、包体基线）应当只住一处并被文档引用，观测数字只进交付记录；`census:<id> = <n>` 是这条取向里最典型的一类。作者侧的这条约定属独立立项。


### 9. 符号 pin 的文件归位

`contract/pins.ts#PinIndex` 的符号表是全树并集，`path#Symbol` 的路径部分只用于识别「这是不是一枚 pin」，不参与解析。两半因此读两个面：**载体半是判过的**——载体路径解析不出来即报一条（`its carrier … resolves nowhere in the tree`，§8 的载体臂读的就是这一处），歧义与行号范围同批判；**成员半不是**——它在全树并集里找，从不进载体内部，故一枚写着错文件的成员 pin 照过，而 `PinShape` 认的 `path` 形状只覆盖不带 `#` 的那一半。

- **成员 pin 有三具写法，其中两具带载体**：① `path#member`——载体是一份路径；② `Class#member` 与 `Class.member`——载体是一个裸类名（两形同走一个 `PinVocabulary.memberOf` 分支：有 `#` 时切在最后一个 `#`，没有时切在第一个 `.`）；③ 裸 `symbol`——没有载体，走 `isSymbol` 的整 token 支路。语料只记条件、不记计数（判形用 `corpusOf` 全量 + `PinVocabulary.memberOf`；写进正文的分值会随正文自己的下一次编辑过期，故要一个数就先在 `contract/census.ts` 登记一行 `census:<id> = <n>`）：(a) ① 与 ② 两具载体合起来覆盖每一枚带载体的成员 pin，且裸类名那一具是更大的那一半；(b) 每一枚成员 pin 都在它的载体解析到的那一份文件里判，一个载体恰好一份文件；(c) 迁移面是判据在交付语料上读出的差集，不是一个计数。② 是本相位之前没有任何文件可查的那一具——不点名它，「改的是作用域」就只对路径载体那一小半的成员 pin 成立。③ 不声称任何文件，file 归位对它无话可说，故本相位不改它的判据。
- **改的是作用域，不是解析；两具载体、一张表**：`PinAudit` 已经会把成员 reference 拆成载体与成员两段（`member.carrier` · `member.member`），错的是两段都拿全树并集当答案。符号表因此改成「文件 → 该文件的符号集」，判据查**解析到的那个文件**；反查方向是**同一张表**——裸类名载体落到**声明**它的那份文件（用下一具的声明识别器判「声明」，不按「文中出现」判：`BoardView` 在多份文件里被用到，声明只有一处，在 `face/board-view.ts`）。两具载体因此一个机制：路径载体由 `PinVocabulary.pathOf` + `PinIndex.resolve` 落到文件（缺失与歧义已各报一条），裸类名载体由这张表反查落到文件；落成**恰一份**之后，成员由同一个文件归位判定。落不成恰一份（声明在零份或多份文件里，或类名只以用法出现）⇒ 恰一条 finding 点名该载体与它的候选，与路径第三层「不替文档挑一个候选」同一读法——故一个在语料里不是唯一标识的裸类名必须改写成路径载体；这是同一张表的另一个方向，不是新增的解析器。
- **路径形状只由 `PinVocabulary.pathOf` 说（本相位之前已经如此，本节只把这句话钉住）**：「这个 token 像不像路径」只有一个判者——`contract/pins.ts#PinVocabulary.pathOf`。`contract/pins.ts#ForwardPaths#declaredPathsOf` 里那条 `/^\s*[-*]\s+Create:/` **不是第二个判者**，它是**行选择器**：选中 `- Create:` 行之后逐 token 交给 `PinSpans.tokensOf` + `PinVocabulary.pathOf`，形状判定本来就在后者手上。故本相位不合并任何东西，只把两句话摆正：行选择器保持全身扫面（块内块外同读），动词那一面由 §3.1 的投影供给 `single-create` 的动词格；豁免集**不动**——`Add:` 与 `新建：` 不豁免未落地 pin，豁免只认 `Create:`。`contract/task-blocks.ts#PlanTaskBlocksReader#fileTokensOf` **不是判者**——它是分词器（剥 bullet · 剥 `FILE_ROW_LABEL` · 落掉占位 · 按分隔符切 span），切出的 token 交 `PinVocabulary.pathOf` 判形状；本相位只按 §3.1 给它加分隔符切分，不改它的职责。
- **成员形态要认得**：两具带载体的写法（`path#member` 与裸类名载体）共用一个成员判据——一个名字算「在那个文件里」的条件是它以**声明形态**出现，不是「文中出现过这个词」——按词出现算是把注释与字面量里的提及当成坐标。判「声明形态」的是一处**声明识别器**，吃 `contract/pins.ts#PinSource.codeOf(text)` 的输出而不是标识符分词器：`codeOf` 抹掉 `//` 与 `/* */` 的正文、**保留字符串字面量**（一个字面量是值，不是散文），故只在注释里出现过的名字已经不在它里面，而只在字符串字面量里出现过的名字仍在——**判别臂只能落在字符串那一半**，注释那半在相位之前就是绿的。**形态闭集分两栏写，成员那一栏不只类体**：声明一栏是类 · 接口 · 类型 · 常量 · 函数 · 枚举；成员一栏是四种——类体里的方法与字段、**接口体里的方法与字段**（`readonly carrierPath?: string | null;` 这一类）、**类型字面量里的属性**（`type X = { … }` 与对象类型注解里的属性），以及**对象字面量里的属性键**（`export const ENGINE_RUNTIME = { … } as const` 一类常量表：语料里 `ENGINE_RUNTIME` 一枚常量载 17 枚 pin · `CAPSULE_WORDS` 6 · `ARGV_CHANNEL` 4 · `NEXT_HOP_REASON` 与 `DISPATCH_REASON` 各 1，共 29 枚）。`codeOf` 给的是整份文件的代码正文，接口体、类型字面量与对象字面量的属性都在其中，故「成员」不是多一条分词器，是同一处识别器多认三形。**这一栏不是补充说明，是语料的多数**：裸类名载体里成片的是 interface / type 载体（`readonly …` 属性一类；本 spec 自己的坐标正落在这一片）——`RoundRecord.carrierPath` 是 `session/ledger.ts` 里 `export interface RoundRecord` 的一枚 `readonly carrierPath?: string | null;`，`RoundFinding.severity` 在同一个接口里，`GraphIssue.task` 在 `session/graph.ts` 的接口里。闭集只写「类体里的」，整片 interface / type 载体 pin 当场判死，§9 自己的启动条件（正文里每一枚成员 pin 零 finding）当场不可达。闭集之外出现、而只在字面量或注释里出现过的名字 ⇒ 该 pin 报一条。成对臂两枚，就在这一栏上：`RoundRecord.carrierPath` ⇒ 零 finding；同一枚把成员换成该文件里任何形态都没有出现过的名字 ⇒ 恰一条。**成员半的拼写必须先过 `PinVocabulary.isSymbol`**：三段的 `path#Class.member` 成员半带点、过不了这道筛，它不是一枚被读的 pin 而是散文；本相位**不**放松这道筛（放松会把语料里每一个带点的名词送进 pin 面），故任何验收臂都不许写在这个拼写上。
- **迁移归本相位，两具载体都在面上**：改成文件归位之后，语料里路径对而符号在别处的 pin 会一次性变红——路径载体里成员不在载体文件里的那些，与裸类名载体里「声明文件唯一且成员就在那里」之外的部分（成员不在声明文件里、类名声明在零份或多份文件里）一次性变红。它们逐条改到正确的文件，三类各一条落法：成员实际住在另一份文件的改路径（`gate.ts#linePhase` 那几枚住在 `session/ledger.ts` 的 `Ledger.linePhase`，路径改到那一份）；类名不是唯一标识的改写成路径载体；**成员在树里根本没有声明的**，把坐标改指取代它的那份实现、或删掉那条已无对应实现的 claim，**绝不改到同名的测试 helper 上**（本工作区语料里那几枚载体写作 `face/board-view.ts`、成员写作 `#nextOf` 的 pin：`#nextOf` 随 board / next 重做一起退场，树里仅存的 `nextOf` 是 `face/__tests__/board-view.test.ts` 里的用例局部辅助，同名而无关——照「成员住在另一份文件」修，会把文档指到一份与 board 的 next 判断毫无关系的断言辅助上）。改写面是判据在交付语料上读出的差集，而不是把裸类名那一整具全数重写。差集的边界由 `pins.guard` 的零 finding 断言钉住——漏一条迁移就红一条，改法与判据同批落地，不留「门已经严了、语料还红着」的中间态。
- **报文与档位不变**：产出的依旧是一条 `pin` 形状的 finding，档位与既有的 `pins.guard` 一致；变的是它现在真的校验了路径。
